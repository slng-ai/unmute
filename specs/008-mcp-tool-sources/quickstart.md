# Quickstart: validating MCP tool sources end to end

Feature: `008-mcp-tool-sources` · Date: 2026-08-13

This is the validation guide for the finished feature. It proves the spec's
success criteria SC-001 through SC-007 with the repository's own gates plus
one live run per target. Contracts referenced: [contracts/](contracts/),
shapes: [data-model.md](data-model.md).

## Prerequisites

- Go 1.24, Docker running (web dev mode runs the deployable image).
- Root `.env` holding the voice-stack keys plus:
  - `FIRECRAWL_API_KEY` (already present at the root today)
  - `FIRECRAWL_MCP_URL=https://mcp.firecrawl.dev/v2/mcp`
- Build the CLI once: `make build` (binary at `bin/unmute`).

## 1. The repository gates (no Python, no network)

```sh
make fmt && make lint && make build && make test
```

`make test` must pass with zero Python. It now covers: load and validation of
the grown `mcp:` block (L1), the pipecat gate lifted and both emitter
agreement tests green (L1), generated bytes for both drivers pinned in goldens
that now contain MCP output (L3), and the example README link and transport
tests (L2/L3).

## 2. Validate and compile the example (SC-001, SC-002, SC-006)

```sh
bin/unmute validate examples/mcp-example
bin/unmute compile examples/mcp-example
```

Expected: validation green for both declared targets; `build/livekit/` and
`build/pipecat/` written; each `build/<target>/.env.example` names
`FIRECRAWL_MCP_URL` and `FIRECRAWL_API_KEY`; `compile-report.json` lists both
env names with their `tools/web_search.yaml mcp.*` reference sites.

Negative checks (each must fail before any artifact):

```sh
# a pasted secret value instead of an env name (SC-005)
# a transport outside {sse, streamable_http}
# a target that cannot run MCP tools (deepgram) (SC-006)
```

Each is an L1/L2 test in the suite; no manual step needed.

## 3. Copy credentials and run each target (SC-003, SC-007)

```sh
cp examples/mcp-example/build/livekit/.env.example examples/mcp-example/.env
# fill the named values from the root .env (FIRECRAWL_* plus the voice keys)

bin/unmute dev examples/mcp-example --target livekit
```

Talk to the agent in the browser over WebRTC. Ask something that needs
current information, for example "search the web for today's top story about
space". Expected: the agent calls `firecrawl_search` through the Firecrawl
MCP server, answers from the results, and neither the compile output nor the
container logs show an error.

Then the same for pipecat:

```sh
bin/unmute dev examples/mcp-example --target pipecat
```

Same conversation, same expectation, zero package edits between the two runs
(SC-002).

## 4. Selection check (SC-004)

With the dev run up, confirm the model sees exactly one Firecrawl tool:

- LiveKit: the generated `agent.py` mounts the server with
  `allowed_tools=["firecrawl_search"]`; the session log lists the offered
  tools at startup.
- Pipecat: the generated `bot.py` passes the selection as the client's tool
  filter; the log line that registers MCP tools names exactly one.

## 5. Optional smoke (L4, needs uv)

```sh
make smoke
```

Proves the emitted Python imports and instantiates against the pinned SDKs,
including the new MCP client code on both targets. Opt-in, never part of the
PR gate.

## Expected failure modes worth seeing once

- Missing `FIRECRAWL_API_KEY` in `.env`: the generated startup check names it
  before anything dials.
- Wrong `FIRECRAWL_API_KEY` value: the server refuses; the failure appears in
  the project log at session start (platform-native behaviour, documented in
  the emitted README).
- A selected tool name the server does not expose: the tool is never offered;
  nothing crashes (documented, not detectable at compile time).
