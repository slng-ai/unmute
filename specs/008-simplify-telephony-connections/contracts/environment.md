# Contract: where each environment name lives

The question that grew this feature: *where do credentials go, and where do the
numbers I dial go?* This page is the answer, and
`docs/user/reference/connections.md` will carry the same table for users
(FR-023b).

---

## The table

| Value | Declared in | In `secrets:`? | Documented in README + phone-calls page? |
|---|---|---|---|
| Carrier credentials (`account_sid`, `auth_token`, `from_number`, the four SIP values) | `connections/<name>.yaml` → `environment:` | **yes** | yes |
| Numbers dialled for a transfer | `agent.yaml` → `destinations:` | **yes** | yes |
| Model and tool credentials | `agent.yaml` → `secrets:` | yes (that is where they live) | yes |
| Route runtime variables (`DAILY_API_KEY`, `PIPECAT_CLOUD_ORGANIZATION`, `REDIS_URL`, `LIVEKIT_*`, `UNMUTE_*`) | nowhere — the route table supplies them | **no** | yes, **when they reach `.env.example`** |

Two rules, answering two different questions:

- **`secrets:` answers "what did the author write?"** Every name an author typed
  in a package file is listed there. Names no author typed are not, or every
  phone package carries boilerplate it did not choose (FR-005c).
- **The docs answer "what does the reader need to know?"** Membership of the
  generated `.env.example` is the whole test.

`DAILY_API_KEY` is the case that forces the two rules apart: never written by an
author, so exempt from `secrets:`; required at runtime and present in
`.env.example`, so documented.

---

## Why a name appears twice

A connection says `account_sid: TWILIO_ACCOUNT_SID`. `secrets:` says
`TWILIO_ACCOUNT_SID`. These are not redundant:

- the connection line says which **role** the variable plays on the route, which
  `secrets:` cannot express;
- the `secrets:` line says the runtime **requires** it, which the connection
  cannot express for names no author writes.

The agreement between them is the existing V10 cross-check, at warning severity
(`contracts/errors.md` §10). This is a recorded deviation from Principle III and
is justified in `plan.md`'s Complexity Tracking.

---

## Documentation rule (FR-005f)

**What the docs say about environment variables equals the generated
`.env.example`. Nothing missing, nothing extra.**

- **Nothing missing** — every name in `.env.example` is documented with what it
  is and where to get it. Checked (FR-027a).
- **Nothing extra** — a variable the reader never sets is not mentioned at all.
  Naming one only to say "you do not set this" gives a reader something to worry
  about and nothing to do with it. Editorial, not checked, because a check strict
  enough to catch it would fail deliberate teaching lines such as
  `twilio-telephony-hello`'s use of `11LABS_API_KEY` as an unexportable name.

### Membership is per-route, and that is not an inconsistency

`REDIS_URL` reaches `.env.example` on the carrier-websocket and connector routes —
`unmute dev` injects it locally, the operator sets it for a deploy — and never
reaches it on cloud-websocket or SIP, which do not read it. So it is documented in
`outbound-reminder` and absent from `twilio-telephony-hello`, and both are
correct. Do not "fix" the difference.

### The deletion this rule forces now

`examples/twilio-telephony-hello/README.md` currently names
`UNMUTE_OUTBOUND_TOKEN`, `UNMUTE_PUBLIC_URL`, and `REDIS_URL` to tell the reader
not to set them. Neither route in that package reads any of them and none reaches
its `.env.example`, so the paragraph goes (FR-005h).

## What `.env.example` contains

Generated by `secretEnvDocs` in two lists:

1. the names declared in `secrets:`;
2. the route-required names the package never declared, labelled once as a group.

After FR-005a most names move into list 1, and list 2 narrows to the
driver-supplied ones an author never writes.

**Known consequence**: a package with an empty `secrets:` block keeps the plain
unlabelled name list. `livekit-human-transfer` and `pipecat-human-transfer-twilio`
have no `secrets:` block today and gain one, so their `.env.example` switches to
the two-list form. Those two goldens change, for that reason and no other. Any
other golden that moves is a bug in this feature.

## Per-example accounting

| Example | Connection env | Destinations | `secrets:` today | `secrets:` after |
|---|---|---|---|---|
| `twilio-telephony-hello` | 3 Twilio + 4 SIP | none | 2 model keys | 2 + 7 |
| `livekit-human-transfer` | 4 SIP | 2 | **none** | gains 4 + 2 + its model keys |
| `pipecat-human-transfer-twilio` | 3 Twilio | 1 | **none** | gains 3 + 1 + its model keys |
| `outbound-reminder` | 3 Twilio (in each of two connection files) | none | 5 | 5 + 3 |
| `pipecat-human-transfer-daily` | none — the connection declares transport only | 1 | **none** | gains 1 + its model keys |

`pipecat-human-transfer-daily` is the shape worth studying: no carrier
credentials at all, one destination, and `DAILY_API_KEY` required at runtime and
declared nowhere. Its README already documents that key in a table with what it is
for, and that table is the model the other four follow.
