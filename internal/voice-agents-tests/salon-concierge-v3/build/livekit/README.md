# salon-concierge-v3 — generated LiveKit Agents project

Generated by `unmute compile` (LiveKit driver). Model routes, prompts, agents,
tasks, and tools come from the source package. Entry agent: `Concierge`.

## Run

Install the generated dependencies, copy the environment template, and start
the LiveKit development worker.

```sh
uv sync                       # or: pip install -e .
cp .env.example .env          # then fill in the selected provider values
uv run python -m livekit.agents start agent.py   # run the worker
```

`unmute dev` uses local LiveKit ports `7880`–`7882`. To run beside another
LiveKit stack, move all three together:

```sh
LIVEKIT_HOST_PORT=7890 LIVEKIT_TCP_HOST_PORT=7891 LIVEKIT_UDP_HOST_PORT=7892 \
  unmute dev <source-dir> --target livekit
```

## Latency measurements

`dev_metrics.py` prints one line per turn to stdout, so you can see where a slow
reply went. It prints nothing unless `UNMUTE_DEV_METRICS` is set, and `unmute
dev` sets it for you. Nothing is sent anywhere: the line goes to stdout and that
is all.

```text
UNMUTE_METRIC {"kind":"turn","seq":1,"e2e":1.204,"user_turn":0.388,"stages":[...],"tools":[...]}
```

Read them with `grep UNMUTE_METRIC` on the run's output. Times are seconds.
`e2e` is from the caller falling silent to the agent starting to speak, each
entry in `stages` carries the time to first byte for that service and, for the
voice, the total time the reply took to stream out. `tools` carries how long each
tool took, including tools reached through a remote tool source. Controls are not
listed there: a task or a transfer hands the conversation somewhere else rather
than doing a unit of work, and a task does not return until the flow it started
has finished, so its duration is that flow's, not a tool's.

A measurement LiveKit does not report is left out of the line rather than sent as
zero, so a field you do not see was not measured, not instant.

This reads LiveKit session events, not OpenTelemetry spans, so it cannot
interfere with a trace exporter you have configured.

## Agent handoffs

A handoff with `announce:` gives the exact sentence spoken once by
the active agent, after any brief the handoff carries has been validated, so a
handoff refused for a bad brief never speaks it. LiveKit finishes the line
before it activates the receiving agent. Without `announce`, the handoff stays
silent.

The opening greeting belongs to call start only. A later handoff back to the
entry agent continues from the carried context and never repeats it. Transfer
tools become available after that entry turn, so carried history cannot send
the call straight back before the caller speaks again.

## Facts resolved before the greeting

This agent resolves some values once per call, before it speaks, so the model
never spends a turn discovering them. Each entry below runs in the order
`agent.yaml` lists it.

| Entry | Reads | Lands in |
|---|---|---|
| `today` | the clock, in `Europe/Madrid` | `booking_date` |
| `caller` | the call's own `from_number` | `customer_phone` |
| `profile` | `look_up_customer`, a read-only lookup | `customer_name` |

**The budget.** The whole block has 2.0 seconds, which you will find in the
code as `_PREFETCH_BUDGET_S`. Past that it gives up, the
values keep their declared defaults, and the call greets on time. Nothing here can
fail a call: a lookup that times out or raises is logged and stepped over.

**An entry can do nothing, and that is normal.** An entry whose inputs are empty
is skipped. A call that carries no caller ID skips every entry that reads one,
and every entry downstream of those, so the agent behaves exactly as it would
have without this block at all. Compiling for a target whose route supplies no
call facts prints a warning naming each entry it will skip there.

**The clock is read once, at session start, in `Europe/Madrid`.** Not the
container's clock, which is UTC and would name the wrong day for anybody who is
not on it.

**A call that crosses midnight keeps the day it started on.** The value is read
once and never refreshed, so a call beginning at 23:55 still says that day at
00:10. This is deliberate: a value that changed underneath a conversation would
be worse, because the caller and the agent would stop agreeing about what
"tomorrow" means halfway through. If a call really can outlast midnight and the
date has to follow, read it in a tool instead of pre-fetching it.

**A pre-fetched value can need confirming.** `customer_name` (confirmed by `verify_customer`), `customer_phone` (confirmed by `verify_customer`) arrive
filled but not yet agreed to. Until the naming step has heard the caller agree,
such a value appears in no prompt except that step's own, and any tool that
reads it is refused. So the agent reads the value back and asks for a yes
rather than acting on it, which is what stops somebody ringing from a friend's
phone being treated as the account holder.

**What you see in the log.** One line per entry, naming the entry and the values:

```text
prefetch today: resolved booking_date
prefetch profile: skipped, ...
```

A value is never written to the log, only its name, which matters when it is
something like a phone number.

## Turn taking

Two numbers decide how long a caller waits, and they are not the same number.

**The floor is 0.4s.** The prewarmed Silero VAD waits that much
silence before it reports end of speech. It comes from the package's
`endpointing_delay`.

Nothing downstream can start earlier, because the transcriber is only asked to
finalise once the VAD says the caller stopped. The runtime refuses anything under
0.25s, so `unmute compile` rejects it rather than letting the worker raise on its
first call.

**The ceiling is 1.6s.** That is `turn_handling`'s endpointing
`max_delay`, the longest the turn can run before closing regardless. It comes
from `pace: balanced`.

Mode is `dynamic`, so the wait adapts between 0.3s and
1.6s from the pauses this caller actually leaves.

**Lowering the floor alone does not shorten a turn.** The floor is when the
runtime may start deciding; the ceiling is when it stops waiting. A turn that
runs long is sitting at the ceiling, and only the pace moves that. This is worth
saying because getting it wrong here cost a whole round of measurement: a live
call spent 2.5s per turn in endpointing while the authored window was 0.4s.

Faster is not free. `pace: snappy` will occasionally answer a caller who was
pausing to think, and `patient` is the escape hatch for callers reading out
numbers, addresses or spellings.

## Handoffs and the opening turn

A receiving agent's automatic opening reply names the tools it may use, which is
every tool it has except its own handoffs: two agents that both want to route
would otherwise bounce the call before the caller hears anything. Every later
turn has the full list back.

## Tasks and task groups

A task may list a handoff in its own `handoffs:`. Calling it ends the active
task and any remaining task-group steps, then hands the caller directly to the
receiving agent. It does not return through the task owner. A task definition
has `tools:` and `handoffs:` and no other list, so a task or an escalation on a
task is unwritable rather than rejected: there is no key to put one in.

A task that lists no handoff still has a way out. Every task prompt here
ends with one generated rule: when the caller asks for something none of the
step's tools can do, and no handoff on the step covers it, call `finish` right
away with the closest result, naming that request in `unserved_request`. Every
`finish` here takes that field, optional and empty by default, and a filled one
rides the returned result: a `then: return` group's docstring tells the owner to
take that request next. The rule does not excuse skipping the step's own
work, and a handoff the step declares wins over it.

In a group with `context_scope: shared`, each exact typed result enters the
shared context before the next task starts. The result is labeled with its
source task so the next task can identify it. An isolated group carries no
results between steps. The final `merge: results` map is keyed by task name.

## Empty task responses

Before it generates anything, a generated task drops the call that started it
from its own copy of the conversation. That call is still running
while the task runs, so LiveKit adds it plus a placeholder result reading "The
tool call is still in progress." This is right for the agent that made the call:
it stops the model re-issuing a call already in flight. It is wrong for a task,
which is a different agent reading an unfinished call it never made, and which
then opens with nothing or apologises for a failure that did not happen.

Generated LiveKit tasks retry up to twice when a full successful response has
neither non-whitespace text nor a tool call. Each retry starts immediately in
the same speech turn. It keeps the task state and model settings, and
adds a distinct temporary recovery instruction to a fresh copy of the
conversation context before each retry. After a task tool returns, recovery
keeps only `finish` instead of the full tool list. Non-whitespace text or an
allowed tool call stops recovery.
Errors and cancellations keep LiveKit's normal behavior.

If all three opening attempts are empty, the task speaks one fixed brief
failure, runs no action, and stays active for the caller's next turn. If an
empty reply follows a task tool, recovery can only call `finish`; it cannot run
another operation. Exhausting that recovery asks the caller to check the current
state before trying again. This applies only to generated LiveKit tasks. Normal
LiveKit agents and Pipecat output are unchanged.

**Test in the browser before you test on a phone.** `unmute dev <source-dir>`
opens a browser session without checking a cold-transfer destination or other
values that only a real phone call reads.
Get the prompt and the models right there, then add `--telephony`. A missing
cold-transfer destination fails a real phone job before its greeting, not the
browser worker at startup. The browser loop is the shortest one this project has.

## Tools that speak first

A tool with `announce:` speaks that exact sentence as it starts, so the caller
is not waiting in silence while the call is in flight. The line is started, not
awaited: the tool's own work starts straight away and the caller hears the
answer no later than they would without the line. A tool whose injected values
are still unset is refused first, so a refused call stays silent. If the caller
speaks over the line, LiveKit still runs the tool to completion, which is what
its per-tool `interruption:` warning is about.
## Knowledge bases

The agent answers from these documents rather than from what the model
remembers. Each folder was copied into this project by `unmute compile`.

- `refunds`, from `knowledge/refunds/`, embedded with `text-embedding-3-small` (needs `OPENAI_API_KEY`). `hybrid` search over passages of 90 tokens overlapping 20, returning 3 per lookup
- `services`, from `knowledge/services/`, embedded with `text-embedding-3-small` (needs `OPENAI_API_KEY`). `hybrid` search over passages of 220 tokens overlapping 40, returning 3 per lookup

Four things to expect at run time:

- **Content is fixed until the next compile.** The documents in
  `knowledge/` are what this project searches. Editing the originals in the
  source package changes nothing here until you compile and deploy again.
- **Indexing runs once per worker process, at startup, not per call.** It
  happens in `prewarm`, before any job is accepted, so a caller never waits for
  it. Every worker process reads the whole corpus, so the cost is per process
  rather than per deployment.
- **Bake the index into the image and that cost disappears.** Without it each
  process embeds the corpus itself, once per process, so a larger corpus and more
  workers both cost more startup time. Baked, startup is a disk read instead.

  ```sh
  docker build --build-arg KNOWLEDGE_BAKE=1 \
    --secret id=OPENAI_API_KEY,env=OPENAI_API_KEY .
  ```

  The credential arrives as a build secret, so it is never written into a layer.
  Leave the flags off and the image still works, and the log says at startup that
  it is embedding instead. A lookup still embeds the caller's question, so the run
  time needs the same credential either way: baking removes the corpus cost, not
  the query cost.
- **A document with no text layer is named and skipped at startup.** A scanned
  PDF is an image of a page, and nothing can extract text from it without OCR.
  If some documents are readable the agent still starts and the log says how
  many of how many were indexed. If none are, the process exits and the
  deployment never reaches ready, the same as a missing credential.
- **A lookup that fails does not end the call.** The agent is told the lookup is
  unavailable and says so. The reason goes to this process's log and never into
  the model's context, because a model handed a provider error can read it out
  loud.

Nothing here writes outside the container. The index is in memory for the life
of the process and is not persisted anywhere.

## Declared state

Every agent prompt and every task prompt in this project ends with a block the
compiler wrote:

```text
Conversation info:
What this call has established so far. Read it rather than re-reading the conversation, and never ask for something already recorded here.
1. Booking date: {{booking_date}}
2. Customer: {{customer}}
3. Appointments: {{appointments}}
4. Complaints: {{complaints}}
5. Last booking day: {{last_booking_day}}
```

No prompt file contains it. Adding a field to a shape in the source package
changes every prompt here with no prompt file edited, so the model is told what
the call has established rather than being left to re-read the conversation.

The values it names:

- `booking_date` (`Date`)
- `customer` (`Customer | None`)
- `appointments` (`list[Appointment]`)
- `complaints` (`list[Complaint]`)
- `last_booking_day` (`Date | None`)
- `customer_phone` (`Phone`), which the caller has to agree to in the `verify_customer` step

What to expect when you read a prompt or a trace:

- A value with no contents renders as the words `none recorded yet.`, never as
  an empty list or a null. A step reading an empty structure cannot tell "not
  yet known" from "known to be nothing".
- A value with contents renders as compact JSON, never as a Python repr.
- A value the caller has not agreed to renders in its confirming step's prompt
  and nowhere else on the call.
- No declared secret renders in the block at all.
- One value is bounded at `_STATE_VALUE_MAX` characters. A longer one is
  shortened and logged, never dropped and never allowed to end the call.

Each declared shape is a generated Pydantic class in this module. A step's
result is validated against it before anything is recorded, so a value outside a
declared set never enters the state: the previous contents stay as they were and
the model is told which field and what was allowed, which is what lets it
correct itself on the next turn.

A text type with a validated shape (`Phone`, `Date`, `Time`, `Id`) is a `str` in
the schema the model is sent, with its shape checked by a validator. That is
deliberate: a `pattern` in the schema survives the strict tool-schema converter
and the provider rejects it, so the shape is checked here instead.


## Request block

A step or a receiving agent that declares `expect:` is handed those values by
the agent that ran it or handed the caller over, and its prompt ends with a
second block the compiler wrote, after the conversation state:

```text
# task handle_complaint
Request:
What you were handed for this visit. It does not change while you run.
1. Problem: {{problem}}
2. About: {{about}}

# task manage_booking
Request:
What you were handed for this visit. It does not change while you run.
1. Action: {{action}}
2. Service: {{service}}
3. Requested day: {{requested_day}}
4. Requested time: {{requested_time}}

# handoff to_complaints, read by complaint_specialist
Request:
What you were handed for this visit. It does not change while you run.
1. Problem: {{problem}}
2. About: {{about}}

# handoff to_concierge, read by concierge
Request:
What you were handed for this visit. It does not change while you run.
1. Outcome: {{outcome}}
2. Next request: {{next_request}}
```

The values are validated before the step is entered or the receiver is built.
A value outside its type is refused with the field named, nothing is started,
and the message reaches the agent that supplied it, which can correct itself or
ask the caller. A required value the agent left out is refused the same way. An
optional value left out renders as `not given.`, and the step
may ask for that one thing.

The values live on the shared state for one visit. A step's are put back when
it finishes, and a receiving agent's stay until the next handoff, so a brief
survives the receiver's own steps. Nothing about an expected value is recorded
unless the step's result carries it.

What each seam is handed:

- `handle_complaint` (step): `problem` (str) `about` (Appointment | None, optional)
- `manage_booking` (step): `action` (Literal["create", "modify", "cancel"]) `service` (Literal["haircut", "haircolor", "haircut_and_haircolor", "dry_cut"] | None, optional) `requested_day` (str | None, optional) `requested_time` (str | None, optional)
- `to_complaints` (handoff, read by `complaint_specialist`): `problem` (str) `about` (Appointment | None, optional)
- `to_concierge` (handoff, read by `concierge`): `outcome` (str) `next_request` (str)

## Deploy

Two supported paths: LiveKit Cloud with the `lk` CLI, or a worker you host
yourself. Both run this project as generated.

### Option 1: LiveKit Cloud

Before the first command: authenticate once with `lk cloud auth`, then set the
project this agent belongs to as the default (`lk project list`, then
`lk project set-default "<name>"`). Without a default project every command
below fails with a subdomain mismatch that does not say which side is wrong.

The first deploy registers the agent, builds the image from the generated
`Dockerfile`, and writes the `livekit.toml` this directory deliberately does not
ship, because the platform assigns both of its values.

```sh
cp .env.example .env            # then fill in the values
lk agent create --region eu-central --secrets-file .env
```

Every later version is a redeploy, which needs that config file and the
`Dockerfile` in this directory:

```sh
lk agent deploy
```

`create` is the first deploy and refuses to run when a config file of that name
already exists. `deploy` ships a new version of an agent that already exists and
takes no region. Running them the wrong way round either refuses or registers a
second billable agent with dispatch split between versions.

#### This worker's agent name

The worker registers as **salon-concierge-v3-livekit**, which is `name:` in your
`agent.yaml` joined to the `livekit` target it was compiled for.

It comes from the package rather than the target because every package on this
target calls its target `livekit`. Two packages in one LiveKit project that
registered the same worker name split dispatch between them, and a call reached
whichever answered first.

A dispatch rule matches a worker by that exact string, and this project's
`sip-dispatch-rule.json` already names it. Renaming the package leaves the rule
you already created pointing at the old worker, so inbound calls ring and
nothing answers.

Re-running `telephony-setup.sh` does **not** fix that. It reuses any rule that
already names your trunk rather than replacing it, which is what makes it safe
to run twice. Delete the stale rule first, then run it:

```sh
lk sip dispatch list   # find the rule whose agent is the old name
lk sip dispatch delete <SDR_...>
bash telephony-setup.sh
```

#### Secrets

`--secrets-file .env` sends every name in `.env.example` to the platform, which
injects them as environment variables. `LIVEKIT_URL`, `LIVEKIT_API_KEY`, and
`LIVEKIT_API_SECRET` are supplied by the platform itself: the CLI drops them
from the file, they must not be set in the image, and their absence from the
deployed secret list is correct rather than a mistake.

`.env.example` does not name them at all, for the same reason: it lists what you
fill in, and these are not yours to fill in. On LiveKit Cloud the SIP service is
managed, so `REDIS_URL` belongs to a self-hosted deployment and is never read by
the agent. "Carrier setup" above says where each value comes from, and
`compile-report.json` carries the complete list under `required_env`.

**Every name in that file must be a valid shell identifier**: letters, digits and
underscores, never starting with a digit. The platform exports your secrets with a
shell, so one bad name fails at export and that value is simply missing at
runtime. The agent then dies later, somewhere unrelated, and the only trace is a
single line near the top of `lk agent logs`:

```text
/etc/run/env: line 2: export: `11LABS_API_KEY=...': not a valid identifier
```

If you see that, rename the variable in `.env` (`ELEVENLABS_API_KEY`, not
`11LABS_API_KEY`) or delete the line, then run the overwrite command below.
Merging is not enough: the bad name stays until something replaces the whole set.

Change a value later without a full redeploy:

```sh
lk agent update-secrets --secrets-file .env              # merges into the existing set
lk agent update-secrets --secrets-file .env --overwrite  # replaces the whole set
```

#### Region

Region is chosen at the first deploy and is immutable. Moving one means creating
the agent in the new region and deleting the old one; the platform will not move
it in place.

#### Check it, and recover it

```sh
lk agent status                 # Sleeping is healthy on plans that scale to zero
lk agent logs
lk agent config --id CA_xxx     # rebuild a lost config file, then deploy again
```

`unmute compile` preserves any `livekit*.toml` the platform wrote here, so a
recompile does not cost you the agent. If a config file belongs to a different
project than the current default, the deploy fails with that same subdomain
mismatch: check `lk project list` and set the default that matches the file.

### Option 2: self-hosted worker

The worker connects out to a LiveKit Server you run and needs no inbound ports.
Build the generated `Dockerfile` into an image, set `LIVEKIT_URL`,
`LIVEKIT_API_KEY`, and `LIVEKIT_API_SECRET` to your server's values plus the
provider keys from `.env.example`, then start the worker:

```sh
python -m livekit.agents start agent.py
```

See `docs-site/deploy/going-live.mdx` in the Unmute repository for the full
self-hosted setup: server, Redis, firewall ports, sizing, and scaling.

## Human transfers

### Reading a transfer in the logs

`lk agent logs` shows three `info` lines per transfer.

Cold:

```text
human transfer fired: <control name> (cold)
cold transfer referring the caller out
cold transfer completed after <n>s
```

or `cold transfer failed after <n>s: <reason>`. There is a fourth line, and it is
the one most people meet first:

```text
cold transfer skipped: no phone caller in the room
```

**Cold cannot be tested from the Agent Console.** It refers the caller's *existing*
SIP leg out, and a console session has no SIP leg, so there is nothing to act on.
Warm works from the console because it dials out instead. The other cause of this
line is a dispatch rule pointing at a different agent name, so the call never
reaches this worker: compare `lk sip dispatch list` with the `agentName` in the
`sip-dispatch-rule.json` in this directory.

No log line carries a destination, a credential, an environment variable value,
or the caller's words. The control name on the first line already says which
destination fired.

## Trace with Langfuse

Tracing is configured. Set `LANGFUSE_SECRET_KEY`, `LANGFUSE_PUBLIC_KEY`, and
`LANGFUSE_BASE_URL` in `.env`; all three are required. The trace name is
`concierge-salon-concierge-v3-livekit`; the LiveKit room name becomes the Langfuse
session ID.

Starting the worker or exporting a synthetic span proves connectivity only.
Complete at least one user turn before reviewing the trace. A traced request
contains `llm_node` and `llm_request` generation observations in addition to
the session and agent spans.

Each tool call is its own span, named `tool:<name>` after the tool that ran. The
framework names all of them `function_tool` and carries the real name in an
attribute, which makes every tool call in a trace look the same, so the name is
put back on the way out. A task's structured result is the arguments of its
`finish` call, on that call's span.

Traces can contain caller speech, model input and output, and tool arguments and results.
Use only fake identities and fake customer data for release tests. Use a separate
Langfuse project for those tests, and do not send real customer data until its
access and retention rules are approved.

## Telephony setup

Your carrier's SIP trunk carries the phone calls and LiveKit runs this agent, on
the `livekit/sip/twilio` route. Setting it up is six actions in
your carrier's account, then one command here. The carrier part is yours to do:
nobody but you can sign in to your carrier account, so every step is written out
below.

You need two tools: `lk`, the LiveKit CLI, authenticated against this project
(`lk cloud auth`), and `jq`. Nothing else.

### Required configuration and credentials

Set these values in `.env` or your deployment secret store:

- `SIP_TRUNK_HOSTNAME`, `SIP_AUTH_USERNAME`, and
  `SIP_AUTH_PASSWORD`: the address your carrier's trunk accepts calls
  on, and the username and password it accepts them with, from
  your carrier's SIP trunking console. The termination step below is where you get all
  three.
- `SIP_FROM_NUMBER`: the phone number linked to that trunk, in
  E.164 form like `+15551234567`.
- `LIVEKIT_URL`, `LIVEKIT_API_KEY`, and `LIVEKIT_API_SECRET`: your LiveKit
  connection. On LiveKit Cloud the platform injects these into the deployed
  agent; set them yourself for a local run or a self-hosted server.
- `REDIS_URL`: the Redis that LiveKit Server and LiveKit SIP share. LiveKit
  Cloud runs its own and this agent never reads it; a self-hosted deployment
  needs one.

### Verifying it

A phone call reaches an agent that is deployed, so there is no local phone step
here. Deploy first (**Run** above), do the carrier setup below, then call your
number. That is the only arrangement that proves anything about the phone path:
a carrier reaches you over publicly routable SIP signalling and RTP ingress, and
a laptop behind normal NAT provides neither.

To hear this agent before any of that, run `unmute dev` in the source package
and talk to it in the browser. It exercises the same prompt, tools and model
settings with no phone involved.

### Get your origination URI

Both parts below need one value: the SIP address your carrier hands incoming calls
to. On LiveKit Cloud it is built from your **project ID**, not from your project
URL: drop the `p_` prefix from the ID and put the rest in front of
`.sip.livekit.cloud`. The two subdomains are different strings, so guessing from
`LIVEKIT_URL` gives an address that rings nowhere.

Run this to print every project you have configured, each with its SIP URI:

```sh
lk project list --json |
  jq -r '.[] | "\(.Name)  \(.URL)  ->  sip:\(.ProjectId | sub("^p_";"")).sip.livekit.cloud;transport=tcp"'
```

Take the line for the project this agent deploys to, and use the third column.
`lk project list` on its own marks the default project with `*`. Look at how
little the URL column and the SIP column have in common: that is why the SIP
address cannot be guessed from `LIVEKIT_URL`.

Keep that output piped through `jq`. The raw `--json` listing also contains your
project API key and secret, so it is not something to paste anywhere.

To use it in the commands below, set it once by project name:

```sh
LK_PROJECT="<the name from that list>"
LK_SIP_URI=$(lk project list --json | jq -r --arg n "$LK_PROJECT" \
  '.[] | select(.Name==$n) | "sip:\(.ProjectId | sub("^p_";"")).sip.livekit.cloud;transport=tcp"' | head -1)
echo "$LK_SIP_URI"
```

*Self-hosted LiveKit:* there is no project SIP URI. The address is the public SIP
signaling endpoint of the LiveKit SIP service you deployed.


### At your carrier (Twilio)

Do these in the [Twilio Console](https://console.twilio.com), in this order. Each
one names the console path, and the CLI equivalent where Twilio has one.

1. **Get a voice-capable phone number.** Phone Numbers, Manage, Buy a number,
   with the Voice capability. Skip this if you already own the number you want
   this agent to use.
2. **Create an Elastic SIP trunk.** Elastic SIP Trunking, Manage, Trunks, Create
   new SIP trunk. One trunk carries everything below.
3. **Termination, which lets this agent place calls.** On the trunk's Termination
   tab, set the Termination SIP URI to a domain name you choose ending in
   `pstn.twilio.com`, for example `my-agent.pstn.twilio.com`. That one domain is
   the value of `SIP_TRUNK_HOSTNAME`; there is no second address to
   look for. Then under Authentication, select or create a Credential List: the
   username and password you put in it are the values of
   `SIP_AUTH_USERNAME` and `SIP_AUTH_PASSWORD`.
4. **Origination, which lets calls reach this agent.** On the
   trunk's Origination tab, add an Origination URI: your LiveKit project SIP URI
   with `;transport=tcp` on the end, like
   `sip:abc123def.sip.livekit.cloud;transport=tcp`. Leave priority and weight at
   1 and tick Enabled. Two ways to get that URI: read it from the LiveKit Cloud
   project settings page, or derive it from the project ID with the command in
   **Get your origination URI** below. **Do not build it from `LIVEKIT_URL`**:
   the project URL subdomain and the SIP subdomain are different strings.

   *Self-hosted LiveKit:* there is no project SIP URI. Point origination at the
   public SIP signaling address of the LiveKit SIP service you deployed instead.
   Every other step on this page is the same.
5. **Attach the number to the trunk.** The trunk's Numbers tab, Add an existing
   number. The number you attach is the value of
   `SIP_FROM_NUMBER`. CLI: `twilio api trunking v1 trunks
   phone-numbers create --trunk-sid <trunk-sid> --phone-number-sid <number-sid>`.
6. **Turn transfer on, because this agent hands calls to a person.** On the same
   trunk, under Features: set Call Transfer (SIP REFER) to Enabled,
   tick Enable PSTN Transfer, and choose a Caller ID for Transfer Target. CLI:
   `twilio api trunking v1 trunks update --sid <trunk-sid> --transfer-mode
   enable-all --transfer-caller-id from-transferor`. Transfer caller ID is a
   trunk setting, never something one call can choose.

   `from-transferor` presents your own number to the person receiving the
   transfer, and connects anywhere. `from-transferee` presents the caller's
   number instead, which reads better but only works where the receiving
   carrier accepts a number your account does not own; across a border it is
   usually refused, and every transfer then fails instantly with `486 Busy
   Here` and a zero second, zero cost leg in the Twilio call log.

LiveKit's own version of these steps is the
[twilio provider guide](https://docs.livekit.io/telephony/start/providers/twilio/), if you want
a second description of the same thing.

#### The same steps as commands

Prerequisites: the [Twilio CLI](https://www.twilio.com/docs/twilio-cli/getting-started/install)
with a profile (`twilio login`), plus `lk` and `jq`. Run the block from this
directory, top to bottom, with `LK_SIP_URI` already set above. Nothing is
copied by hand:
each command finds what it needs from the one before it, by the domain and number
you already know. Verified against `twilio-cli` 6.2.4 and `lk` 2.18.2 on
2026-08-12.

```sh
# You choose these two. The domain must be unique across Twilio and end in
# pstn.twilio.com. Twilio requires the password to be 12 characters or longer,
# mixed case, with at least one digit.
TRUNK_DOMAIN="salon-concierge-v3-trunk.pstn.twilio.com"
SIP_USERNAME="salon-concierge-v3-agent"
read -rsp "SIP password: " SIP_PASSWORD; echo

# The number you already own, read from .env exactly as telephony-setup.sh reads it.
NUMBER=$(sed -n 's/^SIP_FROM_NUMBER=//p' ./.env | head -1 | tr -d "\r\"'")

# Steps 1 and 2: the trunk, then its SID looked up by the domain you just chose.
# Already have a trunk? Skip the create and list what you have instead:
#   twilio api:trunking:v1:trunks:list -o json |
#     jq -r '.[] | "\(.friendlyName)  \(.domainName)  \(.sid)"'
twilio api:trunking:v1:trunks:create --friendly-name "salon-concierge-v3" --domain-name "$TRUNK_DOMAIN"
TRUNK_SID=$(twilio api:trunking:v1:trunks:list -o json |
  jq -r --arg d "$TRUNK_DOMAIN" '.[] | select(.domainName==$d) | .sid')

# Step 3, termination: the trunk domain is the address, and a credential list
# holds the username and password. Three commands: create the list, put the
# credential in it, attach it to the trunk.
twilio api:core:sip:credential-lists:create --friendly-name "salon-concierge-v3"
CL_SID=$(twilio api:core:sip:credential-lists:list -o json |
  jq -r --arg n "salon-concierge-v3" '.[] | select(.friendlyName==$n) | .sid' | head -1)
twilio api:core:sip:credential-lists:credentials:create --credential-list-sid "$CL_SID" \
  --username "$SIP_USERNAME" --password "$SIP_PASSWORD"
twilio api:trunking:v1:trunks:credential-lists:create --trunk-sid "$TRUNK_SID" \
  --credential-list-sid "$CL_SID"

# Step 4, origination: where Twilio sends calls that arrive on your number.
twilio api:trunking:v1:trunks:origination-urls:create --trunk-sid "$TRUNK_SID" \
  --friendly-name "LiveKit SIP" --sip-url "$LK_SIP_URI" --weight 1 --priority 1 --enabled

# Step 5: attach the number to the trunk.
NUMBER_SID=$(twilio phone-numbers:list -o json |
  jq -r --arg n "$NUMBER" '.[] | select(.phoneNumber==$n) | .sid')
twilio api:trunking:v1:trunks:phone-numbers:create --trunk-sid "$TRUNK_SID" \
  --phone-number-sid "$NUMBER_SID"

# Step 6: allow transfers, including out to the phone network. Without this the
# carrier rejects the cold transfer.
twilio api:trunking:v1:trunks:update --sid "$TRUNK_SID" \
  --transfer-mode enable-all --transfer-caller-id from-transferor

# Finally, put the three termination values in .env:
#   SIP_TRUNK_HOSTNAME=$TRUNK_DOMAIN
#   SIP_AUTH_USERNAME=$SIP_USERNAME
#   SIP_AUTH_PASSWORD=the password you typed above
```

#### Check the carrier side

```sh
twilio phone-numbers:list -o json |
  jq -r --arg n "$NUMBER" '.[] | select(.phoneNumber==$n) | "trunk: \(.trunkSid // "none")"'
twilio api:trunking:v1:trunks:list -o json |
  jq -r --arg s "$TRUNK_SID" '.[] | select(.sid==$s) | "transfers: \(.transferMode), caller id: \(.transferCallerId)"'
twilio api:trunking:v1:trunks:origination-urls:list --trunk-sid "$TRUNK_SID" -o json |
  jq -r '.[] | "origination: \(.sipUrl) enabled=\(.enabled)"'
```

Expect the trunk SID you just created, `transfers: enable-all`, and your LiveKit
SIP URI enabled. These three lines are the three ways this side goes wrong:
`trunk: none` means calls to that number never reach LiveKit;
`transfers: disable-all` or `sip-only` is what makes a cold transfer to a phone
number fail; a missing or disabled origination URI means the call arrives at
Twilio and stops there.

### At LiveKit

One command, run from this directory with `.env` filled in:

```sh
bash telephony-setup.sh
```

It creates the two records an incoming call needs, and it finds them by your
phone number, so there is no ID to copy anywhere:

- the inbound trunk, which claims your number for this LiveKit project;
- the dispatch rule, which routes calls on that number to this agent, one
  `call-*` room per caller.

Only incoming calls need records like these. A call arrives with no request of
yours for configuration to travel with, so the platform has to already know
which project owns the number and where the caller goes. Placing a call is the
opposite: your own code starts it, so the trunk settings ride along.

Run the command again any time. Whatever already exists is reused, and it says
which. Two failures it can report: your number is already claimed by a trunk
this project cannot see, which means someone else owns it; or `lk` is not
authenticated, which `lk cloud auth` fixes.

Earlier builds of this project also needed `LIVEKIT_SIP_INBOUND_TRUNK` in the
environment. That variable is retired and nothing reads it, so delete it from
`.env` and from your platform secrets.

### Take it live, in order

The two halves above can be done in either order, but a call only works once both
exist and the agent is running. This is the whole sequence, from a compiled build
directory:

1. **Carrier**: the steps above. If you already have a trunk, the two that are
   easy to miss are attaching your number to it and, for a cold transfer, the
   transfer toggles. A number that is not on the trunk never reaches LiveKit, no
   matter how right the origination URI is.
2. **LiveKit records**: `bash telephony-setup.sh`, then run it again and expect
   every line to say reused.
3. **The agent**: `lk agent deploy` from this directory (or `lk agent create` the
   first time, see Deploy above), then `lk agent update-secrets --secrets-file .env
   --overwrite` if you changed `.env`. Check `lk agent status`.
4. **Call your number** from a phone. The agent answers. Ask for whatever the cold
   transfer covers; you should be connected onward and the agent should drop out.
5. **Read `lk agent logs`.** The transfer lines are listed under Human transfers
   below. Check the top of the log too: that is where a bad secret name shows up.

If the call rings and drops with no agent, work backwards: does
`lk sip inbound list` show a trunk claiming your number, does `lk sip dispatch list`
show a rule for it naming `salon-concierge-v3-livekit`, and does `lk agent status` show the
agent up. Each of those is one of the three steps above.

### What transfers need

Cold transfer needs nothing at LiveKit beyond the records above. It refers the
caller's existing call out through your carrier, so the carrier toggles in
step 6 are its only setting. It cannot be tested from the Agent Console, because
a console session has no phone leg to refer. When the logs say
`cold transfer failed after <n>s`, the usual cause is that step 6 was skipped:
Call Transfer (SIP REFER) or PSTN transfer is off on the trunk.



### Scale the route

Redis is control-plane infrastructure, not an audio hop. LiveKit Server uses
it for distributed room state and routing; LiveKit SIP uses the same Redis
deployment to coordinate SIP participants with the server. Audio still flows
through the SIP/RTP and LiveKit media services. Scale worker replicas on active
jobs, keep the shared Redis available, and drain active calls before shutdown.
## Carrier setup you have to do yourself

Going live on this route needs real carrier configuration. Every step below is
dictated by the route and none of them is performed by any local development
run. A local run that completes proves the wiring on this machine and nothing
about your carrier account.

1. get LIVEKIT_URL and the API key pair from the LiveKit Cloud project settings, or from a self-hosted LiveKit Server configuration; a self-hosted deployment configures LiveKit Server and LiveKit SIP with the same Redis deployment
1. point the carrier's origination URI at the LiveKit project SIP URI with transport=tcp (the LiveKit Cloud project settings page, or lk project list --json with the p_ prefix dropped from ProjectId); for a self-hosted deployment, deploy LiveKit SIP with public SIP signaling and RTP ports and point origination at that public SIP endpoint instead
1. get the selected carrier SIP address, username, password, and phone number from its SIP trunking console; these four reach the deployed agent's dial-out path directly, so no outbound trunk is registered
1. for inbound calls only, run bash telephony-setup.sh from the build directory: it resolves the inbound trunk by phone number and creates the trunk and dispatch rule, so no record ID is ever copied by hand

Do not edit this project by hand — it is regenerated from the agent spec.
Change the package and recompile.
