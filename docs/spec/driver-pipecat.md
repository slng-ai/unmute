# SPEC — Pipecat driver (generate.Artifact case)

Consumes the core: [compiler.md](compiler.md) (`ir.Agent`, `ir.Target`, the capability table, the `Artifact` socket). Schema truth: [SCHEMA.md](../SCHEMA.md). Pipecat facts: SCHEMA.md conditions ¹ + ORCHESTRATOR_SHARED_CONFIGURATION.md footnote ¹. Where they disagree, SCHEMA.md wins.

Type: **code target**. Emits a Pipecat Python project on disk (`Artifact.Files`). The generator lives in `internal/generate/pipecat_v1.go` and renders embedded `templates/pipecat_v1/*.tmpl` files from the v1 IR.

## §G goal
Lower a validated `ir.Agent` + a `pipecat` target instance into a runnable Pipecat project: `bot.py` (pipeline, agents, tasks/Flows, controls, tools, conversation), dependency + deploy files, and a compile report. Cascaded pipeline only. Flows lives in `pipecat-ai` core (`pipecat.flows`) since 1.5.0.

## §C constraints
- C1: Go emits Python via `text/template` (ADR-0002). Python is generated, never maintained here. Embedded template FS.
- C2: all four roles are **open** (listen, turn, speak, reason): every used profile needs a binding (core V9). Custom OpenAI-compatible STT/TTS is a config forward — `OpenAISTTService`/`OpenAITTSService` take a documented `base_url` override; subclass only for non-OpenAI protocols.
- C3: framework pin. `version:` checked against the driver's template-compatible range (codegen check, not model validation). Flows no longer needs a `pins:` entry (core since 1.5.0); **never pin the deprecated standalone `pipecat-ai-flows`** (rule 11).
- C4: `flow_manager.state` exists only under a FlowManager; a T0/T2-only source has no Flows, so the driver generates a typed state store for `variables`.
- C5: per-task `model:` is **gated on Pipecat** (capability table deny; SCHEMA 4.6). The paper mechanism (`LLMSwitcher` — `FlowManager` accepts `llm: LLMService | LLMSwitcher`) fails at runtime on 1.5.0: `LLMWorker(llm=switcher)` crashes in `_register_tools` (the switcher lacks the private `_register_direct_function`), and a switcher placed inside the worker's pipeline stalls every flow frame (spike-verified 2026-07-16, B7). The gate lifts when a working switch-inside-worker lowering is proven. A standalone task is a one-node flow — same code path as a group, no separate `@job` mechanism.
- C6: never use Pipecat's deprecated `ContextStrategy.RESET_WITH_SUMMARY` (removed in 2.0.0); its deprecation notice points to Pipecat's **native** summarizer (`LLMContextSummarizer` / `LLMAutoContextSummarizationConfig`), so a `history: summary` lowering configures that native summarizer instead of hand-building one.
- C7: a runnable cascaded bot needs scaffolding beyond the role bindings — transport in/out wiring (`transport.input()` → STT → context aggregator → LLM → TTS → `transport.output()`), a VAD analyzer (`SileroVADAnalyzer`), and a runner. The `turn` role lowers to VAD + smart-turn analyzers, not an API-keyed service, so its binding is advisory (SCHEMA §4.2) — the template supplies the analyzer. (Runner spelling corrected against current docs 2026-07-15: Pipecat's current worker API is `WorkerRunner` + `PipelineWorker` from `pipecat.workers`/`pipecat.pipeline.worker`, not the older `PipelineRunner`+`PipelineTask`; the workers subsystem is also where `@job`/`activate_worker` live, so one API covers the pipeline, handoff, and delegate-and-return.)
- C8: the driver lowers the agency model through **two mechanisms, each on Pipecat's documented recommended path** (rewritten 2026-07-16, B7; every API claim below verified end-to-end against real pipecat-ai 1.5.0 — scripted-SSE spike, not docs alone). **Handoff = workers/bus**: each agent is an `LLMWorker` (its own LLM = `reason` binding, system instruction = agent instructions); `agent_transfer` is a `@tool` calling `activate_worker(target, args=LLMWorkerActivationArgs(messages=[reason]), deactivate_self=True)` (V3 native handoff + reason message); webhook tools are `@tool` methods; context management chooses what messages ride the activation (full=all, reset=none, last_n/messages=trimmed, summary=native `LLMContextSummarizer`). **Tasks = Flows on the owning worker** (`pipecat.flows`, core since 1.5.0): the delegate `@tool` snapshots the shared context's `(messages, tools)`, constructs `FlowManager(llm=self.llm, context_aggregator=<pair over the shared context>, worker=self)` (`LLMWorker` subclasses `PipelineWorker`, so `worker=self` is the documented type), and `initialize`s the first node. The delegate resolves its own `@tool` call with `FunctionCallResultProperties(run_llm=False)` (added 2026-07-22, SPEC F5/B4) so the owner runs no follow-up completion and the flow's first node (`respond_immediately`) is the sole responder — otherwise the caller hears the task's opening line twice. Each node sends its task instructions as `role_message` (the current LLM system instruction) plus one developer `Begin this step.` task message; it never appends a second system message. The owner **stays the active worker throughout** — Flows rewrites its role, context, and tools per node; tasks never touch the bus, the bus stays handoff-only. A non-ending completion restores the owner's agent instructions, messages, and tools. No `pipecat-flows` dependency ever (deprecated standalone package, C3). **Inline single agent** (amended 2026-07-22, SPEC F3): the workers/bus scaffolding above is skipped when there is exactly one agent with no `agent_transfer`, no tasks, no tracing, no `variables`, and no telephony — the agent's LLM sits directly in the main pipeline (`transport.input → STT → user aggregator → LLM → TTS → transport.output → assistant aggregator`) and its tools are module-level direct functions registered on the `LLMContext`; there is no bus, `BusBridgeProcessor`, `LLMWorker`, or `activate_worker` (validated against pipecat-ai 1.5.0 + pipecat-slng). Any handoff, task, tracing, `variables`, or telephony reverts to the workers/bus topology.
- C10: **slng is a first-class provider**, not an OpenAI-compatible endpoint. `provider: slng` on `listen`/`speak` lowers to `SlngSTTService`/`SlngTTSService` from the standalone `pipecat-slng` package (verified against github.com/slng-ai/pipecat-slng 2026-07-15: `from pipecat_slng import SlngSTTService, SlngTTSService`; `api_key=SLNG_API_KEY`, `model="slng/<vendor>/<model>"`, TTS also `voice=`; routes by api_key + region params, **no `base_url`** — an `endpoint_env` on an slng binding is now a hard error, not silently ignored: the entry has no endpoint slot). There is no `SlngLLMService`; the `reason` role stays OpenAI-compatible. `pipecat-slng` is emitted as its own pyproject dependency (`Install.Package` on the catalogue entry), separate from the `pipecat-ai[extras]` pin.
- C9 (scope, driver v1; amended 2026-07-21, and 2026-08-10 for warm transfer): the following are **maturity-gated** on Pipecat — recorded in SCHEMA.md §9 + the capability table — because they need generated Python this driver does not emit yet: `models.fallback`, `thinking_audio`, `on_voicemail`, `mcp` tools, warm transfer (designed in [human-transfer.md](human-transfer.md) as the carrier-WebSocket two-socket bridge; the gate becomes the exact `(carrier-websocket, twilio)` route condition rather than a flat deny when §T7/§T8 land); and transfer/task context shaping beyond the safe-core defaults — `history` other than `full`, `context.variables` subset, `include_tool_calls: false`. The exact Twilio, Telnyx, and Plivo carrier-WebSocket adapters emit inbound, outbound, hangup, and out-of-band carrier-REST cold-transfer paths offline, but remain provisional; outbound cannot validate until the required voicemail lowering exists. Emitted outside those provisional routes: the three agency levels (single agent, `agent_transfer` including the `requires` guard, `tasks`/`task_groups`) with `context_scope` shared/isolated, and `local` tools. Each remaining gate lifts when its follow-up task lands; `mcp` stays gated.
- C11 (console mode; parity [compiler.md](compiler.md), verified against pipecat-ai 1.5.0 2026-07-19): the emitted `bot.py` runs two ways. Web (default): the dev runner (`pipecat.runner.run.main`) serves a WebRTC client. Console (`unmute dev --console` → `uv run --extra console bot.py console`): the dev runner has **no local transport** (its `-t` choices are daily/eval/vonage/webrtc/websocket/telephony), so the bot emits its own `console_main()` that builds a `LocalAudioTransport(LocalAudioTransportParams(audio_in_enabled=True, audio_out_enabled=True))` and reuses `run_bot`. `LocalAudioTransport` needs pyaudio (`pipecat-ai[local]`, portaudio system lib), kept out of the default deps as a `console` optional-dependency group and lazily imported inside `console_main` so a plain web `uv sync` never touches it. `LocalAudioTransport` fires no `on_client_connected`, so entry activation is centralised in `run_bot`'s `activate_entry` and triggered on `on_pipeline_started` in console (post-StartFrame by definition, so the B8/V14 gate is already satisfied) vs the client-connect path on web.

## §I surfaces
- I.emit: `GeneratePipecat(agent *ir.Agent, target ir.Target, bindings []ir.ForwardedBinding, sizing []ir.Sizing) (Artifact, error)` — registered as the `pipecat` case of `generate.Artifact`. The socket (`generate.Generate`) runs `Validate(caps)` before dispatch and forwards the validation report's bindings and sizing; the emitter never reads the generic capability table.
- I.templates: `templates/pipecat_v1/*.tmpl` (embedded) → `bot.py` (transport wiring + VAD + `WorkerRunner` + pipeline roles + agents + tasks/Flows + controls + tools + conversation, per C7), `pyproject.toml`, `Dockerfile`, `README.md`, deploy files, `compile-report.json`.
- I.state: generated typed state store for `variables` when no FlowManager is present (C4).

## §V invariants
- V1: task (T1) lowers to a `NodeConfig`: `role_message` = the task instructions, `task_messages` = one developer `Begin this step.` message, and `functions` = the task's tools plus a **uniquely named** `finish_<task_name>` `FlowsFunctionSchema` derived from the `result` schema (same-named functions across nodes collide in the LLM service's handler registry — first registration wins and the flow loops on the stale handler; proven by spike 2026-07-16). The finish handler records the typed result and returns `(result, next_node | None)`; handlers are **bound methods with per-delegate state on `self`** — never per-call closures — so a sticky registration always resolves to a callable reading current state. A standalone task is a one-node flow; per-task `model:` is gated (C5). A task converses: its node serves real user turns on the owner's LLM — never a background completion over the transcript (B7).
- V2: `task_group` lowers to a linear dynamic-flow chain on the owning worker (each finish handler returns the next step's node); `context_scope: shared` → `ContextStrategy.APPEND`, `isolated` → per-node `RESET`; `then: return` restores the owner's pre-flow system instruction and `(messages, tools)` snapshot, then injects only the merged typed results as a developer message (merge: results, N13) — no worker switch, the owner never stopped being active; `then: transfer` restores then `activate_worker(then_target, deactivate_self=True)`; `then: end` runs the `end_conversation` action.
- V3: `agent_transfer` lowers to worker activation (native); the generated code accounts for the native handoff passing full history + injecting a reason message.
- V4: `fallback` is generated (model switcher / `ParallelPipeline`), not a native adapter.
- V5 (amended 2026-08-10, SCHEMA N25; full design in [human-transfer.md](human-transfer.md)): `human_transfer` — the `cold:` block uses native Pipecat transfer on Daily SIP. Exact Twilio, Telnyx, and Plivo carrier-WebSocket routes instead emit provisional out-of-band carrier-REST transfer; the media-stream serializer itself still does not transfer the call. The `warm:` block is **generated**, designed for the exact `(carrier-websocket, twilio)` route as a two-socket software bridge: the supervisor is dialed as a second streamed call onto the same process through the app's existing outbound create-call path, briefed on their own private WebSocket, and then the two sockets are bridged in software; hold music is the caller transport's own `SoundfileMixer`, which is safe here precisely because each human has a separate output track (human-transfer.md C9 — on Daily's shared room the same mixer would leak the briefing or lose the music, B5 there). It is **not emitted yet**; [human-transfer.md](human-transfer.md) §T7/§T8 lift the gate after TELEPHONY.md Phase 3's credentialed smoke. Daily-SIP warm is a possible later lowering with its own second-participant design, not this one degraded. Two constraints are structural rather than incidental: the bot owns both media legs, so a warm transfer never pushes `EndFrame` and the bot stays as a silent audio bridge for the rest of the call (cold does end it); and the briefing interpolates the formatted transcript into the instruction rather than using `ContextStrategy.RESET_WITH_SUMMARY`, which C5 forbids. Support resolves against the exact target transport and carrier.
- V6 (amended 2026-08-08, SCHEMA N20): `greeting` — `speaks_first: user`, fixed `text`, and model-written opening are all generated (no gated failure here). An **absent** block is not a fourth mode: it lowers identically to `speaks_first: agent` without `text` (developer message + `run_llm=True` on `activate_worker`), matching the LiveKit driver's V8 so one source cannot open a call differently across the two shipped drivers (Vapi is managed and keeps its native default; Deepgram's driver does not exist yet, so its absent-block behaviour stays unproven per SCHEMA N6). It previously activated with `run_llm=False` and waited in silence. Consequence for V12/inline: a model-written opening needs an `activate_worker` to carry the developer message, so a single-agent package with no greeting block stays on the workers/bus shape rather than the inline shape. Guarded by `TestV32PipecatGreetingModes` (`no greeting block` case) and the cross-driver `TestGreetingDefaultIsModelWrittenOnEveryDriver`.
- V7: Pipecat documents `VoicemailDetector` for `on_voicemail`, but this driver does not emit that lowering yet; exact carrier-WebSocket outbound routes therefore stay gated. `placement: local` on listen/speak is allowed (code target).
- V8: the emitted project's `pyproject.toml`/lockfile pins the framework and plugins; the driver rejects a `version:` outside its template-compatible range (C3).
- V9: L4 smoke (build tag `smoke`, `make smoke`, opt-in, needs Python) proves the emitted `bot.py` is importable/valid; never in the default suite (CLAUDE.md testing).
- V10: safe_core → pipecat emits a valid project with no gated errors; the only warnings are the SCHEMA §7 warn-tagged notes safe_core exercises — turn semantic-endpointing plus the universal inactivity / max-duration range-check reminders (these warn on every target, not just Pipecat).
- V11 (amended 2026-07-15, catalogue pilot): provider → service facts live on **one catalogue entry per (framework, role, vendor)** (`internal/target/catalog_pipecat.go`): class, import, exactly one of a pipecat-ai extra or a standalone package, key env, constructor shape (flat kwargs vs `Class.Settings(...)`). Class/import/install travel together, so an emitted class structurally cannot drop its import (`TestCatalogInvariants` supersedes `TestServiceInfoCoversEveryMappedClass`). An unknown vendor **fails closed** with a matrix-quoting error unless the binding carries `endpoint_env` (the genuinely OpenAI-compatible custom-endpoint wildcard) — `TestPipecatUnknownProviderFailsClosed` keeps B1's failure mode covered.
- V12 (amended 2026-07-21 with B22): bot.py imports only what the spec exercises — no dead imports. `httpx` (webhook tools), `FunctionCallParams`/`tool` (any @tool method), the turn-start strategies (interruption min-words), `EndFrame`/`LLMMessagesAppendFrame` (their specific features), and `LLMUpdateSettingsFrame`/`LLMSettings` (a non-ending Flow delegate) are each conditional. `asyncio` is unconditional: every bot needs it for the activation gate (V14). Proven by the safe_core + tasks goldens (feature-rich), an end-only Flow generation check, and the single-agent slng scaffold (bare).
- V13 (added 2026-07-17): a `local` tool lowers to the **same bound `@tool` method shape as webhook** — only the body differs: it calls the user's handler function `<name>(...)` imported from the artifact's `tools/<name>.py` (an `import tools.<name>` line, emitted conditionally per V12), awaits the result if awaitable, and returns it through `params.result_callback`. The handler file rides `Artifact.Files` (source from `ir.Tool.HandlerSource`, empty scaffold when absent), mirroring the LiveKit driver's `LocalTools` collection + `import tools.<name>` template lines. L4 smoke instantiates a local-tool bot against real pipecat-ai (a `py_compile`-only check cannot see a wrong import, B5).
- V14 (added 2026-07-18, B8): entry-agent activation never races the main pipeline's StartFrame — `on_client_connected` awaits an `asyncio.Event` set by main's `on_pipeline_started` handler before `activate_worker`. Transport-independent: SmallWebRTC starts the pipeline at connect (the race B8 hit), Daily starts it at `runner.run()` (the event is already set and the await is free). Guarded by `TestV14_ActivationGatedOnPipelineStart` + the goldens; runtime-proven by a live headless WebRTC session (greeting audio received).
- V15 (added 2026-07-19, C11 console): the console additions are **purely additive** to the web emission — a bot with no `console` argv still delegates to `pipecat.runner.run.main()` (the `"console" in sys.argv` branch never shadows the runner's own flags), and a default `uv sync` never installs pyaudio (the `local` extra + the lazy import in `console_main`). Entry activation is centralised in one `activate_entry` helper called after the pipeline-start gate on both paths (never before). Guarded by the amended `TestV14_ActivationGatedOnPipelineStart` (asserts the client-connect path awaits the gate before the helper) + the regenerated goldens.
- V16 (added 2026-07-20, B9): tracing verification must drive the emitted worker/bus topology through an LLM request and assert that the `llm` span carries `gen_ai.request.model` and shares a trace ID with `conversation`; a synthetic root span proves exporter connectivity only. Guarded by `TestV16PipecatRequestTracingWiring` and the credential-free L4 `TestSmokeV16PipecatRequestTracing`; the credentialed probe additionally confirmed Langfuse ingests `llm` and `tts` as `GENERATION` observations.
- V17 (added 2026-07-20, B10): L4 tracing must drive audio through the STT and TTS service paths and assert completed `stt`, `llm`, and `tts` spans share the `conversation` trace. Speech services cannot be replaced with `Passthrough`.
- V18 (amended 2026-07-21, B15/B17; supersedes B11's broad custom processor): the driver exports Pipecat's native `conversation` → `turn` → `stt`/`llm`/`tts` service span tree unchanged and does not install a custom `SpanProcessor`. A narrow, idempotent patch around Pipecat's STT/TTS/LLM attribute helpers mirrors only speech payloads, speech metrics, and the configured LLM system instruction into Langfuse's documented OTEL attributes; it does not replace the native exporter, span lifecycle, hierarchy, provider/model/settings attributes, or decorators. The conversation root carries `langfuse.trace.name: <entry-agent>-<target-name>`. Guarded by `TestV21PipecatUsesNativeTracing`, `TestV23PipecatSpeechObservationsAreRich`, `TestV25PipecatTracesConfiguredSystemInstruction`, and `TestSmokeV17PipecatSpeechTracing`.
- V19 (added 2026-07-20): Langfuse tracing is emitted iff the core IR carries `tracing.provider: langfuse`. Without it, the project contains no Unmute tracing setup, Langfuse/OpenTelemetry-only imports or dependencies, Langfuse environment keys, tracing hooks, or README tracing section. With it, the driver preserves V16–V18's native trace tree and naming, lists `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, and `LANGFUSE_BASE_URL` in `.env.example`, and fails agent startup when any value is missing or empty, including all three. Presence and absence are both locked by L3 goldens; L4 tracing smokes use the configured path.
- V20 (added 2026-07-20, B12): the L4 tracing probe derives the entry worker class and service-builder names from the emitted configured example; changing that example's agent name cannot break the probe before tracing runs. Guarded by `TestSmokeV17PipecatSpeechTracing`.
- V21 (added 2026-07-21, B13): configured projects install Pipecat's official `tracing` extra plus the HTTP OTLP exporter, call `setup_tracing`, and enable tracing on the conversation worker. The L4 probe must call the generated Langfuse setup against a local OTLP receiver, drive native STT, LLM, and TTS spans, assert one shared trace named `<entry-agent>-pipecat`, and observe the authenticated OTLP request. A probe that replaces the generated setup with its own tracer provider cannot pass. Guarded by `TestV16PipecatRequestTracingWiring`, `TestV21PipecatUsesNativeTracing`, and `TestSmokeV17PipecatSpeechTracing`.
- V22 (added 2026-07-21, B14): every generated Pipecat `@tool` execution and task-flow function emits one completed `tool:<function-name>` child span under the active turn. The span records `tool.function_name`, the Pipecat `tool.call_id` when available, and JSON Langfuse observation input/output. Tool errors retain OpenTelemetry's error status. This hook is emitted only when both tools and Langfuse tracing are configured. Guarded by `TestV22PipecatToolCallsAreTraced` and the real `lookup_customer` call in `TestSmokeV17PipecatSpeechTracing`.
- V23 (added 2026-07-21, B15): every traced STT span exposes JSON Langfuse observation input `"audio"` and output equal to the transcript; every traced TTS span exposes input equal to synthesized text and output `"audio"`. STT transcripts and TTS text also populate trace input/output. Pipecat's `metrics.ttfb` maps to filterable `ttfb_seconds` metadata plus Langfuse completion-start time, and TTS `metrics.character_count` maps to filterable metadata plus `characters` usage details. Native provider, model, voice, language, finality, settings, raw metrics, and span duration remain present. The generated worker enables both performance and usage metrics. Guarded by `TestV23PipecatSpeechObservationsAreRich` and `TestSmokeV17PipecatSpeechTracing`.
- V24 (added 2026-07-21, B16): every generated Pipecat project declares `ty` as a development dependency and `examples/simple-prompt` passes `ty check .`. Runtime patch markers and method replacement use dynamic-safe `setattr`; optional tracing state is narrowed before access; agent collections accept subclasses covariantly; Pipecat speech language arguments use its `Language` enum; and SDK-only flush methods are called only on an SDK `TracerProvider`. Guarded by `TestV24PipecatStaticCheckSurface` and `TestSmokeV24PipecatSimplePromptStaticCheck`.
- V25 (amended 2026-07-21, B17/B18): every traced Pipecat LLM observation includes its configured `LLMSettings.system_instruction` as the leading `system` message in both Pipecat's canonical `input` and Langfuse's `langfuse.observation.input`, with identical JSON payloads, while retaining Pipecat's native `gen_ai.system_instructions` attribute. Guarded by `TestV25PipecatTracesConfiguredSystemInstruction` and `TestSmokeV17PipecatSpeechTracing`.
- V26 (added 2026-07-21, B19): task inference has one system instruction: the current task's instructions via `NodeConfig.role_message`. The required `task_messages` contains only developer `Begin this step.`. `APPEND`/`RESET` shape context messages, not the role. Because `role_message` persists in the owning LLM, every non-ending delegate completion restores the agent instructions with `LLMUpdateSettingsFrame` before the worker is reused. Guarded by `TestPipecatV1TasksGolden` and `TestSmokePipecatV1TaskGroupsInstantiate`.
- V27 (added 2026-07-21, B20): Pipecat generation rejects task instructions that are empty after trimming whitespace. No Flow node may emit an empty `role_message`, because Pipecat treats it as absent and would retain the owning agent's system instruction. Guarded by `TestPipecatRejectsBlankTaskInstructions`.
- V28 (added 2026-07-21, B21): every non-ending Flow completion drains the queued owner-role update through the owning worker before the function result can trigger another inference or `then: transfer` can deactivate it. L4 starts the generated workers against Pipecat 1.5.0 and observes task instructions followed by owner instructions; the generation test covers return, transfer, and end branches. Guarded by `TestPipecatV1TasksGolden` and `TestSmokePipecatV1TaskGroupsInstantiate`.
- V29 (added 2026-07-20, SCHEMA N18): the emitted `pcc-deploy.toml` carries `region = "<value>"` exactly when the target instance declares `deployment_region`, and no region line otherwise — the provider default applies. The value is forwarded as declared, never validated (free provider vocabulary; `pipecat cloud deploy` is the real validator). Guarded by the pcc-deploy goldens covering both shapes.
