# SPEC — Pipecat driver (generate.Artifact case)

Consumes the core: [compiler.md](compiler.md) (`ir.Agent`, `ir.Target`, the capability table, the `Artifact` socket). Schema truth: [SCHEMA.md](../../SCHEMA.md). Pipecat facts: SCHEMA.md conditions ¹ + ORCHESTRATOR_SHARED_CONFIGURATION.md footnote ¹. Where they disagree, SCHEMA.md wins.

Type: **code target**. Emits a Pipecat Python project on disk (`Artifact.Files`). A generator already exists (`internal/generate/pipecat.go`, `text/template` from `templates/pipecat/*.tmpl`) but consumes the OLD schema — this rewrites it against the v1 IR.

## §G goal
Lower a validated `ir.Agent` + a `pipecat` target instance into a runnable Pipecat project: `bot.py` (pipeline, agents, tasks/Flows, controls, tools, conversation), dependency + deploy files, and a compile report. Cascaded pipeline only. Flows lives in `pipecat-ai` core (`pipecat.flows`) since 1.5.0.

## §C constraints
- C1: Go emits Python via `text/template` (ADR-0002). Python is generated, never maintained here. Embedded template FS.
- C2: all four roles are **open** (listen, turn, speak, reason): every used profile needs a binding (core V9). Custom OpenAI-compatible STT/TTS is a config forward — `OpenAISTTService`/`OpenAITTSService` take a documented `base_url` override; subclass only for non-OpenAI protocols.
- C3: framework pin. `version:` checked against the driver's template-compatible range (codegen check, not model validation). Flows no longer needs a `pins:` entry (core since 1.5.0); **never pin the deprecated standalone `pipecat-ai-flows`** (rule 11).
- C4: `flow_manager.state` exists only under a FlowManager; a T0/T2-only source has no Flows, so the driver generates a typed state store for `variables`.
- C5: per-task `model:` is **gated on Pipecat** (capability table deny; SCHEMA 4.6). The paper mechanism (`LLMSwitcher` — `FlowManager` accepts `llm: LLMService | LLMSwitcher`) fails at runtime on 1.5.0: `LLMWorker(llm=switcher)` crashes in `_register_tools` (the switcher lacks the private `_register_direct_function`), and a switcher placed inside the worker's pipeline stalls every flow frame (spike-verified 2026-07-16, B7). The gate lifts when a working switch-inside-worker lowering is proven. A standalone task is a one-node flow — same code path as a group, no separate `@job` mechanism.
- C6: never use Pipecat's deprecated `ContextStrategy.RESET_WITH_SUMMARY` (removed in 2.0.0); its deprecation notice points to Pipecat's **native** summarizer (`LLMContextSummarizer` / `LLMAutoContextSummarizationConfig`), so a `history: summary` lowering configures that native summarizer instead of hand-building one.
- C7: a runnable cascaded bot needs scaffolding beyond the role bindings — transport in/out wiring (`transport.input()` → STT → context aggregator → LLM → TTS → `transport.output()`), a VAD analyzer (`SileroVADAnalyzer`), and a runner. The `turn` role lowers to VAD + smart-turn analyzers, not an API-keyed service, so its binding is advisory (SCHEMA §4.2) — the template supplies the analyzer. (Runner spelling corrected against current docs 2026-07-15: Pipecat's current worker API is `WorkerRunner` + `PipelineWorker` from `pipecat.workers`/`pipecat.pipeline.worker`, not the older `PipelineRunner`+`PipelineTask`; the workers subsystem is also where `@job`/`activate_worker` live, so one API covers the pipeline, handoff, and delegate-and-return.)
- C8: the driver lowers the agency model through **two mechanisms, each on Pipecat's documented recommended path** (rewritten 2026-07-16, B7; every API claim below verified end-to-end against real pipecat-ai 1.5.0 — scripted-SSE spike, not docs alone). **Handoff = workers/bus**: each agent is an `LLMWorker` (its own LLM = `reason` binding, system instruction = agent instructions); `agent_transfer` is a `@tool` calling `activate_worker(target, args=LLMWorkerActivationArgs(messages=[reason]), deactivate_self=True)` (V3 native handoff + reason message); webhook tools are `@tool` methods; context management chooses what messages ride the activation (full=all, reset=none, last_n/messages=trimmed, summary=native `LLMContextSummarizer`). **Tasks = Flows on the owning worker** (`pipecat.flows`, core since 1.5.0): the delegate `@tool` snapshots the shared context's `(messages, tools)`, constructs `FlowManager(llm=self.llm, context_aggregator=<pair over the shared context>, worker=self)` (`LLMWorker` subclasses `PipelineWorker`, so `worker=self` is the documented type), and `initialize`s the first node. The owner **stays the active worker throughout** — Flows rewrites its context+tools per node; tasks never touch the bus, the bus stays handoff-only. No `pipecat-flows` dependency ever (deprecated standalone package, C3).
- C10: **slng is a first-class provider**, not an OpenAI-compatible endpoint. `provider: slng` on `listen`/`speak` lowers to `SlngSTTService`/`SlngTTSService` from the standalone `pipecat-slng` package (verified against github.com/slng-ai/pipecat-slng 2026-07-15: `from pipecat_slng import SlngSTTService, SlngTTSService`; `api_key=SLNG_API_KEY`, `model="slng/<vendor>/<model>"`, TTS also `voice=`; routes by api_key + region params, **no `base_url`** — an `endpoint_env` on an slng binding is now a hard error, not silently ignored: the entry has no endpoint slot). There is no `SlngLLMService`; the `reason` role stays OpenAI-compatible. `pipecat-slng` is emitted as its own pyproject dependency (`Install.Package` on the catalogue entry), separate from the `pipecat-ai[extras]` pin.
- C9 (scope, driver v1; amended 2026-07-17 — `local` tools lifted, T14): the following are **maturity-gated** on Pipecat — recorded in SCHEMA.md §9 + the capability table, mirroring warm transfer — because they need generated Python this driver does not emit yet: `models.fallback`, `thinking_audio`, `outbound`+`on_voicemail`, `mcp` tools, warm transfer; and transfer/task context shaping beyond the safe-core defaults — `history` other than `full`, `context.variables` subset, `include_tool_calls: false` (the workers `activate_worker` handoff carries the running context; fine-grained shaping is not verified/emitted yet). Emitted: the three agency levels (single agent, `agent_transfer` incl. the `requires` guard, `tasks`/`task_groups`) with `context_scope` shared/isolated, and `local` tools (T14 — Pipecat function calling supports them natively; verified against docs.pipecat.ai function-calling + the already-runtime-proven `@tool` webhook shape 2026-07-17). Each remaining gate lifts when its follow-up §T task lands; `mcp` stays gated — do not lift it with `local`.

## §I surfaces
- I.emit: `GeneratePipecat(agent *ir.Agent, target ir.Target) (Artifact, error)` — registered as the `pipecat` case of `generate.Artifact`. The socket (`generate.Generate`) already runs `Validate(caps)` before dispatch (V17), so the case drops `caps` when calling the emitter: a provider-specific emitter reads only the resolved `agent`+`target`, never the generic capability table. (Resolves the socket/emit signature drift: the case drops `caps`, I.emit stays two-arg.)
- I.templates: `templates/pipecat/*.tmpl` (embedded) → `bot.py` (transport wiring + VAD + `PipelineRunner` + pipeline roles + agents + tasks/Flows + controls + tools + conversation, per C7), `pyproject.toml`, `Dockerfile`, `README.md`, deploy files, `compile-report.json`. Rewritten for v1 IR.
- I.state: generated typed state store for `variables` when no FlowManager is present (C4).

## §V invariants
- V1: task (T1) lowers to a `NodeConfig`: `task_messages` = the task instructions, `functions` = the task's tools plus a **uniquely named** `finish_<task_name>` `FlowsFunctionSchema` derived from the `result` schema (same-named functions across nodes collide in the LLM service's handler registry — first registration wins and the flow loops on the stale handler; proven by spike 2026-07-16). The finish handler records the typed result and returns `(result, next_node | None)`; handlers are **bound methods with per-delegate state on `self`** — never per-call closures — so a sticky registration always resolves to a callable reading current state. A standalone task is a one-node flow; per-task `model:` is gated (C5). A task converses: its node serves real user turns on the owner's LLM — never a background completion over the transcript (B7).
- V2: `task_group` lowers to a linear dynamic-flow chain on the owning worker (each finish handler returns the next step's node); `context_scope: shared` → `ContextStrategy.APPEND`, `isolated` → per-node `RESET`; `then: return` restores the owner's pre-flow `(messages, tools)` snapshot via `LLMContext.set_messages`/`set_tools` and injects only the merged typed results as a developer message (merge: results, N13) — no worker switch, the owner never stopped being active; `then: transfer` restores then `activate_worker(then_target, deactivate_self=True)`; `then: end` runs the `end_conversation` action.
- V3: `agent_transfer` lowers to worker activation (native); the generated code accounts for the native handoff passing full history + injecting a reason message.
- V4: `fallback` is generated (model switcher / `ParallelPipeline`), not a native adapter.
- V5: `human_transfer` — `mode: cold` compiles **only on a Daily SIP transport**; `mode: warm` is gated as **not-emitted-yet** (Pipecat ships warm transfer via a custom `TransferCoordinator` + hold-music mixer on Daily PSTN, official `warm_transfer.py`; this driver does not emit that plumbing yet — a maturity gate, not a platform limit); WebSocket serializers (Twilio/Telnyx/Plivo) cannot transfer **via the media-stream serializer** (out-of-band carrier-REST transfer exists but is not emitted) → gated error there. Resolved against the target's `transport`/`carrier`, not the brand. (review-corrected 2026-07-15.)
- V6: `greeting` — `speaks_first: user`, fixed `text`, and model-written opening are all generated (no gated failure here).
- V7: `on_voicemail` (`hangup`/`leave_message`) lowers to `VoicemailDetector`; `placement: local` on listen/speak is allowed (code target).
- V8: the emitted project's `pyproject.toml`/lockfile pins the framework and plugins; the driver rejects a `version:` outside its template-compatible range (C3).
- V9: L4 smoke (build tag `smoke`, `make smoke`, opt-in, needs Python) proves the emitted `bot.py` is importable/valid; never in the default suite (CLAUDE.md testing).
- V10: safe_core → pipecat emits a valid project with no gated errors; the only warnings are the SCHEMA §7 warn-tagged notes safe_core exercises — turn semantic-endpointing plus the universal inactivity / max-duration range-check reminders (these warn on every target, not just Pipecat).
- V11 (amended 2026-07-15, catalogue pilot): provider → service facts live on **one catalogue entry per (framework, role, vendor)** (`internal/target/catalog_pipecat.go`): class, import, exactly one of a pipecat-ai extra or a standalone package, key env, constructor shape (flat kwargs vs `Class.Settings(...)`). Class/import/install travel together, so an emitted class structurally cannot drop its import (`TestCatalogInvariants` supersedes `TestServiceInfoCoversEveryMappedClass`). An unknown vendor **fails closed** with a matrix-quoting error unless the binding carries `endpoint_env` (the genuinely OpenAI-compatible custom-endpoint wildcard) — `TestPipecatUnknownProviderFailsClosed` keeps B1's failure mode covered.
- V12: bot.py imports only what the spec exercises — no dead imports. `httpx` (webhook tools), `FunctionCallParams`/`tool` (any @tool method), the turn-start strategies (interruption min-words), `asyncio`/`EndFrame`/`LLMMessagesAppendFrame` (their specific features) are each conditional. Proven by the safe_core + tasks goldens (feature-rich) vs the single-agent slng scaffold (bare).
- V13 (added 2026-07-17): a `local` tool lowers to the **same bound `@tool` method shape as webhook** — only the body differs: it calls the user's handler function `<name>(...)` imported from the artifact's `tools/<name>.py` (an `import tools.<name>` line, emitted conditionally per V12), awaits the result if awaitable, and returns it through `params.result_callback`. The handler file rides `Artifact.Files` (source from `ir.Tool.HandlerSource`, empty scaffold when absent), mirroring the LiveKit driver's `LocalTools` collection + `import tools.<name>` template lines. L4 smoke instantiates a local-tool bot against real pipecat-ai (a `py_compile`-only check cannot see a wrong import, B5).
