This is the `sip` transport with the `twilio` carrier. A call on it takes four
hops:

```text
caller -> Twilio number -> Elastic SIP Trunk -> LiveKit SIP
       -> inbound trunk -> dispatch rule -> your agent
```

Each hop breaks on its own, and three of the four live outside your package.
Unmute writes the code for the route. It never signs in to Twilio, and it never
creates a LiveKit record, so steps 3 and 4 are yours to run every time.

| Step | What it is | Where it lives | If it is missing |
|---|---|---|---|
| 1 | a phone channel and a connection | your package | a browser-only agent, with nothing to route a call to |
| 2 | the deployed agent | LiveKit Cloud | the rule names an agent that never joins, so the phone rings forever |
| 3 | the origination URL on the trunk | Twilio | the call stops at Twilio, because nothing forwards it |
| 4 | the inbound trunk and the dispatch rule | your LiveKit project | LiveKit refuses the call, or opens a room with nobody in it |

## Before you start

You need three things on your machine: the
[LiveKit CLI](https://docs.livekit.io/reference/developer-tools/livekit-cli/)
(`lk`), the [Twilio CLI](https://www.twilio.com/docs/twilio-cli/getting-started/install)
(`twilio`), and `jq`. Sign in to both once, with `lk cloud auth` and
`twilio login`.

Then look up three values. Every command below uses one of them:

```sh
LK_PROJECT="<project name>"   # lk project list
NUMBER="+15551234567"         # E.164, and the same value as SIP_FROM_NUMBER
TRUNK_SID="TK..."             # twilio api:trunking:v1:trunks:list
```

You never type your agent's name. The generated `sip-dispatch-rule.json`
carries it.

<Warning>
  Pass `--project "$LK_PROJECT"` on every `lk` command. `lk` has a default
  project, marked with `*` in `lk project list`, and it is often not the project
  your agent deploys to. A command without `--project` writes to that default,
  and reports success. That is the most common way to end up with working
  records in the wrong account.
</Warning>

## Two things are called a trunk

This route needs one trunk in Twilio and one in LiveKit. They do different jobs,
and having one is not having the other:

| Trunk | Lives in | Created by | Does what |
|---|---|---|---|
| Elastic SIP Trunk | your Twilio account | you, in the Twilio console | carries the call between Twilio and LiveKit |
| inbound trunk | your LiveKit project | you, with `lk sip inbound create` | tells LiveKit your number belongs to this project |

LiveKit refuses a call whose number no inbound trunk claims, however right the
Twilio side is. So finishing the Twilio side is only half the job.

The Twilio trunk itself has two sides, on two tabs that sound alike and do
opposite things:

| Tab | Direction | What it is for |
|---|---|---|
| **Termination** | out of Twilio | your agent dialing out: outbound calls and warm transfers |
| **Origination** | into LiveKit | incoming calls reaching LiveKit SIP |

An inbound-only agent still fills all four SIP values, because the route wants
them whichever direction it uses. A cold transfer needs the trunk too, even
though the caller only ever rang in.

## 1. Write the route into the package

Three files. The channel says the agent answers the phone, the connection says
how the call arrives, and the target picks that connection.

```yaml agent.yaml
channels:
  web:
    kind: realtime_audio
  phone:
    kind: telephony
    inbound: true
    outbound: false

capacity:
  peak_sessions: 5
  max_sessions: 10
  peak_starts_per_second: 1
  avg_session_duration: 5m

secrets:
  - SIP_TRUNK_HOSTNAME
  - SIP_AUTH_USERNAME
  - SIP_AUTH_PASSWORD
  - SIP_FROM_NUMBER
```

A telephony channel makes `capacity.peak_starts_per_second` required, so add it
in the same edit. [Phone calls](/telephony/overview#every-key-capacity-takes)
has the rest of the `capacity:` keys.

```yaml connections/twilio_sip.yaml
transport: sip
carrier: twilio
environment:
  sip_address: SIP_TRUNK_HOSTNAME
  sip_username: SIP_AUTH_USERNAME
  sip_password: SIP_AUTH_PASSWORD
  from_number: SIP_FROM_NUMBER
```

```yaml targets.yaml
targets:
  livekit:
    provider: livekit
    version: "1.8.1"
    connection: twilio_sip
```

Then compile:

```sh
unmute validate my-agent --target livekit
unmute compile my-agent --target livekit
```

Compiling writes `sip-inbound-trunk.json` and `sip-dispatch-rule.json` into
`build/livekit/`. Those two files are what step 4 sends to LiveKit, and they are
the only thing under `build/` you fill in by hand. For everything else, change
the package and compile again.

### Every key this connection takes

Two scalars and four names. Nothing else belongs in the file.

<ParamField path="transport" type="sip" required>
  The mechanism. `sip` is this route. The other three, `connector`,
  `cloud-websocket` and `daily-sip`, are other routes with other keys.
</ParamField>

<ParamField path="carrier" type="twilio | telnyx | plivo" required>
  The carrier account behind the trunk. This page is `twilio`, and the other
  two take the same four names, because they are standard SIP names.
</ParamField>

<ParamField path="environment.sip_address" type="environment variable name" required>
  Holds the trunk's termination domain, the one ending in `pstn.twilio.com`.
</ParamField>

<ParamField path="environment.sip_username" type="environment variable name" required>
  Holds the username from the trunk's credential list.
</ParamField>

<ParamField path="environment.sip_password" type="environment variable name" required>
  Holds that credential's password.
</ParamField>

<ParamField path="environment.from_number" type="environment variable name" required>
  Holds the attached number in E.164 form. It has to be the number you attach to
  the trunk in step 3.
</ParamField>

Every value here is a **name**, never a value, and each name is UPPER_SNAKE. An
`account_sid` or an `auth_token` is refused: those belong to the routes that call
Twilio's REST API, and this one signs in to a trunk instead.

Put the four values in `.env`.
[Get your Twilio details](/telephony/twilio#the-four-sip-values)
says which console field fills which name.

## 2. Deploy the agent

```sh
cd my-agent/build/livekit
lk --project "$LK_PROJECT" agent create --region "<region>" --secrets-file .env
lk --project "$LK_PROJECT" agent list
```

[LiveKit Cloud](/deploy/livekit-cloud) walks the deploy in full. Use `create`
once, then `lk --project "$LK_PROJECT" agent deploy .` for every later change.
`deploy` updates the agent named in `livekit.toml`, and `Version` and
`Deployed At` in `agent list` both change when it worked.

The agent comes before the LiveKit records because the
<Tooltip tip="A LiveKit setting that sends calls on a trunk to your agent, one room per caller.">dispatch rule</Tooltip> names it. A rule that names an agent nobody deployed
opens a room and leaves the caller listening to ringing.

Pass `--secrets-file .env` whenever the list of names changes. The four `SIP_*`
names are new to a package that had no phone route, and the generated agent
checks its whole declared list the moment a SIP caller arrives. A missing name
fails the call, not the build.

<Tip>
  The image builds on LiveKit's side, over several minutes, with little output.
  Ctrl-C aborts it with `context canceled` and leaves the previous version
  running.
</Tip>

## 3. Set up the trunk in Twilio

Twilio owns the number and answers the phone network. The origination URL is the
forwarding address that hands the call to LiveKit. Unmute creates none of this.
[Twilio's own guide](https://www.twilio.com/en-us/blog/elastic-sip-trunking-step-by-step-setup)
shows the same console screens.

<Steps>
  <Step title="Open or create the trunk">
    In the Twilio Console, go to **Elastic SIP Trunking**, **Manage**,
    **Trunks**. Open the trunk you want to use, or create one. Do not change a
    shared trunk that is already serving another route.

    A new trunk starts with every feature off, so nothing below is inherited
    from a trunk you set up before.
  </Step>

  <Step title="Set termination and authentication">
    On the **Termination** tab, choose a Termination SIP URI ending in
    `pstn.twilio.com`. Under **Authentication**, select or create a Credential
    List with a username and password. Save the trunk.

    This is the dial-out side. Its domain and credential are three of your four
    SIP values.
  </Step>

  <Step title="Point origination at LiveKit">
    First write down your project's SIP address. It comes from the project ID:

    ```sh
    lk project list
    ```

    Take the ID of the project your agent deploys to. It starts with `p_`. Drop
    the `p_`, put the rest in front of `.sip.livekit.cloud`, and add
    `;transport=tcp`:

    | Project ID | SIP address |
    |---|---|
    | `p_abc123def` | `sip:abc123def.sip.livekit.cloud;transport=tcp` |

    Then add that address to the trunk. In the console: the **Origination** tab,
    **Add new Origination URI**, paste it, leave priority and weight at 1, tick
    **Enabled**, save. From the CLI:

    ```sh
    twilio api:trunking:v1:trunks:origination-urls:create \
      --trunk-sid "$TRUNK_SID" \
      --friendly-name "LiveKit SIP" \
      --sip-url "sip:abc123def.sip.livekit.cloud;transport=tcp" \
      --weight 1 --priority 1 --enabled
    ```

    Do not build this address from `LIVEKIT_URL`. The project URL subdomain and
    the SIP subdomain are different strings, and a wrong host here gives you a
    number that rings and never connects.

    *Self-hosted LiveKit:* there is no project SIP address. Point origination at
    the public SIP signalling address of the LiveKit SIP service you deployed.
  </Step>

  <Step title="Attach the number to the trunk">
    This is the step people miss, because you do it from inside the trunk and
    not from the number.

    Open the trunk, go to its **Numbers** tab, and click **Add a Number**. Some
    accounts label the button **Add an Existing Number**. Tick your number in
    the list and save. The **Numbers** tab should then show it.

    Check it from the CLI:

    ```sh
    twilio api:trunking:v1:trunks:phone-numbers:list --trunk-sid "$TRUNK_SID"
    ```

    Write down the number's old Voice configuration first. A number attached to
    a trunk ignores its own Voice configuration, silently, so it cannot also
    serve a webhook or a TwiML Bin.
  </Step>

  <Step title="Allow calls to transfer">
    Skip this one if your agent never hands a caller to a person.

    In the trunk's **General settings**, turn on **Call Transfer (SIP REFER)**
    and tick **Enable PSTN Transfer**. Then set **Caller ID for Transfer
    Target**. Read [which caller ID to
    present](/telephony/twilio#caller-id-for-a-transfer-target) before you
    choose: the wrong value fails every transfer with no useful error. Save the
    trunk.
  </Step>
</Steps>

<Tip>
  If your number and trunk live in a Twilio Region such as Ireland, the console
  and the API show you that region only. [Twilio
  Regions](/telephony/twilio#if-your-trunk-is-in-a-twilio-region) says what
  changes.
</Tip>

## 4. Create the two LiveKit records

Twilio now forwards the call, and LiveKit rejects it, because nothing in your
project claims that number yet. Two records fix that:

| Record | What it does |
|---|---|
| inbound trunk | claims your number for this LiveKit project |
| dispatch rule | sends that trunk's calls to your agent, one room per caller |

Both are created from the JSON that compiling wrote into `build/livekit/`. Each
file holds one placeholder you fill in by hand.

**The inbound trunk.** Open `sip-inbound-trunk.json` and put your number in
place of `${SIP_FROM_NUMBER}`, so the line reads:

```json
"numbers": ["+15551234567"]
```

Then create it:

```sh
cd my-agent/build/livekit
lk --project "$LK_PROJECT" sip inbound create sip-inbound-trunk.json
```

It prints the record it made. Copy the ID, the one starting with `ST_`.

**The dispatch rule.** Open `sip-dispatch-rule.json` and put that ID in place of
`${UNMUTE_SIP_TRUNK_ID}`. The rest of the file, your agent's name and the room
prefix, is already filled in. Then:

```sh
lk --project "$LK_PROJECT" sip dispatch create sip-dispatch-rule.json
```

If the first command printed no `ST_` ID, fix that before running the second. A
rule with the placeholder still in it matches every trunk in the project.

Then check both:

```sh
lk --project "$LK_PROJECT" sip inbound list      # Authentication column empty
lk --project "$LK_PROJECT" sip dispatch list     # Agents column names your agent
```

Compiling again rewrites both files, so keep a copy of the filled-in versions if
you want them.

### Use the JSON, not the lk flags

Two flag sets look like they do the same job and do not.

- **`sip dispatch create --individual`** has no flag for the agent, so it makes
  a rule with an empty Agents column. The room opens, nothing joins it, and the
  caller hears ringing until LiveKit gives up.
- **`sip inbound create --auth-user/--auth-pass`** makes a trunk that asks
  incoming calls for a SIP password. Twilio origination sends none, because it
  identifies itself by source IP, so LiveKit rejects every call. The generated
  JSON sets no authentication, which is what this route wants.

To limit who can call in, put Twilio's signalling IP ranges in
`allowedAddresses` on the trunk. Never use digest authentication here, because
Twilio will not answer it.

Both records belong to one project and one number. A new project needs its own
pair, and so does a new number.

## Call the number

Call it from a phone. The agent answers and greets you. Speak, and it replies.

That call is the only proof of the phone path. [`unmute dev`](/dev/overview) is a
browser session, and it stops exactly where the phone leg starts. There is no
local SIP rehearsal. Watch the call arrive with:

```sh
lk --project "$LK_PROJECT" agent logs
```

## Take it down

To stop calls reaching the agent and keep everything else, remove the origination
URL. The number and both trunks stay as they are:

```sh
twilio api:trunking:v1:trunks:origination-urls:list --trunk-sid "$TRUNK_SID"
twilio api:trunking:v1:trunks:origination-urls:remove \
  --trunk-sid "$TRUNK_SID" --sid "<OU...>"
```

To remove the LiveKit records, delete the rule first, because it points at the
trunk:

```sh
lk --project "$LK_PROJECT" sip dispatch list     # find the SDR_ id
lk --project "$LK_PROJECT" sip dispatch delete "<SDR_...>"
lk --project "$LK_PROJECT" sip inbound delete "<ST_...>"
```

To take telephony out of the package: drop the `phone` channel from `agent.yaml`,
drop `connection:` from `targets.yaml`, delete `connections/twilio_sip.yaml`, and
compile again. Remove the four `SIP_*` names from `secrets:` too, or the agent
will demand values nothing uses.

## What to redo, and when

| What changed | Steps to redo |
|---|---|
| prompt, tools or model | 1 and 2 |
| a new phone number | `SIP_FROM_NUMBER` in `.env`, then 1, 2, 3 and 4 |
| a new LiveKit project | all four: the SIP address, the trunk and the rule are all per project |
| the agent's name | 1, 2, then the dispatch rule in step 4, which names the agent |

An ordinary redeploy leaves the trunk, the rule and the number alone. Renaming
the agent does not. The dispatch rule holds the agent name as plain text, and no
deploy updates it. The number then rings while the agent reports healthy,
because nothing ever dispatched it. [Renaming the agent breaks that
rule](/deploy/livekit-cloud#renaming-the-agent-breaks-that-rule) walks the swap.

## If the call does not arrive

The symptom is what you see. The cause is rarely next to it.

| What you see | What it is | What to do |
|---|---|---|
| Twilio call log: `failed`, 0 seconds, 0 cost, direction `trunking-originating` | the inbound trunk asks for a SIP password, and Twilio origination sends none | delete the trunk and create it again from the generated JSON |
| the records are in an account nobody expected | an `lk` command ran without `--project` | delete the strays, set `LK_PROJECT`, create them again |
| the phone rings forever and nobody answers | the dispatch rule's Agents column is empty, or the agent it names is not deployed | recreate the rule from the JSON, then check `lk agent list` |
| nothing in the Twilio call log at all | no origination URL on the trunk, or the number is not attached to it | step 3, especially the **Numbers** tab |
| everything looks right and the call still fails | the number is on a SIP trunk, so it ignores its own voice configuration | one route per number; use a second number for the other route |
| the deploy worked and the agent behaves like the old one | deployed from a branch without the SIP changes | deploy from the branch that has them |

Two more worth knowing:

- **`.env` is not in git.** It follows neither a branch nor a worktree, so each
  checkout needs its own copy. Everything in it is uploaded by `--secrets-file
  .env`, so keep it to the names you declared.
- **A trunk's name changes nothing.** A trunk you inherited from an old demo
  works fine once it claims the right number and asks for no inbound password.
  Renaming it is cosmetic. The authentication setting is not.

<AccordionGroup>
  <Accordion title="the call rings and rings, and nobody ever answers">
    A LiveKit SIP call is answered when something in the room publishes audio.
    So a job that dies before the agent speaks leaves the caller listening to
    ringing until LiveKit gives up.

    The usual cause is a secret that is declared but not deployed. The generated
    agent checks its phone environment the moment a SIP caller arrives, so a
    missing name fails the job there, on a real call only. Compare the two
    lists:

    ```sh
    lk --project "$LK_PROJECT" agent secrets
    cat build/livekit/.env.example
    ```

    Every name in the second belongs in the first. Add what is missing to
    `.env`, then run `lk --project "$LK_PROJECT" agent update-secrets
    --secrets-file .env`, which restarts the agent.
  </Accordion>
  <Accordion title="a transfer fails at once with 486 Busy Here">
    The trunk is presenting a caller ID the other carrier rejects. [Caller ID
    for a transfer target](/telephony/twilio#caller-id-for-a-transfer-target)
    has the two settings and how to tell them apart in Twilio's call log.
  </Accordion>
</AccordionGroup>

## The other LiveKit route: the connector

LiveKit also reaches Twilio without a trunk. On the `connector` transport, a
generated bridge speaks Twilio Media Streams over a WebSocket and joins the call
into a LiveKit room, where the same agent answers. The number's voice webhook
points at `POST /telephony/inbound` on the bridge, so the connection file names
the account trio instead of the four SIP values:

```yaml connections/twilio_connector.yaml
transport: connector
carrier: twilio
environment:
  account_sid: TWILIO_ACCOUNT_SID
  auth_token: TWILIO_AUTH_TOKEN
  from_number: TWILIO_PHONE_NUMBER
```

### Every key the connector connection takes

<ParamField path="transport" type="connector" required>
  The mechanism. It is what puts the bridge in the emitted project.
</ParamField>

<ParamField path="carrier" type="twilio" required>
  The only carrier this route has.
</ParamField>

<ParamField path="environment.account_sid" type="environment variable name" required>
  Holds the account SID, the one starting `AC`.
</ParamField>

<ParamField path="environment.auth_token" type="environment variable name" required>
  Holds the account's auth token.
</ParamField>

<ParamField path="environment.from_number" type="environment variable name" required>
  Holds your number in E.164 form, which is the caller identity a dialled
  person sees.
</ParamField>

What changes:

- **You host the bridge.** One container runs the agent worker and the bridge
  web server, reachable at the HTTPS origin you put in `UNMUTE_PUBLIC_URL`. It
  connects out to a LiveKit Server you run. There is no SIP trunk and no Redis.
- **No transfers.** A transfer needs a SIP participant and an outbound trunk,
  and this route has neither, so validation refuses a cold or warm transfer.
  Inbound, outbound and hangup work.
- **One more call fact.** The bridge supplies everything the SIP route does,
  plus `stream_id`.

The emitted `build/livekit/README.md` for a connector target carries the
endpoint, the variables, and how to scale it.
