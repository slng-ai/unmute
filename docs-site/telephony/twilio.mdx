A connection file holds environment variable **names**. This page is about the
values behind them: where each one lives in your Twilio account, and which key it
belongs to.

<Note>
  Unmute never buys a number, creates a trunk, or changes anything on your carrier
  account at compile time. The one exception is deliberate and temporary:
  on supported HTTP callback routes, [`unmute dev --telephony`](/dev/local-telephony)
  points your number's voice webhook at the local run and puts the previous
  value back when you stop it.
</Note>

## Which values you need depends on the route

| Target | `transport` | `environment` keys | Where they come from |
|---|---|---|---|
| Pipecat | `cloud-websocket` | `account_sid`, `auth_token`, `from_number` | the account dashboard, plus a number you own |
| Pipecat | `carrier-websocket` | `account_sid`, `auth_token`, `from_number` | the same three |
| LiveKit Agents | `connector` | `account_sid`, `auth_token`, `from_number` | the same three |
| LiveKit Agents | `sip` | `sip_address`, `sip_username`, `sip_password`, `from_number` | an Elastic SIP trunk you create |

The two groups are different credentials, not two names for one thing. The account
trio identifies your account to Twilio's REST API. The four SIP values are one
trunk's own dial-out settings, and they live in a different part of the console. One
number can serve both, one target at a time.

## First, a voice-capable number

**Phone Numbers**, **Manage**, **Buy a number**, with the Voice capability. Skip
this if you already own the number you want the agent to use.

Whatever you buy or already own is the value of `from_number` (or `SIP_FROM_NUMBER`
on the SIP route). It is also the caller identity the person you dial sees, and
voice capability is the whole requirement on it.

## The account trio: Pipecat routes and the LiveKit connector

These three routes talk to Twilio's REST API in your name, so they need the account
credentials.

| Connection key | The value | Where it is |
|---|---|---|
| `account_sid` | starts with `AC` | the Twilio Console account dashboard |
| `auth_token` | the account's auth token | the same dashboard, revealed on request |
| `from_number` | the number in E.164 form, `+15551234567` | Phone Numbers, Manage |

```yaml connections/twilio_voice.yaml
transport: cloud-websocket
carrier: twilio
environment:
  account_sid: TWILIO_ACCOUNT_SID
  auth_token: TWILIO_AUTH_TOKEN
  from_number: TWILIO_PHONE_NUMBER
```

The names on the right are yours to choose. Those three are what every Twilio example
in the repository uses, so one `.env` drives all of them.

### Pointing the number at the agent

This part differs by route, and it is the part to get right:

- **`cloud-websocket`, in production**: the number points at a static piece of TwiML
  in the console, which streams the call to Pipecat Cloud. There is no URL of yours
  to configure, because nothing of yours is hosted. Your build's generated README
  dictates the exact markup, including the regional stream address, because that
  address comes from the region in your `targets.yaml`.
- **`carrier-websocket` and `connector`, in production**: the number's voice webhook
  points at the public URL of the service you host, as a POST.
- **All three, locally**: `unmute dev --telephony` sets the voice webhook to its
  own tunnel on every start and restores the previous value on exit, so you do
  not touch the console to test. Pipecat `cloud-websocket` points at `POST /`,
  which its local `uv` runner answers. Pipecat `carrier-websocket` and LiveKit
  `connector` point at `POST /telephony/inbound` on the generated application.

<Warning>
  Take the number off any SIP trunk before using it on one of these routes. A number
  attached to a trunk ignores its voice configuration completely, and does so
  silently, so the markup or webhook you set would simply never be consulted.
</Warning>

## Set up the LiveKit SIP trunk in Twilio Console

Here the call arrives over a Twilio Elastic SIP trunk. Configure it in the
Twilio Console; Unmute does not create or attach these carrier resources.
[Twilio's step-by-step guide](https://www.twilio.com/en-us/blog/elastic-sip-trunking-step-by-step-setup)
shows the same Console screens.

<Steps>
  <Step title="Open the trunk">
    In Twilio Console, go to **Elastic SIP Trunking**, **Manage**, **Trunks**.
    Open the trunk used by LiveKit, or create one if none exists. Do not change a
    shared trunk that is serving another route.
  </Step>

  <Step title="Set termination and authentication">
    On **Termination**, choose a unique Termination SIP URI ending in
    `pstn.twilio.com`. Under **Authentication**, select or create a Credential
    List with a username and password. Save the trunk.
  </Step>

  <Step title="Point origination at LiveKit Cloud">
    On **Origination**, select **Add new Origination URI**. Paste the SIP URI from
    your LiveKit Cloud project settings and append `;transport=tcp`, for example
    `sip:abc123def.sip.livekit.cloud;transport=tcp`. Keep it enabled, then add and
    save it. Do not derive this value from `LIVEKIT_URL`: the project URL and SIP
    address can have different subdomains.
  </Step>

  <Step title="Attach the phone number">
    First record the number's current Voice routing so you can restore it later.
    On the trunk's **Numbers** tab, choose **Associate a Number with this Trunk**,
    select your existing voice-capable number, choose this SIP trunk for Voice,
    and save. A number attached to a trunk ignores its normal voice webhook.
  </Step>

  <Step title="Allow calls to transfer">
    In the trunk's **General settings** or **Features**, enable **Call Transfer
    (SIP REFER)** and **PSTN Transfer**. Set the transfer target's caller ID to
    **Transferee**, so the person receiving the transfer sees the original caller.
    Save the trunk.
  </Step>

  <Step title="Test and restore the number">
    Call the attached number. When testing is complete, return to **Numbers** and
    disassociate it from the trunk, then restore the Voice routing you recorded.
    Disassociating keeps the number in your Twilio account; it does not delete the
    number or the existing trunk.
  </Step>
</Steps>

### Copy the four SIP values

| Connection key | The value | Where it is |
|---|---|---|
| `sip_address` | the complete domain ending in `pstn.twilio.com` | the trunk's **Termination** tab |
| `sip_username` | the username in the trunk's credential list | Termination, **Authentication**, Credential Lists |
| `sip_password` | that credential's password | the same credential list |
| `from_number` | the attached number in E.164 form | the trunk's **Numbers** tab |

```yaml connections/twilio_sip.yaml
transport: sip
carrier: twilio
environment:
  sip_address: SIP_TRUNK_HOSTNAME
  sip_username: SIP_AUTH_USERNAME
  sip_password: SIP_AUTH_PASSWORD
  from_number: SIP_FROM_NUMBER
```

The names are plain SIP names rather than Twilio ones because the generated code
can dial through any SIP carrier with them.

## Then declare the names

Two files, and neither holds a value:

```yaml agent.yaml
secrets:
  - TWILIO_ACCOUNT_SID
  - TWILIO_AUTH_TOKEN
  - TWILIO_PHONE_NUMBER
```

Every name your connection maps belongs in `secrets:` too, which is what puts it in
the generated `.env.example` and the startup check. The values go in `.env` locally,
and in your platform's secret store for a deployment.

## Where this page's facts come from

The key names and which route accepts which are read from this repository's own
route table, and they match the connection files in
`examples/twilio-telephony-hello`, `examples/outbound-reminder`,
`examples/pipecat-human-transfer-twilio`, and `examples/livekit-human-transfer`.

The Console workflow was checked against
[Twilio's step-by-step Elastic SIP Trunking guide](https://www.twilio.com/en-us/blog/elastic-sip-trunking-step-by-step-setup)
and [Twilio's SIP Trunking documentation](https://www.twilio.com/docs/sip-trunking)
on 2026-08-18. The account dashboard location of the Account SID and auth token
comes from this repository's generated runbooks; the Twilio pages name the two
values without giving a console path for them.

Your build's `build/<target>/README.md` is the authority for your route, because it
was generated from your package and names your region and your number.
