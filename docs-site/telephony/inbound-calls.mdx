title: "Inbound calls"
description: "Take a real call from your own phone number, on the route that reaches a laptop."
---

An inbound agent answers a call somebody else placed. The channel has to declare
it, and your carrier has to be able to reach whatever is running the agent.

```yaml agent.yaml
channels:
  phone:
    kind: telephony
    inbound: true
```

This page follows `examples/salon-concierge`, the shipped package with an
inbound phone route. It declares `inbound: true` and no outbound, and it carries
a target for each transport, so the same package proves the wiring on whichever
route you pick.

<Note>
  A first inbound call with **no carrier account at all** is the faster loop, and
  it is a different command: see [call your agent
  locally](/dev/local-telephony). This page is the real call, through your own
  number.
</Note>

## Pick the target your carrier can reach

The package declares two targets, one per platform, on the route each platform
recommends for Twilio:

| Target | Transport | How the call arrives |
|---|---|---|
| `pipecat` | `cloud-websocket` | your number points at a static TwiML Bin whose stream goes to Pipecat Cloud |
| `livekit` | `sip` | your number is attached to a Twilio Elastic SIP Trunk pointed at LiveKit SIP |

**Use the `pipecat` target for a real call that lands on your laptop.** Twilio
reaches that route over HTTPS and WSS, which a tunnel can carry. SIP needs the
carrier to reach a LiveKit Server and a LiveKit SIP service over public
signalling and media addresses, which an HTTPS tunnel cannot provide. For
`livekit`, use a LiveKit Cloud project or run both services at public addresses.
The agent worker can still run on your laptop.

## What you need

- A Twilio account with a voice capable phone number.
- [`uv`](https://docs.astral.sh/uv/getting-started/installation/) on your PATH.
  This route starts the generated Pipecat agent with `uv run`.
- `cloudflared` on your PATH for the managed tunnel (`brew install cloudflared`
  on macOS), or your own tunnel and `--public-url`.
- Model provider keys.

Put the values in `examples/salon-concierge/.env`:

```bash
OPENAI_API_KEY=sk-...
SLNG_API_KEY=...
TWILIO_ACCOUNT_SID=ACxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
TWILIO_AUTH_TOKEN=your_auth_token
TWILIO_PHONE_NUMBER=+15551234567
PIPECAT_CLOUD_ORGANIZATION=your-org-slug
SIP_TRUNK_HOSTNAME=your-trunk.pstn.twilio.com
SIP_AUTH_USERNAME=your_trunk_username
SIP_AUTH_PASSWORD=your_trunk_password
SIP_FROM_NUMBER=+15551234567
```

The last four are the trunk settings the `livekit` target's connection names.
They are in this list because `agent.yaml` declares every name the package
writes, and the generated agent checks that whole list before it takes a call. If
you are only testing the `pipecat` target you can put any placeholder there. The
[connections reference](/reference/connections-yaml) shows where each group of
names comes from.

You never set `UNMUTE_PUBLIC_URL` or `UNMUTE_OUTBOUND_TOKEN`. The dev command
supplies those itself.

<Warning>
  Every environment variable name must be a valid shell identifier: letters,
  digits, and underscores, never starting with a digit. A name like
  `2FACTOR_API_KEY` would fail when a platform exports it, so Unmute refuses the
  name during validation, before it starts a tunnel or a local agent.
</Warning>

## Take the call

```sh
unmute dev examples/salon-concierge --telephony --carrier --target pipecat
```

`--carrier` is the part that reaches your account: without it the run stays on
your machine and your number is never touched. What it changes, and what it puts
back, is on [call your agent
locally](/dev/local-telephony#when-you-do-want-a-real-call).

Watch for three things in the output:

1. the line saying your number's Twilio voice webhook was updated, and what it
   was before,
2. the local agent line with its temporary public origin and a note that quick
   tunnel URLs rotate on every run,
3. the call line: `call +1XXXXXXXXXX  ·  ctrl-c to stop`.

Call that number. The agent answers and greets you. Speak, and it replies.

Ctrl-c stops the run and puts your number's previous voice configuration back.
Your TwiML Bin is never touched, because the run answers Twilio's webhook itself
at `POST /` and sends the media stream through `wss://<tunnel-host>/ws`.

## One number, one target at a time

A number attached to a SIP trunk ignores its voice configuration, so it cannot
also point at a TwiML Bin. Take the number off the trunk to test the `pipecat`
target, and follow the [Twilio Console steps](/telephony/twilio#set-up-the-livekit-sip-trunk-in-twilio-console)
to put it back for the `livekit` target.

## If the call does not arrive

<AccordionGroup>
  <Accordion title="cloudflared not found on PATH">
    Install it, or run your own tunnel and pass its HTTPS origin with
    `--public-url https://your-tunnel.example`.
  </Accordion>
  <Accordion title="phone number was not found on this Twilio account">
    The number in `TWILIO_PHONE_NUMBER` is not on the account behind
    `TWILIO_ACCOUNT_SID`, or it is not voice capable. Check it in the Twilio
    console.
  </Accordion>
  <Accordion title="Twilio refuses the call">
    The reason is printed in Twilio's own words: geographic permissions, or a
    trial account that can only reach verified numbers. Fix it in the console
    and run again.
  </Accordion>
  <Accordion title="missing telephony credentials">
    The command lists exactly which names it could not find, before it starts
    anything.
  </Accordion>
  <Accordion title="nothing happened to my number at all">
    The run had no `--carrier`, so it never asked your carrier for anything. That
    is the default, and the route line says `no carrier involved`.
  </Accordion>
</AccordionGroup>
