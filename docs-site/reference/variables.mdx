A variable is a named value that lives for one call. This is the complete field
reference. For a task-led introduction, start with [Variables](/build/variables).

```yaml agent.yaml
variables:
  customer_name:
    type: string
    source: call_start
    default: there
    description: Caller's first name, used in the greeting and the prompt.
```

| Field | Required | What it is |
|---|---|---|
| `type` | yes | `string`, `number`, `integer`, or `boolean` |
| `source` | no | where the value comes from |
| `default` | no | the value to use when nothing supplies one |
| `description` | no | a note; for `conversation` variables the model reads it |

## Sources

| Source | Who supplies it | Availability |
|---|---|---|
| `call_start` | the dispatch payload, or `--var` locally | every channel, before the first word |
| `conversation` | the model, through the generated `update_variables` tool | during the call |
| `session_id` | the phone adapter | Pipecat `carrier-websocket`; LiveKit `sip` or `connector` |
| `call_id` | the phone adapter | Pipecat `carrier-websocket`; LiveKit `sip` or `connector` |
| `stream_id` | the phone adapter | Pipecat `carrier-websocket`; LiveKit `connector`; not LiveKit `sip` |
| `direction` | the phone adapter | Pipecat `carrier-websocket`; LiveKit `sip` or `connector` |
| `from_number` | the phone adapter | Pipecat `carrier-websocket`; LiveKit `sip` or `connector` |
| `to_number` | the phone adapter | Pipecat `carrier-websocket`; LiveKit `sip` or `connector` |
| `carrier` | the phone adapter | Pipecat `carrier-websocket`; LiveKit `sip` or `connector` |
| `connection` | the phone adapter | Pipecat `carrier-websocket`; LiveKit `sip` or `connector` |

The last eight are system sources. You declare them and the selected phone route
must prove it can supply them. Pipecat `daily-sip` and `cloud-websocket` routes
do not bind system sources today, so using one there is a validation error.

For an inbound LiveKit or Pipecat telephony channel, every `call_start` variable
needs a default. There is no dispatch payload to supply an unsolicited incoming
call before its greeting.

## Where a variable can be used

`{{name}}` renders a variable. Two kinds of site, with different timing:

| Site | Renders | Can name |
|---|---|---|
| `conversation.greeting.text` | once, at session start | a variable that already has a value |
| an agent's instructions | once, at session start | a variable that already has a value |
| a task's instructions | when that task starts | a variable that already has a value, or one assigned from a task result |
| a tool's `inject:` value | on every tool call | any declared variable |
| a webhook tool's `path` | on every tool call | any declared variable, URL encoded |

"Already has a value" means `source: call_start`, a system source, or a
`default`. Naming anything else in a session-start site is an error:

```text wrap
conversation.greeting.text references {{requested_service}}, which has no value when the prompt is built; give it source: call_start, a system source, or a default
```

Task instructions use the live call state when the task begins. This lets a
later task read a variable assigned from an earlier task result. If no earlier
task assigned that value, the template renders an empty string.

An undeclared name is an error too. Invalid session-start and undeclared names
are never silent empty strings.

## Seeding values locally

```sh
unmute dev ./agent --var customer_name=Ada --var customer_id=cus_2002
```

Repeatable. Each value is parsed against the declared type, so an `integer`
variable receives a number and not a quoted string. `--var` is the local stand
in for the dispatch payload production sends, so it accepts `call_start`
variables only:

```text wrap
unmute: dev examples/salon-support: --var requested_service=haircut: "requested_service" has source conversation, so the model saves it mid-call through update_variables, not you
```

An undeclared name is refused rather than accepted and dropped.

## Letting the model save one

Declaring any `source: conversation` variable creates a tool named
`update_variables` in the generated project. You do not write it, and you do
not list it. The name is reserved: a package tool or control cannot also be named
`update_variables`. The model calls it when the caller says something worth
keeping.

## Passing a value into a tool

```yaml tools/book_appointment.yaml
description: Book the selected appointment for the current customer.

input:
  type: object
  properties:
    slot_id:
      type: string
  required:
    - slot_id

inject:
  customer_id: "{{customer_id}}"
  service: "{{requested_service}}"

local:
  handler: tools/book_appointment.py
```

`inject` values are not part of the model's schema, so the model can neither
see them nor overwrite them. An `inject` key that also names an `input`
property is a compile error, for exactly that reason.

Each injected value must be a scalar. A string may contain `{{variable}}`
tokens; maps and lists are refused.

`inject` is legal on `webhook` and `local` tools: the two kinds whose request
Unmute builds itself.

When an injected variable has no value at call time, the tool refuses instead
of sending a half formed request, and the model is told to ask:

```text
cannot call book_appointment yet: requested_service not set. Ask the caller first.
```

## Assigning a task result to a variable

```yaml agent.yaml
controls:
  check_customer:
    kind: delegate
    task: customer_record
    assign:
      customer_id: result.customer_id
```

The task's typed result lands in the variable, and the rest of the call can use
it.

## Carrying variables through a handoff

```yaml
    context:
      history: full
      variables: all
```

`variables` takes `all` or a list of names.
