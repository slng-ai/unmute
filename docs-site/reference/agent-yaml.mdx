`agent.yaml` is the agent. Nothing in it is specific to a runtime; that lives
in [targets.yaml](/reference/targets-yaml).

YAML decoding is strict. An unknown field is an error with the file and the
line, not a shrug.

Durations use Go duration syntax, for example `90s`, `15m`, or `1h30m`.

## Top level

| Key | Required | What it is |
|---|---|---|
| `version` | yes | the schema version, `1` |
| `entry_agent` | yes | which agent answers |
| `models` | yes | the model palette, grouped by kind |
| `listen` | when `models.listen` has 2 or more entries | which listen entry to use |
| `turn` | when `models.turn` has 2 or more entries | which turn entry to use |
| `variables` | no | per call values |
| `secrets` | no | every environment variable name this package writes |
| `destinations` | when a `human_transfer` is used | symbolic name to the environment variable holding a number |
| `agents` | yes | one or more agents |
| `tasks` | no | delegated steps |
| `task_groups` | no | ordered sequences of tasks |
| `controls` | no | delegate, agent transfer, human transfer |
| `tools` | no | which tool files to load |
| `conversation` | no | greeting, interruption, inactivity, limits |
| `tracing` | no | tracing provider |
| `channels` | yes | how people reach the agent |
| `capacity` | for telephony or code targets | your traffic estimate |

## models

Four sections. The section an entry sits in decides its kind: `think` (LLM),
`speak` (TTS), `listen` (STT), `turn` (turn detection). Entry names share one
namespace across sections and are yours to choose.

```yaml
models:
  think:
    reasoning:
      provider: openai
      model: gpt-5.6-luna
      params:
        reasoning_effort: "none"
```

Which fields are legal depends on the section:

| Field | Legal section |
|---|---|
| `provider`, `model`, `endpoint_env`, `placement`, `params`, `description` | `think`, `speak`, `listen`, `turn` |
| `voice`, `speed` | `speak` |
| `language` | `speak`, `listen` |
| `temperature`, `top_p`, `top_k` | `think` |
| `semantic_endpointing` | `turn`: `required`, `preferred`, or `off` |
| `fallback` | `think`, `listen` |

Entries you do not reference are legal alternates.

The provider catalogue has two wildcard routes. Pipecat accepts an unlisted
listen, speak, or think provider only with `endpoint_env`, through an
OpenAI-compatible integration. LiveKit accepts an unlisted think provider
through LiveKit Inference; its listen and speak provider lists are closed.
Never invent a provider name for either route.

`model`, `voice`, and `params` are passthrough. Unmute does not check their ids,
keys, or values. A name the target's settings object has no field for is not
dropped: it rides that target's overflow field and reaches the provider anyway.
The `reasoning_effort` line above is the case to know: a reasoning model such as
`gpt-5.6-luna` refuses a request that carries function tools without it.
[Reasoning model](/models/llm) says why.

Do not guess model ids, voice ids, or params. Use values the user supplied or
values verified in the provider's own documentation.

## variables

```yaml
variables:
  customer_name:
    type: string
    source: call_start
    default: there
    description: Caller's first name.
```

| Field | Values |
|---|---|
| `type` | `string`, `number`, `integer`, `boolean` |
| `source` | `call_start`, `conversation`, or a system source |
| `default` | any value of the declared type |
| `description` | a note, also read by the model for `conversation` variables |

Full detail on [variables](/reference/variables).

## secrets

```yaml
secrets:
  - OPENAI_API_KEY
  - SLNG_API_KEY
  - SIP_TRUNK_HOSTNAME
  - SIP_AUTH_USERNAME
  - SIP_AUTH_PASSWORD
  - SIP_FROM_NUMBER
  - BILLING_PHONE_NUMBER
  - SUPERVISOR_PHONE_NUMBER
```

A list of UPPER_SNAKE environment variable names. Never values, and never usable
in a `{{template}}`. That list is `examples/livekit-human-transfer`'s: two model
keys, the four names its connection maps, and the two desks it can transfer to.

The rule is: **every environment name you wrote anywhere in this package** goes
here. Model and tool credentials, the names a connection's `environment:` maps
to, and the numbers `destinations:` points at. Names the driver or the platform
supplies for you, such as `REDIS_URL` or `DAILY_API_KEY`, are not yours to
declare and are left out. See [secrets](/reference/secrets).

## destinations

```yaml
destinations:
  billing_line: BILLING_PHONE_NUMBER
  supervisor_line: SUPERVISOR_PHONE_NUMBER
```

The symbols a `human_transfer` control can name. A value is only the UPPER_SNAKE
name of an environment variable holding an E.164 number or a `sip:` URI, read at
call time. A number written here is refused, because `agent.yaml` is the portable
half of a package:

```text
agent.yaml:60: destination "billing_line" is a literal. agent.yaml is
  the portable half of a package, so a destination names an environment variable holding
  the number: billing_line: BILLING_PHONE_NUMBER
```

The model never sees a number, and cannot dial one that is not listed here.

## agents

```yaml
agents:
  appointment_desk:
    instructions: instructions.md
    model: reasoning
    voice: voice
    tools:
      - check_availability
```

| Field | What it is |
|---|---|
| `instructions` | path to a Markdown prompt in the package |
| `model` | a `models.think` entry name |
| `voice` | a `models.speak` entry name |
| `tools` | names this agent may call: loaded tool files and controls; definitions never go here |

## tasks

```yaml
tasks:
  customer_record:
    instructions: tasks/customer-record.md
    tools:
      - lookup_customer
    result:
      customer_id: string
      record_status:
        enum:
          - existing
          - created
          - failed
    context:
      history: full
```

| Field | What it is |
|---|---|
| `instructions` | the task's own prompt file |
| `tools` | names of loaded tools the task may call; definitions never go here |
| `model` | optional override of the thinking model |
| `result` | the typed result returned by the whole task, not a tool's `output` schema |
| `context` | what the task sees, see below |

**Task `result:` and tool `output:` are different contracts.** A task must
declare `result:`, but do not copy an attached tool's `output:` into it by
default. The tool output describes one call in `tools/<name>.yaml`; the task
result describes what the calling agent receives after the task has made all of
its calls.

### context

Used by tasks and by transfer controls.

| Field | Values | Notes |
|---|---|---|
| `history` | `full`, `messages`, `last_n`, `summary`, `reset` | required |
| `max_messages` | a positive number | legal with `last_n` only |
| `summarizer` | a model entry name | legal with `summary` only |
| `include_tool_calls` | `true` or `false` | whether tool calls travel too |
| `variables` | `all` or a list of names | transfer controls only |

## task_groups

```yaml
task_groups:
  appointment_flow:
    steps:
      - identify_customer
      - select_appointment
    context_scope: shared
    then: return
    merge: results
```

| Field | Values |
|---|---|
| `steps` | task names, in order, at least one |
| `context_scope` | `shared` or `isolated` |
| `then` | `return`, `transfer`, or `end` |
| `then_target` | an agent name, required with `transfer`, illegal otherwise |
| `merge` | `results` |

When a task runs inside a group, the group's `context_scope` governs it. The
member task's own `context` does not override the group.

## controls

Everything the model can trigger besides a tool. One `kind` per control.

```yaml
controls:
  check_customer:
    kind: delegate
    task: customer_record
    when: Identify the caller first.
    assign:
      customer_id: result.customer_id
```

| Kind | Fields |
|---|---|
| `delegate` | `task` or `group`, `when`, `assign` |
| `agent_transfer` | `to`, `when`, `announce`, `context`, `requires` |
| `human_transfer` | `when`, and exactly one of `cold:` or `warm:` |

For `agent_transfer`, `announce` is optional exact spoken text. It is not a
model instruction: write the short sentence the caller should hear. Omit it
for a silent handoff.

A human transfer names its shape with a block, so a warm only field cannot be
written on a cold transfer:

| Block | Fields |
|---|---|
| `cold` | `destination`, `ring_timeout`, `on_unavailable` |
| `warm` | `destination`, `briefing`, `ring_timeout`, `on_unavailable` |

`on_unavailable` is `return_to_caller` or `hangup`; omitted means
`return_to_caller`. `ring_timeout` uses the platform default when omitted:
30 seconds on LiveKit and 60 seconds on the Pipecat Twilio route.
`destination` is a symbol resolved in the top level
[`destinations:`](#destinations) map above.

Whether a route can carry the shape you asked for is decided by the connection.
A warm transfer is supported only on LiveKit `sip`; Unmute does not support warm
transfer on any Pipecat target.
A warm transfer on a route with no leg to move is refused by name:

```text
pipecat: telephony warm_transfer: telephony route (pipecat, cloud-websocket, twilio) does
  not emit warm transfer: a warm handoff has to act on how the destination's leg ended,
  which on this route needs a callback endpoint you host, and hosting nothing is what
  this route is for; warm transfer compiles on (livekit, sip) trunks today. Connection
  "twilio_voice" declares transport: cloud-websocket
```

## tools

```yaml
tools:
  - check_availability
  - end_call
```

Which `tools/<name>.yaml` files to load. Availability is decided by the `tools`
list on each agent and task.

This top-level list and every agent or task list contain names only.
**Define each tool once.** Put its full contract in `tools/<name>.yaml`; never
inline `description`, `input`, `output`, `inject`, or an execution block under
a `tools:` list in `agent.yaml`.

### Tool files

One file per tool, in `tools/`. The top level is the contract with the model;
exactly one execution block says how it runs.

| Field | What it is |
|---|---|
| `description` | what the model reads |
| `input` | JSON Schema of the parameters the model fills |
| `output` | JSON Schema of the result, recorded in the compile report but not enforced at run time yet |
| `inject` | hidden arguments, values may carry `{{variables}}`; legal on `webhook` and `local` |
| `interruption` | `provider_default`, `continue`, `cancel` |
| `effect` | `returns_data`, `ends_conversation` |

| Execution block | Fields |
|---|---|
| `local` | `handler`, a Python file in the package |
| `webhook` | `url_env`, `path`, `auth` |
| `mcp` | `url_env`, `transport`, `auth`, `tools` |
| `builtin` | `id`, `instructions` |
| `client` | none |
| `provider_hosted` | none |

An `mcp` file is the block and nothing else. The six contract fields above are
all illegal on one, because the server describes its own tools.

| Field | Values |
|---|---|
| `transport` | `sse` or `streamable_http` |

Builtin ids: `end_call`.

`webhook.auth`:

| Field | What it is |
|---|---|
| `type` | `bearer` or `api_key` |
| `token_env` | environment variable holding the token |
| `header` | header name, `api_key` only, defaults to `X-API-Key` |

## conversation

```yaml
conversation:
  greeting:
    speaks_first: agent
    text: "Hi, how can I help?"
  interruption:
    enabled: true
```

| Field | Values |
|---|---|
| `greeting.speaks_first` | `agent` or `user` |
| `greeting.text` | the opening line, requires `speaks_first: agent` |
| `interruption.enabled` | required when `interruption` is present |
| `interruption.minimum_words` | how much speech counts as an interruption |
| `interruption.ignore_phrases` | phrases that do not interrupt |
| `inactivity.nudge_after`, `inactivity.end_after` | durations |
| `max_duration` | a duration |
| `thinking_audio` | `none` or `subtle` |

## tracing

```yaml
tracing:
  provider: langfuse
```

`langfuse` is the only provider today. It requires `LANGFUSE_BASE_URL`,
`LANGFUSE_PUBLIC_KEY`, and `LANGFUSE_SECRET_KEY`.

## channels

```yaml
channels:
  web:
    kind: realtime_audio
  phone:
    kind: telephony
    inbound: true
    outbound: true
```

| Field | Values |
|---|---|
| `kind` | `realtime_audio` or `telephony` |
| `inbound`, `outbound` | `true` or `false` |
| `required_controls` | controls this channel requires |
| `on_voicemail` | `hangup` or `leave_message`, requires `outbound: true` |

### Two rules a telephony channel brings with it

Both are enforced, both fail validation, and both are easier to read here than
to meet by trial and error.

**A warm transfer needs `outbound: true`.** A warm transfer dials the
destination itself, so the agent places a call, and a channel that only receives
them cannot:

```text
channel "phone" needs outbound: true; a warm transfer places a call to its destination
```

Write `outbound: true` even on a line people only ring in on. It describes what
the agent does, not what the number is for.

**`capacity.peak_starts_per_second` becomes required.** The moment any channel
is `telephony`, the field stops being optional and must be positive:

```text
capacity.peak_starts_per_second must be positive for telephony
```

Calls arrive in bursts and each one starts a session, so a rate is the number
the compiler sizes workers from. One is a fine answer for a first line.

## capacity

Capacity is required for every code target, including both targets documented
on this site. A telephony channel also makes `peak_starts_per_second` required.

```yaml
capacity:
  peak_sessions: 5
  max_sessions: 10
  avg_session_duration: 5m
```

| Field | What it is |
|---|---|
| `peak_sessions` | expected concurrent sessions at peak |
| `max_sessions` | the ceiling you want to support |
| `peak_starts_per_second` | how fast calls arrive at peak. **Required and positive** as soon as any channel is `telephony`; optional otherwise |
| `avg_session_duration` | a duration, for example `5m` |

The compiler turns these into worker and quota numbers, marked
`[unbenchmarked]`.
