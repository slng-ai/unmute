title: "Secrets"
description: "Names only, never values: how a credential reaches the agent and its tools."
---

A package never contains a secret value. It contains the **name** of an
environment variable, and the value arrives at run time from your environment
or your platform's secret store.

## Declare them

```yaml agent.yaml
secrets:
  - OPENAI_API_KEY
  - SLNG_API_KEY
  - SIP_TRUNK_HOSTNAME
  - SIP_AUTH_USERNAME
  - SIP_AUTH_PASSWORD
  - SIP_FROM_NUMBER
  - BILLING_PHONE_NUMBER
  - SUPERVISOR_PHONE_NUMBER
```

A list of names. Each one must be UPPER_SNAKE: a capital letter, then capitals,
digits, and underscores. A lower case or punctuated entry is a typo that would
otherwise become a lookup failing at call time, so it is refused:

```
agent.yaml:7: secret "openai_api_key" must be an UPPER_SNAKE environment variable name
```

Declaring the same name twice is refused too.

<Warning>
  The name must also be a valid shell identifier, which is the same rule.
  Platforms export secrets through a shell, so a name like `2FACTOR_API_KEY`
  fails at export and the value is simply missing at run time, with one obscure
  line in the logs as the only clue. The same check runs on a connection's
  environment values, where it says so out loud:

  ```
  connections/twilio_sip.yaml:6: connection "twilio_sip" environment value
    "2FACTOR_SIP_PASSWORD" is not a valid environment variable name: use letters, digits,
    and underscores, and do not start with a digit. A deployment platform exports secrets
    through a shell, so this name would be missing at runtime with no error of its own
  ```
</Warning>

## The rule: everything you wrote, nothing you did not

`secrets:` answers one question, "what did the author write?" So the list holds
**every** environment name that appears anywhere in your package:

| Where you wrote the name | Example |
|---|---|
| a model's or tool's credential field | `OPENAI_API_KEY`, `SALON_API_TOKEN` |
| a connection's `environment:` values | `SIP_TRUNK_HOSTNAME` |
| a `destinations:` value in `agent.yaml` | `BILLING_PHONE_NUMBER` |

And it holds nothing else. These names are supplied by the route, the platform,
or `unmute dev`, so no package declares them:

| Name | Who supplies it |
|---|---|
| `REDIS_URL` | `unmute dev` locally, the operator at deploy time, on the routes that read it |
| `UNMUTE_PUBLIC_URL`, `UNMUTE_OUTBOUND_TOKEN` | `unmute dev` locally, the operator at deploy time |
| `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET` | the local Compose graph, or your LiveKit Cloud project |
| `DAILY_API_KEY`, `PIPECAT_CLOUD_ORGANIZATION` | the route's own runtime environment |

They are still documented, because you may still have to set them for a local
run or a self-hosted deploy. They are just not yours to declare.

Leaving out a name you did write is a warning, not an error, so the package
compiles and then fails on its first call. Read the warnings:

```
✓ livekit (livekit)

Warnings:
  livekit: environment variables referenced but not declared in secrets: SIP_TRUNK_HOSTNAME (connections/twilio_sip.yaml environment sip_address)
```

## What declaring one buys you

Two things, both in the generated project:

**The environment template.** `build/<target>/.env.example` lists exactly the
variables this build needs, your names first and the ones the route supplies
after:

```
# Environment for pipecat (generated by unmute).
# Copy this file to `.env` and fill in the values. Never commit `.env`.

BILLING_PHONE_NUMBER=
OPENAI_API_KEY=
SLNG_API_KEY=

# required by the target or a connection
DAILY_API_KEY=
```

That is `examples/pipecat-human-transfer-daily`'s real file. On other routes the
generated file also carries a short note about which names a phone call adds and
who reads them, so read the one your build wrote rather than assuming this shape.

**A startup check.** The generated agent refuses to start without them, and
names what is missing:

```python
REQUIRED_ENV = [
    "OPENAI_API_KEY",
    "SLNG_API_KEY",
]
```

A missing key stops the container at startup instead of surfacing as a
confusing failure on the first tool call or the first spoken word.

## Secrets never flow through templates

`{{...}}` renders [variables](/reference/variables) only. Naming a secret in a
template is a compile error, not a value that leaks at run time:

```
agent.yaml:70: conversation.greeting.text references {{OPENAI_API_KEY}}, but secrets never flow through templates; a secret reaches a tool through its own *_env field
```

The reason is where a template ends up. It renders into speech, a prompt, a
tool argument, or a URL, so its value is spoken, logged, or traced. That is
right for a customer's name and wrong for a token.

## The seams a secret travels through

| Seam | Used for |
|---|---|
| a tool's `webhook.url_env` | the base URL of an authenticated API |
| a tool's `webhook.auth.token_env` | the bearer token or API key |
| a tool's `mcp.url_env` | the MCP server address |
| a tool's `mcp.auth.token_env` | the token that server wants |
| a connection's `environment:` values | the carrier account behind a phone route |
| a model's `endpoint_env` | pointing a model at your own gateway |
| `os.environ` inside a `local:` handler | a handler that builds its own request |

```yaml tools/reschedule_appointment.yaml
webhook:
  url_env: SALON_API_URL
  path: /customers/{{customer_id}}/appointments
  auth:
    type: bearer
    token_env: SALON_API_TOKEN
```

Every one of these fields holds a name. `token_env` in particular is checked:

```
token_env must be an UPPER_SNAKE environment variable name, never a secret value
```

## Where the values come from locally

`unmute dev` builds the run's environment from your shell, then `.env` in the
current directory, then `.env` in the package directory. Later files win, so a
repository wide `.env` can hold shared keys while one package overrides a
value.

`.env` files are never generated with values in them, and never committed.

## Where the values come from in production

Your platform's secret store. Both supported platforms take a secrets file on
the first deploy and a one command update after that. The generated
`build/<target>/README.md` carries the exact commands.
