`unmute compile` gives you a normal Pipecat project with a `Dockerfile` and a
deploy manifest. Pipecat Cloud builds the image from that Dockerfile in the cloud
and runs it, and the `pipecat` CLI is how you drive it.

<Note>
  The runbook of record is `build/<target>/README.md` in your own build. It was
  generated from your package, so it names your region, your agent, your secret
  set, and your variables. This page is the same path with the reasons attached.
</Note>

## The manifest the compiler wrote

`agent_name` is your package's [`name:`](/reference/agent-yaml#name) joined to
the target it was compiled for, and it is the agent's identity: names are unique
across your organisation and a deploy updates whichever agent matches. The
secret set follows the same name.

Changing it creates a second agent rather than moving the first: see
[renaming the agent](#renaming-the-agent).

```toml pcc-deploy.toml
agent_name = "acme-support-pipecat"
region = "eu-central"
secret_set = "acme-support-pipecat-secrets"

[scaling]
min_agents = 1
```

Every line comes from your package: the agent name, the
`deployment_region` you declared, the secret set the deploy will read, and the
`warm_instances` you declared. The manifest names **no image**, deliberately:
naming one switches cloud builds off. The `[scaling]` table appears only when the
target declares `warm_instances`, and it comes last because in TOML any key after
a table header belongs to that table.

## Install the CLI

You need Python 3.11 or later and `uv`. Install the
[Pipecat CLI](https://docs.pipecat.ai/api-reference/cli/overview), then check it:

```sh
uv tool install pipecat-ai-cli
pipecat --version
```

## Secret set first, then deploy

The manifest already references the secret set, so a deploy cannot start until it
exists. In order:

```sh
cd my-agent/build/pipecat
cp .env.example .env            # then fill in the values
pipecat cloud auth login
pipecat cloud secrets set acme-support-pipecat-secrets --file .env --region eu-central
pipecat cloud deploy
pipecat cloud agent status acme-support-pipecat
```

`--file .env` uploads every name in the file as one set. Run the same
`secrets set` command again to change a value.

A secret set is **region-scoped**, and an agent can only read one in its own region.
That is why the region appears twice above and comes from one line in your package:
change `deployment_region` and recompile, and both move together.

Secret-set names are globally unique across the platform. If yours is taken, create
it under another name and pass `--secrets <other-name>` on the deploy, which
overrides the manifest.

## What `deploy` does, and does not do

One command does the first deploy and every later one. Deploying the same agent
name again updates the existing agent rather than making a second one. Sessions
already running finish on the old image, and a deploy that fails leaves the previous
ready version serving traffic.

`status` reporting `ready` means the agent is healthy. It does **not** mean the
agent is running the code you just compiled. See [read the Build ID, not
`ready`](#read-the-build-id-not-ready).

No warm instance is kept unless you ask for one. Ask in the package, on the
target:

```yaml targets.yaml
targets:
  pipecat:
    provider: pipecat
    warm_instances: 1
```

That becomes `[scaling] min_agents` in the manifest, so it applies to this deploy
and every later one. On a phone route it is not a latency nicety: a cold start can
outrun the session window, and then the call is never answered at all rather than
answered slowly. See [Pipecat over Twilio](/telephony/pipecat-twilio#deploy-with-a-warm-instance)
for what a cold start costs on that route.

`pipecat cloud deploy --min-agents 1` does the same for one deploy, which is worth
knowing for a quick test. It is not the durable answer, and neither is editing the
manifest: `unmute compile` rewrites that file.

## Every later deploy

`pipecat cloud deploy` reads `build/pipecat/` and nothing else, so a redeploy is
only as current as your last compile, and a stale build deploys without
complaining. Five steps, in this order, every time.

<Steps>
  <Step title="Compile">
    ```sh
    unmute compile ./my-agent
    ```

    <Warning>
      `unmute compile ./my-agent --target pipecat` compiles **only** this target.
      A package that also deploys to livekit or slng leaves those builds
      untouched, however old they are. With no `--target`, every target is
      compiled.
    </Warning>

    Compile and deploy from the same checkout. A second checkout or a git
    worktree has its own `build/pipecat/`, so compiling in one and deploying from
    the other ships the older of the two without saying so.
  </Step>

  <Step title="Check the .env still covers the build">
    ```sh
    cd build/pipecat
    cut -d= -f1 .env.example | grep -E '^[A-Z]' | sort -u > /tmp/required
    cut -d= -f1 .env | grep -E '^[A-Z]' | sort -u > /tmp/present
    comm -23 /tmp/required /tmp/present
    ```

    `.env` is yours and survives every recompile. `.env.example` is the
    compiler's and is rewritten every time, so a renamed or added variable lands
    in one and not the other. Anything the last line prints is missing from your
    `.env`.

    Fill it in before going on. A missing name deploys cleanly, reports ready,
    and then refuses every session: see [your `.env` does not follow a
    rename](#your-env-does-not-follow-a-rename).
  </Step>

  <Step title="Upload the secret set">
    ```sh
    pipecat cloud secrets set acme-support-pipecat-secrets --file .env --region eu-central
    ```

    Needed only when `.env` changed, and safe to run when it did not: it merges
    rather than replaces, so names you do not pass keep their values. It restarts
    the agent.
  </Step>

  <Step title="Deploy">
    ```sh
    pipecat cloud deploy
    ```

    From `build/pipecat`, where step 2 left you. Run it anywhere else and it stops
    with `Agent name is required`, which is about your working directory and not
    your manifest.
  </Step>

  <Step title="Confirm the Build ID changed">
    ```sh
    pipecat cloud agent status acme-support-pipecat
    ```

    A new `Build` value is the only proof your code shipped. `Ready`, `Updated
    At` and `Active Deployment ID` all move without a new image: see [read the
    Build ID, not `ready`](#read-the-build-id-not-ready).
  </Step>
</Steps>

A redeploy moves nothing beyond those steps. The region and the carrier
configuration stay as they are, and any tool sample under `samples/` survives the
recompile alongside your `.env`.

Changing a secret on its own needs no deploy at all, though it does restart the
agent. Step 3 is the whole procedure.

## When the deploy looks fine and the call does not

A deploy can report success while a call reaches old code, or reaches nothing at
all. Four causes, in the order they are worth checking. All four are silent: none
of them fails a deploy.

### Read the Build ID, not `ready`

Three fields on `status` move on their own and say nothing about your code.
`Updated At` changes on any deploy. `Active Deployment ID` changes whenever the
agent is re-rolled, including onto the image it was already running. `Ready`
describes the agent's health.

**`Build` is the field to read.** It changes only when a new image was built, so it
is the one thing that proves your compile shipped.

```sh
pipecat cloud agent status acme-support-pipecat
```

`Ready: True` beside a Build ID from two hours ago means a two-hour-old agent is
healthy.

### Deploy from the directory that holds the manifest

`pipecat cloud deploy` reads `pcc-deploy.toml` from the working directory and
nothing else. Run it anywhere else and it stops with an error about your agent
rather than your directory:

```
Agent name is required
```

The manifest is fine. Go back to [every later deploy](#every-later-deploy) and run
the steps from `build/pipecat`.

### The carrier may point at a different agent

On the `cloud-websocket` route the agent name is half of
`_pipecatCloudServiceHost` in your TwiML, and nothing keeps that value in step
with your manifest. It names an agent, so a wrong name is not an error. It is a
different agent.

| What the parameter names | What a call does |
|---|---|
| the agent you just deployed | works |
| another agent in your organisation | answers with **that** agent's prompt, models and tools |
| an agent that no longer exists | connects, then drops in under a second |

The middle row is the one that costs an afternoon, because the call is answered and
sounds like your agent ignoring every change you make. Read the parameter against
the deployed name before you suspect the build:

```sh
pipecat cloud agent list
```

The value must be `<agent-name>.<organization>`, where the organization is the slug
from `pipecat cloud organizations list`.

### Your `.env` does not follow a rename

`.env` is yours, so `unmute compile` never rewrites it. `.env.example` is the
compiler's, and it is rewritten every time. Rename a transfer destination, or add a
provider, and the two drift apart: the new name is in `.env.example`, missing from
`.env`, and therefore missing from the secret set. The container then starts,
refuses the session and stops:

```
Exception running bot(): Missing environment for a phone call: MANAGER_PHONE_NUMBER
```

Compile does not warn about this, which is why comparing the two files is [step 2
of a redeploy](#every-later-deploy). Add the missing name, upload the set, then
deploy.

Names left in `.env` that no longer appear in `.env.example` are harmless. Delete
them anyway, so the next person does not read a renamed variable as a live one.

## Renaming the agent

A deploy resolves the agent by name, so a new name is a **new agent**. The old
one keeps running, keeps billing, and keeps answering the phone number that
still points at it.

<Steps>
  <Step title="Create the secret set under the new name">
    ```sh
    pipecat cloud secrets set <new-name>-secrets --file .env --region <region>
    ```

    Before the deploy, not after: the manifest references the set by name and a
    deploy cannot start without it. A new agent has no secrets of its own.
  </Step>
  <Step title="Compile, deploy, wait for ready">
    ```sh
    unmute compile ./my-agent && cd build/pipecat && pipecat cloud deploy
    ```

    ```sh
    pipecat cloud agent status <new-name>
    ```
  </Step>
  <Step title="Repoint the carrier">
    On the `cloud-websocket` route the agent name is half of the service host
    your TwiML carries, and nothing updates it for you. Edit the Bin for this
    number in the Twilio Console:

    ```xml
    <Parameter name="_pipecatCloudServiceHost" value="<new-name>.<your-organization>"/>
    ```

    The organization is the **slug** from `pipecat cloud organizations list`, the
    one shaped like `three-random-words-12345`, never the display name. Until
    this is saved, calls keep reaching the old agent.

    On the `daily-sip` route the name is compiled into the helper you host, as
    `AGENT_NAME`. Redeploy the helper from the new build instead; the Twilio
    webhook points at your helper, so it does not change.
  </Step>
  <Step title="Call the number, then delete the old agent">
    ```sh
    pipecat cloud agent delete <old-name>
    ```

    ```sh
    pipecat cloud secrets delete <old-name>-secrets
    ```

    Only once a real call to the new agent works. Until then the old one is your
    way back.
  </Step>
</Steps>

## Verifying a phone route

`status` reporting `ready` is not the finish line: see [a phone call is verified
after you deploy](/telephony/overview#point-the-carrier-at-the-deployment).

Two checks come before the call, and both are cheaper than dialling.

`pipecat cloud agent start <agent-name>` opens a session against the deployed
container with no phone leg, so it proves the image boots and `bot()` runs. If this
fails, the carrier was never the problem. It needs a public API key, which is a
separate thing from your CLI login:

```sh
pipecat cloud organizations keys create
pipecat cloud organizations keys use
```

`pipecat cloud agent logs <agent-name>` is where a refused session says why.

<Warning>
  Do not pass `-l DEBUG` to `agent logs`. It filters to that level **only**, which
  hides the `ERROR` line you are looking for.
</Warning>

Then call, and read the duration in the Twilio call log before anything else. A
call Twilio records as `completed` after a second or two was answered by the
platform and dropped, so the fault sits in front of your agent: the service host,
or a container refusing the session. A call that lasts and stays silent is a
different layer, and that is when the logs matter.

## Regions

```sh
pipecat cloud regions list
```

See Pipecat's [regions guide](https://docs.pipecat.ai/pipecat-cloud/guides/regions)
for the current worker regions and matching telephony WebSocket endpoints.

A second region is a second agent, because agent names are globally unique across
regions:

```sh
pipecat cloud secrets set acme-support-pipecat-<region>-secrets --file .env --region <region>
pipecat cloud deploy acme-support-pipecat-<region> --region <region> --secrets acme-support-pipecat-<region>-secrets
```

This setting places the worker only. SLNG speech compute has its own regional
params. See [regional infrastructure](/optimization/regional-infrastructure) before
making a data residency claim.

## Every name in `.env.example` is in the set

On this platform the generated `.env.example` is usually one group, because one thing
reads it: the deployed agent. If your build has a phone route, the carrier
credentials and `PIPECAT_CLOUD_ORGANIZATION` are in that same group and belong in
the same set.

<Warning>
  Every name must be UPPER_SNAKE: an uppercase letter, then only uppercase
  letters, digits, and underscores. Unmute refuses a bad name before it writes
  the project. Pipecat Cloud applies the same rule to names added outside the package.
</Warning>
