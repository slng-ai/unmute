`unmute compile` hands you a project. Deploying it is deploying a normal Python
container. Unmute is not involved at run time and is not a dependency of the
thing you ship.

## What you get, what you provide

| The compiler emits | You provide |
|---|---|
| the Python project and a `Dockerfile` | somewhere to run containers |
| an `.env.example` naming every required variable | the values, from your secret store |
| Compose files for local development | production networking, TLS, DNS, ingress |
| a deploy manifest and a compile report | Redis where the route needs it, scaling, monitoring |
| a `README.md` runbook written for that platform | the decision to press go |

The same image runs locally and in production. Only the start command and the
environment change.

## The runbook is in the build

Every `build/<target>/README.md` is written for that exact build: its required
variables, its platform commands, and its carrier steps if it has a phone
route. It is the authority for that project, because it was generated from the
same package the code was.

Read it before you deploy. This page is the shape; that file has your values.

## Secrets

Generated files and reports carry environment variable **names**, never values.
`.env.example` is the exact list for this build:

```
# Environment for livekit (generated by unmute).
# Copy this file to `.env` and fill in the values. Never commit `.env`.
LIVEKIT_API_KEY=
LIVEKIT_API_SECRET=
LIVEKIT_URL=
OPENAI_API_KEY=
SLNG_API_KEY=
```

That is a browser-only LiveKit build, the shape `unmute init` scaffolds. The
list is per build: a Pipecat build has no `LIVEKIT_*` names, and a build with a
phone route trades them for the carrier's. Read the one your compile wrote.

Both platforms take a secrets file on the first deploy. After that, changing a
value is one command, and it belongs to your secret store, not to the
repository.

<Warning>
  Every variable name must be a valid shell identifier: letters, digits, and
  underscores, never starting with a digit. Platforms export secrets through a
  shell, so a name like `2FACTOR_API_KEY` fails at export and the value is simply
  missing at run time. The compiler refuses one before you get there:

  ```
  connections/twilio_sip.yaml:6: connection "twilio_sip" environment value
    "2FACTOR_SIP_PASSWORD" is not a valid environment variable name: use letters, digits,
    and underscores, and do not start with a digit. A deployment platform exports secrets
    through a shell, so this name would be missing at runtime with no error of its own
  ```
</Warning>

## Sizing

The compile report turns your `capacity:` block into worker and quota numbers:

```
pipecat: sizing workers=10 [unbenchmarked] (2026-07-15 conservative 1 session per worker/GPU; channels=realtime_audio)
```

`[unbenchmarked]` is not decoration. The numbers come from a conservative
assumption, one session per worker, not from a measurement of your agent. Use
them as a starting point and then measure.

## Production concerns, both targets

- **Redis** is needed for LiveKit SIP, a multi-node self-hosted LiveKit Server,
  and Pipecat's `carrier-websocket` route. Pipecat `cloud-websocket` and
  `daily-sip` do not use it.
- **Separate environments.** Keep production and staging apart, and never point
  a development worker at a production server.
- **Logs.** Workers and the Pipecat application log to stdout. Ship those logs,
  and keep the level at `INFO`: debug logging can expose phone numbers.
- **Model providers.** Hosting the orchestrator yourself does not host the
  models. Speech and reasoning calls still go to the providers you bound.

## Hosting the generated container yourself

The managed-cloud pages are the supported deployment path, but the generated
projects are ordinary containers and can run on infrastructure you control.

For LiveKit, the agent worker connects out to LiveKit Server and needs no
inbound port. The server is the public edge: it needs a trusted TLS domain,
public WebRTC ports, and TURN for callers behind strict firewalls. Add LiveKit
SIP beside it for phone calls, with public SIP signalling and RTP. An HTTPS
tunnel is not enough for SIP.

For Pipecat browser calls, expose the bot port over HTTPS and make WebRTC media
reachable. Cross-network calls need STUN or TURN; the generated SmallWebRTC
configuration does not add ICE servers today, so treat that as required work
before a self-hosted browser deployment.

Only Pipecat's `carrier-websocket` phone route runs the full phone agent on
your infrastructure. Give it public HTTPS and WSS on port 443, WebSocket
timeouts longer than the longest call, `UNMUTE_PUBLIC_URL`, and shared Redis.
The `cloud-websocket` route hosts nothing of yours. The `daily-sip` carrier
form emits only a small webhook helper; the deployed agent still exposes no
inbound service.

Scale by active sessions, not HTTP request rate. Keep each long-lived
WebSocket on the replica that accepted it, and give shutdown enough time to
drain the longest call. LiveKit distributes jobs to registered workers; do not
put a load balancer in front of those workers.

## Phone routes

If the target declares a phone route, the generated README carries the carrier
steps: the markup to paste, the trunk to configure, or the number to attach.
Those steps are per route and per carrier, and they are the part no compiler can
do for you.

Route maturity is printed in the compile report:

```
livekit: telephony evidence inbound=provisional docs=https://docs.livekit.io/telephony/start/providers/twilio/ verified=2026-08-12 smoke=false
```

Read `provisional` as: implemented, compiles, and no credentialed test runs in
CI for it. Some routes also have dated live call evidence recorded in the
repository. Decide with that in hand.

## Changing the agent

Edit the package, compile again, deploy again. Never edit `build/`.

```sh
unmute validate ./my-agent
unmute compile ./my-agent
```
