The first deploy is documented per platform. This page is the second one and
every one after: what to run, in what order, and which records outside the
platform still point at the old agent when you are done.

## The rule underneath all of it

`unmute compile` writes `build/<target>/`. Every deploy command reads that
directory and nothing else. So a redeploy is only as current as the last
compile, and the failure is quiet: the platform accepts a stale manifest exactly
as readily as a fresh one.

<Warning>
  **`--target` compiles one target.** `unmute compile ./my-agent --target livekit`
  leaves `build/pipecat/` untouched, however old it is. A package that deploys to
  two platforms needs both compiled, or one of them ships the previous build's
  agent name, region, and secret set.

  ```sh
  unmute compile ./my-agent
  ```

  With no `--target`, every target is compiled. Prefer it before a deploy.
</Warning>

Three things in `build/<target>/` are yours rather than the compiler's, and all
three survive a recompile: `.env`, LiveKit's `livekit*.toml`, and any tool
sample under `samples/`. Everything else is rewritten every time. Never edit
`build/`.

## An ordinary redeploy

No name change: a new prompt, a new model, a new tool.

<Steps>
  <Step title="Compile every target">
    ```sh
    unmute compile ./my-agent
    ```
  </Step>
  <Step title="Deploy">
    | Target | From `build/<target>/` |
    |---|---|
    | `slng` | `unmute deploy ./my-agent` |
    | `pipecat` | `pipecat cloud deploy` |
    | `livekit` | `lk agent deploy` |
  </Step>
  <Step title="Confirm it is serving">
    | Target | Command | What good looks like |
    |---|---|---|
    | `slng` | the deploy prints the outcome | a version was written |
    | `pipecat` | `pipecat cloud agent status <agent-name>` | `ready` |
    | `livekit` | `lk agent list` | the new version under Deployed At |
  </Step>
</Steps>

Nothing else moves. The carrier keeps pointing where it pointed, secrets stay as
they are, and a phone number that worked before works after.

<Note>
  On LiveKit use `lk agent deploy`, never `lk agent create`. `create` registers a
  **second** billable agent and splits dispatch between the two. `deploy` targets
  the agent id in `livekit.toml`, which is why that file is preserved across
  recompiles.
</Note>

## What a redeploy carries, and what it does not

| | `slng` | `pipecat` | `livekit` |
|---|---|---|---|
| Secrets | in the SLNG Vault, unchanged | in the secret set, unchanged | on the agent, unchanged |
| Region | fixed at create | fixed at create | fixed at create, immutable |
| Carrier configuration | unchanged | unchanged | unchanged |

Changing a secret is its own command and does not need a redeploy, though it
does restart the agent:

```sh
lk agent update-secrets --secrets-file .env
```

```sh
pipecat cloud secrets set <agent-name>-secrets --file .env --region <region>
```

By default both **merge**: names you do not pass keep their old values. LiveKit's
`--overwrite` deletes everything not in the file. LiveKit also refuses
`LIVEKIT_URL`, `LIVEKIT_API_KEY` and `LIVEKIT_API_SECRET` — the platform injects
its own, so their absence from `lk agent secrets` is correct.

## Renaming an agent

[`name:`](/reference/agent-yaml#name) joined to the target **is** the deployed
thing's identity, so changing it is not an ordinary redeploy. See
[changing the agent](/deploy/going-live#except-changing-its-name) for what each
platform does with the old deployment.

The part that catches people is not the agent. It is the record that routes
calls to it, which lives somewhere else and keeps naming the old one.

## Why telephony breaks on a rename

A phone call reaches your agent through a record that names the agent as a
**string**. That record is not part of the agent and no deploy updates it. Rename
the agent and the string stops matching, so the number rings and nothing answers
— while the agent itself reports perfectly healthy, because it is: it was simply
never dispatched.

| Route | The record that names the agent | Where it lives |
|---|---|---|
| LiveKit `sip` | SIP dispatch rule | your LiveKit project |
| LiveKit `connector` | the generated bridge's dispatch | wherever you host the bridge |
| Pipecat `cloud-websocket` | `_pipecatCloudServiceHost` in the TwiML Bin | the Twilio Console |
| Pipecat `daily-sip` | `AGENT_NAME` compiled into the helper | wherever you host the helper |

<Warning>
  Between deleting the old routing record and creating the new one, the number is
  unrouted. Do it in a window you can afford, and have the replacement command
  ready before you delete.
</Warning>

### LiveKit `sip`

The dispatch rule names the worker. Deploy first, so a worker is registered
under the new name, then swap the rule.

<Steps>
  <Step title="Deploy and verify the new name">
    ```sh
    lk agent deploy
    ```

    ```sh
    lk agent list
    ```

    Do not continue until Dispatch Name reads the new value. Reading a stale
    listing here is the easiest way to build the next record wrong.
  </Step>
  <Step title="Delete the rule naming the old worker">
    ```sh
    lk sip dispatch list
    ```

    ```sh
    lk sip dispatch delete <SDR_...>
    ```

    Deleting first is required, not tidiness: the setup script **reuses** any
    rule that already names your trunk, which is what makes it safe to run
    twice, and is exactly why it would skip the step you need.
  </Step>
  <Step title="Recreate it">
    ```sh
    bash telephony-setup.sh
    ```

    Run it from `build/livekit/`. It reads `SIP_FROM_NUMBER` from `.env`,
    resolves the inbound trunk that already claims that number, reuses it, and
    creates one rule pointing at the new worker. It needs `lk` and `jq`.
  </Step>
  <Step title="Check the pair matches">
    ```sh
    lk sip dispatch list
    ```

    The Agents column for your trunk must equal the Dispatch Name from step 1.
  </Step>
</Steps>

The inbound trunk is untouched by a rename. It claims a number, and it says
nothing about which agent answers.

### Pipecat `cloud-websocket`

The agent name is half of the service host your TwiML carries, so the Bin has to
change with it.

<Steps>
  <Step title="Create the secret set under the new name">
    ```sh
    pipecat cloud secrets set <new-name>-secrets --file .env --region <region>
    ```

    Before the deploy, not after: the manifest already references the set by
    name and a deploy cannot start without it. A rename means a new agent, and a
    new agent has no secrets.
  </Step>
  <Step title="Deploy and wait for ready">
    ```sh
    pipecat cloud deploy
    ```

    ```sh
    pipecat cloud agent status <new-name>
    ```
  </Step>
  <Step title="Repoint the TwiML Bin">
    In the Twilio Console, edit the Bin for this number:

    ```xml
    <Parameter name="_pipecatCloudServiceHost" value="<new-name>.<your-organization>"/>
    ```

    The organization is the **slug** from `pipecat cloud organizations list`, the
    one shaped like `three-random-words-12345`, never the display name. Until
    this is saved, calls keep reaching the old agent, which is still running.
  </Step>
  <Step title="Call the number, then remove the old agent">
    ```sh
    pipecat cloud agent delete <old-name>
    ```

    ```sh
    pipecat cloud secrets delete <old-name>-secrets
    ```

    Only after a real call to the new one works. The old agent bills until it is
    deleted.
  </Step>
</Steps>

### Pipecat `daily-sip`

The helper you host has `AGENT_NAME` compiled into it and calls
`https://api.pipecat.daily.co/v1/public/<agent-name>/start`. Recompile, deploy
the agent, then **redeploy the helper** from the new build. The Twilio webhook
URL does not change, because it points at your helper rather than at the agent.

### `slng`

No carrier record to fix: SLNG owns the phone side. What a rename leaves behind
is the **agent id**. Anything holding the old one — a web session, a dashboard
attachment, a saved integration — still addresses the old agent, which is still
there. Take the new id from the push output, or find it with:

```sh
voiceai agents list
```

## Verifying a redeploy actually took

Deploying and answering are different things. Check both.

<Steps>
  <Step title="The platform is serving the new version">
    `lk agent list` shows a new Deployed At. `pipecat cloud agent status` reads
    `ready`. An `slng` push prints the version it wrote.
  </Step>
  <Step title="The routing record names what is deployed">
    Compare the two strings by eye. On LiveKit that is the Agents column against
    Dispatch Name; on Pipecat it is the Bin's service host against the agent
    name.
  </Step>
  <Step title="Call the number">
    Telephony is verified on a deployed agent against a real carrier. No local
    step substitutes for it — `unmute dev` covers prompt, tools and models in the
    browser and stops where the phone leg starts.
  </Step>
</Steps>

If it rings and nothing answers, read the logs before changing anything. An
**empty** agent log means the call never reached the agent, which points at the
routing record rather than at the agent:

```sh
lk agent logs
```

```sh
pipecat cloud agent logs <agent-name>
```
