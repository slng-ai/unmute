SLNG hosts the agent, so there is no project to run and no image to build. One
command takes a package to a live agent, with no mirror and no pull to run
first:

```sh
export SLNG_API_KEY=...
unmute deploy examples/hotel-concierge
```

That validates the package, compiles it, resolves every tool reference
against your organisation's published tools, checks what it resolved, and
pushes. The agent is written only after its required checks pass. A real deploy
may first refresh MCP discovery or fill a Vault entry with your consent; its
report records those changes even if a later check fails. A dry run does neither.

<Warning>
  A real deploy needs a `voiceai` release that supports a checked, resolved
  push; this flow was verified with `voiceai 0.1.18`. `unmute deploy` checks for that support before writing anything: an
  older `voiceai` is refused with upgrade guidance, naming the missing
  capability and the install command, rather than falling back to an
  unchecked push that resolves and attaches whatever is newest without having
  checked it. `unmute validate` and `unmute compile` are unaffected: both work
  offline against any installed `voiceai`, because neither one reads your
  account at all.
</Warning>

## What works today

<Warning>
  **SLNG creates no tool from your package.** A `local:` or `webhook:` block
  is refused here: reference a tool your organisation already has with
  `slng:` instead, or compile the package to `pipecat` or `livekit`, where
  your own handler or endpoint runs.
</Warning>

A builtin names a capability SLNG already owns, so the push has nothing to
create first. In a package that is a `builtin:` block naming `id: end_call`,
or `id: send_sms` with the sender pinned by `inject: from_number`. The other
curated capabilities, voicemail detection, current date and time, and the
caller's phone number, are attached to the agent in the SLNG dashboard rather
than written in the package. A value the model records during the call, such
as a number the caller confirms, is a variable with `source: conversation`,
which becomes one of the agent's runtime variables and comes back on the call
record.

[`hotel-concierge`](https://github.com/slng-ai/unmute/tree/main/examples/hotel-concierge)
is the working example and the shape to copy: two hosted tools by name, two
named MCP tools, a builtin, template variables with defaults in the greeting
and the prompt, an injected argument, a tool announcement and a model fallback,
with no required session inputs. If your agent needs a
tool SLNG does not host yet,
create it in the SLNG dashboard and reference it with `slng:`
(see [Hosted tools](/build/tools/hosted)), or compile the package to
`pipecat` or `livekit` instead, where the handler runs in the project you
host.

## Before you start

<Steps>
  <Step title="Install the voiceai CLI">
    SLNG hosts the agent, and `voiceai` is the tool that owns your account and
    the push. `unmute deploy` runs it for you, so it has to be on your PATH.

    ```sh
    brew install slng-ai/tap/voiceai
    ```

    Unmute's compiler opens no connection to SLNG at any point, at validate time
    or compile time. It writes files and stops.
  </Step>
  <Step title="Get an API key">
    One SLNG key serves every SLNG role, so this is the same key a generated
    livekit or pipecat project reads at run time to reach SLNG models.

    ```sh
    export SLNG_API_KEY=...
    ```

    Get one at [app.slng.ai/api-keys](https://app.slng.ai/api-keys).

    `unmute deploy` reads `SLNG_API_KEY`, then `VOICEAI_API_KEY`, then whatever
    profile `voiceai login` stored. It also reads a package's `.env` and
    `.env.local`, the same files `unmute dev` reads, so a key on a line there
    needs no export.

    <Warning>
      An exported key and a stored `voiceai` profile can belong to **different
      organisations**. `unmute deploy` prints the organisation it resolved on
      every run. Read that line before you read anything else.
    </Warning>
  </Step>
</Steps>

## The walkthrough

Follow these against `examples/hotel-concierge` from a clone of the repository.
It references two hosted tools and one MCP server, all three by name, with no
mirror committed anywhere in the package.

Those names belong to the organisation this example was written for. In a new
organisation, publish the two tools and register the MCP server with its selected
tools and credentials, or replace the references with your own. Run
`unmute resources` to inspect your catalogue. Validation is offline and cannot
prove those resources exist in your account.

<Steps>
  <Step title="Validate">
    ```sh
    unmute validate examples/hotel-concierge
    ```

    ```text
    ✓ slng (slng)
    ```

    This is local and needs no key. It checks each `slng:` reference for its
    own shape, never for whether the name exists on the platform: that check,
    like the tool sandbox behind it, belongs to deployment.
  </Step>

  <Step title="Compile">
    ```sh
    unmute compile examples/hotel-concierge --target slng
    ```

    ```text
    examples/hotel-concierge/build/slng/agent.json
    examples/hotel-concierge/build/slng/README.md
    examples/hotel-concierge/build/slng/compile-report.json
    ```

    Also local, also no key. `agent.json` carries each tool by name only.
    `compile-report.json` names, under `deferred_checks`, exactly what this
    step could not establish: that the organisation still publishes each
    name, that an injected argument fits its published parameters, and which
    Vault entries it needs. `unmute deploy` is what completes those three.
  </Step>

  <Step title="Preview the push">
    ```sh
    unmute deploy examples/hotel-concierge --dry-run
    ```

    This is the step that needs the `voiceai` release described above. With
    one installed, a clean preview names the organisation it resolved,
    resolves `hotel_info`, `search_places_text` and `end_call` against it,
    checks their published contracts and reports the version it would attach
    for each reference, without writing anything:

    ```text
    slng: hotel_info v<n>
    slng: search_places_text v<n>
    slng: dry run, nothing was created or changed
    ```

    A reference the agent already has reads `v<n>, from v<m>`, and one it does
    not reads `v<n>, new`. The deploy step below prints a different line, and
    the difference is the point: a preview says what it would attach and a
    deploy says what it did.

    On a package that already has a live agent, the same run also names what
    a replacement would remove: a reference the package no longer names, or a
    setting the agent has now that the package does not declare, such as a
    description typed in the dashboard or a `call_start` trigger somebody
    added there. Full shape of the preview, including what it says about a
    changed published description or schema, is at
    [`unmute deploy`](/reference/cli/deploy).
  </Step>

  <Step title="Deploy">
    ```sh
    unmute deploy examples/hotel-concierge
    ```

    A successful run prints the version it attached for every reference and
    the agent id:

    ```text
    slng: attached hotel_info v<n>
    slng: attached search_places_text v<n>
    slng: attached end_call v<n>
    slng: attached firecrawl-mcp-2 firecrawl_scrape
    slng: attached firecrawl-mcp-2 firecrawl_search
    slng: agent created <agent_id>
    slng: deployed. Talk to it: voiceai agents web-sessions create <agent_id> --file session.json
    ```

    An MCP selection carries no version, because a server tool has none: what
    was checked for it is the schema hash SLNG's own snapshot recorded, and
    `deploy-report.json` carries that.

    `v<n>` is the latest published version this run resolved and checked, not
    a version the package pinned: run it again after somebody publishes a new
    one and the next deploy resolves that one instead. Keep the agent id.
    `voiceai agents list` finds it again, because unmute stores no id, writes
    no lockfile, and keeps no local state about your account.
  </Step>

  <Step title="Talk to it">
    There is no `unmute dev` for this target. `dev` runs a generated project
    locally and this target generates none. Open the deployed agent in the
    SLNG dashboard, click **Test**, choose **Web session**, and allow microphone
    access. Fill any required inputs shown by the test panel; this example has
    none. See [SLNG's test panel guide](https://docs.slng.ai/dashboard/agent-infra#test-your-agent).

    To connect your own LiveKit client instead, create a session with the CLI:

    ```sh
    export VOICEAI_API_KEY="$SLNG_API_KEY"
    cat > session.json <<'JSON'
    {"arguments": {}, "participant_name": "you"}
    JSON
    voiceai agents web-sessions create <agent_id> --file session.json
    ```

    ```json
    {
      "call_id": "3ee08739-a329-49ee-a3a0-542b8ee9f8de",
      "room_name": "agent-3ee08739-a329-49ee-a3a0-542b8ee9f8de",
      "livekit_dispatch_id": "AD_6bSrcp7fowVe",
      "livekit_url": "wss://slng-atlas-6sw2n5o2.livekit.cloud",
      "livekit_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9…",
      "max_session_seconds": 300
    }
    ```

    This command returns connection details and requests a worker; it does not
    open a browser or microphone. Connect a LiveKit client with `livekit_url`
    and `livekit_token` to talk. A `livekit_dispatch_id` alone does not prove
    that the worker joined or a conversation happened. Setting `VOICEAI_API_KEY`
    above keeps this standalone command in the same account as your deploy.

    Supply the agent id and the request body using `--file`. This example
    needs no session arguments; the model supplies tool arguments from the
    caller's request.

    Other packages can use `arguments` to supply declared variables for one
    web session. Inbound phone calls do not supply that payload. A required
    injected input therefore needs a valid default before an inbound trunk
    can be attached, or the tool must leave that argument to the model.

    Ask for the status of order A-1001, listen for the tool's announcement,
    then say goodbye. Read the resulting call using the returned `call_id`:

    ```sh
    voiceai agents calls get <agent_id> <call_id> --json
    ```

    The call record shows whether the tool ran and what it returned.
  </Step>
</Steps>

## Why the package is shorter here

A slng package is smaller than the same agent written for pipecat or livekit,
and it is worth being clear about what is missing: not capability, but the parts
you would otherwise have to stand up yourself.

| On a code target you author | On slng |
|---|---|
| a Python project, a `Dockerfile`, an image to build and host | nothing; SLNG runs the agent |
| worker counts, concurrency, scaling | SLNG's, already provisioned |
| a VAD, a turn model, endpointing windows | SLNG's turn taking |
| the event loop that wires STT to LLM to TTS | SLNG's pipeline |
| where each provider is called from | one region, chosen per call |

So on slng you author **intent**, the prompt, models, tools, greeting and
variables, and the layer under it is already running. That layer is the trade:
you give up owning the runtime, and you get a runtime that is already deployed
in-region, already warm, with STT, LLM, TTS and the tool sandbox one network hop
apart instead of one internet apart.

That is also why four `targets.yaml` keys are **refused by name** on this target
rather than ignored: `version`, `pins`, `sdk_language` and `connection` each
describe a generated project, and there is none. Other `agent.yaml` features go
the same way, including `turn:` and `tracing:`. See
[what a slng package may not ask for](/targets/slng#what-a-slng-package-may-not-ask-for)
for the complete list. `unmute validate` names each one and says what owns it
instead, so a setting never disappears quietly.

## Every later deploy

`unmute deploy` validates, compiles and pushes in one command, so there is no
stale build to worry about here as there is on the other two targets:

```sh
unmute deploy ./my-agent
```

A push **replaces**. Updating an agent replaces it with what the package
declares, so a field that differs from the live agent is overwritten and a tool
reference the package no longer names is detached. `--dry-run` names both before
anything happens. A push that changes nothing writes no version and does not
relabel the previous one, so re-running a deploy is safe and cheap.

An ordinary redeploy moves nothing else. The region is fixed at create and the
agent id does not change, so a web session or a dashboard attachment holding
that id keeps working.

SLNG itself never goes stale between deploys: every run resolves the latest
published version of each hosted tool fresh, so there is nothing local to
fall behind. What can go out of date is a **mirror**, if your package has
one, because it exists only for a `pipecat` or `livekit` build of the same
package. Somebody edits the tool in the SLNG dashboard, and the committed
mirror is now the old definition, so it is worth checking:

```sh
unmute pull ./my-agent --check
```

It writes nothing and exits 1 on drift, which is what makes it usable in CI.
`unmute pull` then brings the mirror forward. A slng-only package, such as
`examples/hotel-concierge`, carries no mirror and has nothing here to check.

## Renaming the agent

A push resolves the agent by name, so a new name pushes a **second** agent and
leaves the first one exactly where it was. What a rename strands is the **agent
id**. Anything holding the old one still addresses the old agent: a saved web
session, a dashboard attachment, an integration.

Take the new id from the push output, or find it again:

```sh
voiceai agents list
```

Then delete the old agent, or point those places at the new id.

## When it refuses

Problems name what to fix. The agent is written only after its required checks
pass; a real deploy may already have refreshed MCP discovery or filled a Vault
entry with your consent. Inspect `deploy-report.json` for completed changes.

| It says | What to do |
|---|---|
| `vault missing` | create each name in [the vault](https://app.slng.ai/vault/secrets). A name that exists as a *variable* does not count. |
| `hosted tool ... this organisation has no tool of this name` | the package names a tool your organisation cannot see. Rename the reference, or create the tool in the dashboard. Unmute creates none. |
| `hosted tool ... could not be listed` / `published contract was not checked` | this run could not read the organisation's tools, or the one published version it needed. Nothing is attached unverified: fix what blocked the read (often a credential scope) and run again. |
| `--require-resolved` in the message, naming `brew install` | the installed `voiceai` does not support a checked, resolved push. See the warning near the top of this page. |
| `agent ambiguous` | two agents share the package's name. Pass `--agent-id`. |

These problems block the agent push. A dry run makes no remote changes.
A `slng:` tool's mirror is never checked here, because `unmute
deploy` compiles only the slng target and that target reads no mirror; a
`no mirror of it is committed` or `does not match the hash` refusal is
[a `livekit` or `pipecat` compile's](/build/tools/hosted), not this command's.

## Receive phone calls

Phone setup has two separate parts:

1. Configure an inbound connection in [SLNG Telephony](https://docs.slng.ai/dashboard/telephony).
   Use the guided Twilio setup or your provider's SIP setup to route the number
   to SLNG's inbound destination. A number still pointing at Twilio Dev Phone,
   an old webhook or another application will not reach this agent.
2. Run `unmute deploy` and select that free inbound trunk when prompted, or
   assign it in the agent editor's **Telephony** tab. Choosing `0` leaves it
   unattached. The CLI attaches an existing connection; it does not rewrite
   your carrier's routing.

An `attached` or `usable` result describes SLNG account state. It is not proof
of a completed carrier call. Call the number, then check for a new call:

```sh
export VOICEAI_API_KEY="$SLNG_API_KEY"
voiceai agents calls list <agent_id> --json
voiceai agents calls get <agent_id> <call_id> --json
```

No new SLNG call means you should check carrier routing and SIP delivery first.
A recorded call with an error gives you the next component to investigate.
For outbound calls, assign an outbound connection separately; an inbound
attachment does not enable outbound calls.

## When the agent answers with silence

A model can pass every check at create time and still fail on the call. The
create body is validated against what your organisation is *allowed* to use.
Whether the provider behind it answers is a different question, and nothing in
`build/` can tell you.

The call record is where it shows up:

```sh
voiceai agents calls list <agent_id> --json
```

`status` is `in_progress` while the agent is up and waiting. Once a call ends,
read `call_end_reason`. A line like

```text
terminal failure: component=llm reason=hard_fail
```

names the component to investigate: `llm`, `stt` or `tts`. Read its error and
call details before changing a binding; a short duration alone does not identify
the cause. If no new SLNG call appears, inspect the carrier's logs and incoming
number routing first: the call may have failed before the agent started.

A model SLNG does not have enabled for your organisation is rejected at push
with `AGENT_MODEL_UNAVAILABLE`, naming the field. Unmute cannot check this: the
list is per-organisation, and model strings are forwarded exactly as written.
Three things cause it. The model is not enabled for agents, it is your own model
and SLNG's router is off, or it is not served in the region and language this
agent asked for. `deployment_region: any` avoids the third by letting SLNG route
each call, which is worth trying before you pin one.
