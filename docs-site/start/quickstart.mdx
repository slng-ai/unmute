This page takes you from nothing to an agent you can talk to. It uses only
`unmute init` and `unmute dev`.

You need the `unmute` binary ([installation](/start/installation)), Docker
running, and two API keys: one for the model that thinks (`OPENAI_API_KEY`) and
one for the SLNG speech models the scaffold uses (`SLNG_API_KEY`).

<Steps>
  <Step title="Scaffold a package">
    ```sh
    unmute init my-agent
    ```

    ```text
    created my-agent/agent.yaml
    created my-agent/.env.example
    created my-agent/.gitignore
    created my-agent/instructions.md
    created my-agent/targets.yaml
    created my-agent/tools/end_call.yaml
    ```

    Six files. `agent.yaml` is the agent, `instructions.md` is its prompt,
    `targets.yaml` picks the runtime, `tools/end_call.yaml` gives it a way to
    hang up, `.env.example` lists the keys to fill in, and `.gitignore` keeps
    your filled-in `.env` and the `build/` output out of git.

    The scaffold binds **SLNG speech models by design**, for listening and for
    speaking, which is why one `SLNG_API_KEY` covers both. See
    [SLNG Execution Layer](/models/optimization) for what runs behind them. It picks
    **LiveKit Agents** as the runtime, which is what `targets.yaml` says and
    what you will see named in the output below.

    Now move into the package, because everything after this runs inside it:

    ```sh
    cd my-agent
    ```

    <Tip>
      Run `unmute init` with no name in a terminal and you get an interactive
      console that asks for the name, the models, and the target instead.
    </Tip>
  </Step>

  <Step title="Add your keys">
    ```sh
    cp .env.example .env
    ```

    Open `.env` and fill in `OPENAI_API_KEY` and `SLNG_API_KEY`. Those two are
    the ones you supply, and they are the same two `agent.yaml` lists under
    `secrets:`.

    The file lists three more names, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`,
    and `LIVEKIT_URL`. They point at a LiveKit server. `unmute dev` runs one
    for you locally and fills them in itself, so leave them empty until you
    deploy. That split is deliberate: `secrets:` is what your agent needs, and
    the LiveKit connection belongs to wherever the agent happens to run.

    `unmute dev` reads `.env` from the directory you run it in, then from the
    package directory, so a package can override a shared key.
  </Step>

  <Step title="Check the package">
    ```sh
    unmute validate
    ```

    ```text
    ✓ livekit (livekit)

    Warnings:
      livekit: LiveKit turn placement is a preference
    ```

    No argument, because you are standing in the package. `validate`,
    `compile`, and `dev` all take the package directory as an optional
    argument: leave it out and they use the current directory, name one and
    that wins. So `unmute validate my-agent` from the parent directory prints
    the same thing.

    One line per target, and exit code 0. The warning is a real difference
    worth reading, not a failure. If a field is wrong, this is where you find
    out, with the file and the line.
  </Step>

  <Step title="Talk to it">
    ```sh
    unmute dev
    ```

    ```text
    compiled build/livekit
    building and starting the container...

      ▸ http://localhost:8765/?agent=livekit
        ctrl-c to stop  ·  logs: build/livekit/dev.log
    ```

    `unmute dev` compiles the package, builds the container the deploy would
    use, starts it, and serves a small web page against it. Your browser opens
    at that URL. Allow the microphone, press the button, and say hello. The
    agent speaks first, because `agent.yaml` says so:

    ```yaml
    conversation:
      greeting:
        speaks_first: agent
        text: "Hi there, I'm listening. What can I help you with?"
    ```

    Press ctrl-c when you are done. The container is stopped and removed for
    you.
  </Step>
</Steps>

## What just happened

- `unmute init` wrote a package bound to SLNG speech models and an OpenAI
  reasoning model, targeting LiveKit Agents.
- `unmute dev` compiled that package into `build/livekit/`, a normal Python
  project with a Dockerfile.
- The container it ran is the same image a deployment would run. Local testing
  is not a separate code path.

The first run is slow because Docker builds the image. Later runs reuse it.

## If something goes wrong

<AccordionGroup>
  <Accordion title="docker compose is required to run unmute dev">
    Docker is not running, or Compose is missing. Start Docker and run the
    command again. Local development runs the agent in Docker Compose, so
    there is no way to talk to it without Docker.
  </Accordion>
  <Accordion title="Missing required environment variables">
    The container starts, checks the keys the agent needs, and stops with the
    names it did not find. Fill them in `.env` and run again.
  </Accordion>
  <Accordion title="The browser page opens but nothing speaks">
    Look at `build/livekit/dev.log`. It has the container's whole output. Add
    `--verbose` to follow the same log in your terminal while it runs.
  </Accordion>
  <Accordion title="Port already in use">
    Another dev run is holding the port. Either stop it, or pass different
    ports: `--port 8790` for the web page and `--bot-port 7890` for the agent
    container.
  </Accordion>
</AccordionGroup>
