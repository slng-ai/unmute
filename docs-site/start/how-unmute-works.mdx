---
title: "How Unmute works"
description: "The four stages between your package and the Python project you deploy."
---

Unmute is a compiler. It reads your package, resolves it against one target,
and writes a project. Nothing of Unmute is left in the project it writes.

## The four stages

<Steps>
  <Step title="Load">
    Unmute reads [`agent.yaml`](/reference/agent-yaml),
    [`targets.yaml`](/reference/targets-yaml), your tool files, your
    [connections](/reference/connections-yaml), your prompts, and your local
    Python handlers. YAML decoding is strict: an unknown field is an error, not
    a shrug. Errors carry the file and the line. The configuration pages also
    list every [variable](/reference/variables) and [secret](/reference/secrets)
    field.
  </Step>
  <Step title="Build">
    Names get resolved into one internal description of the agent. Model names
    point at model definitions, controls point at tasks or agents, per target
    overrides get applied, and a telephony route is picked from what the target
    declares. This description knows nothing about Pipecat or LiveKit.
  </Step>
  <Step title="Validate">
    The description is checked against the capability table of each target you
    selected. Something a target cannot do is an error before anything is
    written. Something it does differently, while keeping your contract, is a
    warning.
  </Step>
  <Step title="Generate">
    One driver turns the description into files for one target. `validate` and
    `compile` run the same first three stages, so a package that validates
    cannot surprise you at compile time.
  </Step>
</Steps>

## What you get

`unmute compile` writes one directory per target under `build/`. Name the
package, as in `unmute compile my-agent`, or leave the argument out and it
compiles the directory you are standing in:

<CodeGroup>
```text Pipecat
build/pipecat/
├── bot.py              # the agent
├── tools/              # your local handlers, copied
├── pyproject.toml      # pinned dependencies
├── Dockerfile
├── compose.dev.yaml
├── pcc-deploy.toml
├── .env.example        # exactly the variables you supply
├── README.md           # the runbook for this build
└── compile-report.json
```

```text LiveKit Agents
build/livekit/
├── agent.py            # the agent
├── tools/              # your local handlers, copied
├── pyproject.toml      # pinned dependencies
├── Dockerfile
├── compose.dev.yaml
├── .env.example        # exactly the variables you supply
├── README.md           # the runbook for this build
└── compile-report.json
```
</CodeGroup>

That project is a normal Python project. You can read it, run it, and deploy
it. It does not import Unmute.

<Warning>
  Treat `build/` as output. Edit the package and compile again. Anything you
  change inside `build/` is overwritten on the next compile.
</Warning>

## The compile report

`unmute compile` writes what it decided to `build/<target>/compile-report.json`,
next to the project it describes. The terminal itself only shows which files
were written; the report is where you read the detail. Three kinds of entry
matter.

**Model bindings.** Unmute passes your model and voice strings through to the
provider without checking them, and the report names the provider and model
for every role, marked as forwarded and not validated.

**Sizing.** Unmute turns your `capacity:` block into worker and quota numbers.
Each one carries an `unbenchmarked` status and the date of the assumption it
came from, so you know it is a starting point.

**Telephony evidence.** A phone route's entry says how well each capability is
proven, with the vendor document it was checked against.

See [the compile report](/reference/cli/compile#the-report) for the exact
shape of each field.

## Warnings never fail quietly

Warnings go to standard error and the command still exits 0. Errors exit 1.
A warning is a real difference worth reading, for example:

```text
warning: livekit: LiveKit runs tool executions to completion; a per-tool interruption preference is not enforced
```
