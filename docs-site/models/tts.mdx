The `speak` role turns the agent's words into audio. You bind it once in
`agent.yaml`, and this role usually takes a voice as well as a model:

```yaml agent.yaml
models:
  speak:
    voice:
      provider: slng
      model: "deepgram/aura:2"
      voice: "aura-2-thalia-en"
```

A scaffolded package binds SLNG here by design, so one `SLNG_API_KEY` covers
listening and speaking. See the [SLNG Execution Layer](/optimization/execution-layer).
To keep synthesis compute in a world part or exact region, see
[regional infrastructure](/optimization/regional-infrastructure).

<Info>
  Model ids and voice ids are forwarded to the vendor exactly as you write them.
  Unmute keeps no allowlist, so a typo surfaces as a provider error at run time.
</Info>

## The SLNG models the scaffold and examples use

| Where | `model:` | `voice:` |
|---|---|---|
| `unmute init`, and every example except `slng-support` | `deepgram/aura:2` | `aura-2-thalia-en` |
| `slng-support`, which compiles to the `slng` target | `slng/deepgram/aura:2-en` | `aura-2-thalia-en` |

The `slng/` prefix picks a model SLNG hosts itself, and an id without it reaches
the same vendor model through SLNG as a proxy. For **listening** the two differ
in speed by enough to matter, and [Speech to text](/models/stt) explains the
gap. For speaking nobody has measured them against each other; the scaffold
takes the proxied route here to match the transcriber, not because it is known
to be faster.

Those are the only exact ids the docs name, because they are the ones the examples
run. The full SLNG catalog is at
[docs.slng.ai/models](https://docs.slng.ai/models); any id from there goes in
`model:` as written, for example `slng/cartesia/sonic-3` with a voice id of its own.

This list is closed, and closed harder than Pipecat's: LiveKit's OpenAI plugin
carries no language slot for speech, so there is no custom-endpoint fallback for
this role at all.

## The difference between the two

Pipecat has `openai`, LiveKit has `gemini`. Everything else matches.

A `speak` entry cannot carry `fallback:`. That field is legal only on `think`
and `listen` models; see [Reasoning model](/models/llm#fallback).
