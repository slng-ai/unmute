Regional voice agents have more than one place to configure. This complete
`agent.yaml` keeps STT and TTS in Europe:

```yaml agent.yaml
version: 1
name: regional-assistant
entry_agent: regional_assistant

secrets:
  - OPENAI_API_KEY
  - SLNG_API_KEY

models:
  think:
    reasoning:
      provider: openai
      model: gpt-5.6-terra
      params:
        reasoning_effort: "none"
  listen:
    transcriber:
      provider: slng
      model: "slng/deepgram/nova:3-multi"
      params:
        world_part_override: eu
  speak:
    voice:
      provider: slng
      model: "slng/deepgram/aura:2-en"
      voice: "aura-2-thalia-en"
      params:
        world_part_override: eu
        region_override: eu-north-1
  turn:
    detector:
      provider: local
      model: silero

agents:
  regional_assistant:
    instructions: instructions.md
    model: reasoning
    voice: voice

conversation:
  greeting:
    speaks_first: agent
    text: "Hello. How can I help?"

channels:
  web:
    kind: realtime_audio

capacity:
  peak_sessions: 1
  max_sessions: 2
  avg_session_duration: 5m
```

The listening model may use a model-supported region in the `eu` world part.
The speaking model is pinned to `eu-north-1`. It also shows both settings on
purpose: when both are set, `region_override` wins. `world_part_override` is
ignored; it is not a fallback.

Unmute passes these `params` to the SLNG STT and TTS integrations on both
LiveKit and Pipecat. They control where SLNG runs speech inference, not where
the agent worker runs.

Then place the generated workers in `targets.yaml`:

```yaml targets.yaml
targets:
  livekit:
    provider: livekit
    version: "1.6.10"
    sdk_language: python
    deployment_region: eu-central
    pins:
      livekit-plugins-slng: "1.6.7"
    models:
      detector:
        provider: livekit
        model: turn-detector-mini

  pipecat:
    provider: pipecat
    version: "1.8.0"
    deployment_region: eu-central
```

Unmute already installs `livekit-plugins-slng` at its catalog floor, `1.6.1` or
newer, and `pipecat-slng` at `0.5.1` or newer, both of which carry regional
overrides. The LiveKit `pins` entry above is optional: an escape hatch to
require a newer patch than the floor when you need one. Pipecat has no
equivalent field; its floor is fixed by Unmute directly. See the official
[LiveKit SLNG plugin reference](https://docs.livekit.io/reference/python/livekit/plugins/slng/index.html)
and [Pipecat SLNG source](https://github.com/slng-ai/pipecat-slng).

## Why regional alignment matters

A voice turn crosses several network boundaries: the caller enters through a
media or telephony edge, the worker sends audio to STT, the worker calls the LLM
and tools, and the result goes to TTS before audio returns to the caller. Every
long-distance boundary adds network travel to the turn.

Place the media or telephony ingress, worker, and speech models near the users
and near one another when the platforms offer matching regions. Apply the same
review to the LLM, tools, tracing, storage, and other remote services. This
reduces network latency and avoids sending voice data through regions you did
not intend.

[Coval's voice latency guide](https://www.coval.ai/blog/how-to-measure-voice-ai-latency-the-complete-guide/)
explains how network hops add to a cascaded voice pipeline.
[FutureAGI's Pipecat latency guide](https://futureagi.com/blog/how-to-optimize-pipecat-latency-2026/)
also recommends regional routing for the voice gateway, STT, and TTS.

## Separate regional layers

These settings solve different parts of the call:

| Location | What runs there | How you choose it |
|---|---|---|
| media or telephony ingress | the first platform edge that receives the caller's audio | LiveKit realtime region pinning; Pipecat derives its regional WebSocket endpoint from `deployment_region`; carrier settings are separate |
| worker region | the generated LiveKit or Pipecat process | `deployment_region` in `targets.yaml` |
| speech region | SLNG speech to text and text to speech compute | `world_part_override` or `region_override` under each model's `params` |
| reasoning region | the [SLNG Context Router](/optimization/context-router), when the `think` role uses it | `world_part_override` under the think model's `params`, from the router's own set: `eu`, `us`, `india`, `indonesia` |

The reasoning row shares a key with the speech row and not its values. SLNG
speech serves the world parts `na`, `eu` and `ap`; the router serves `eu`, `us`,
`india` and `indonesia`. One word covers all three SLNG roles because it answers
the same question, and each role accepts the set it actually serves, so copying
`na` from the speech table into a think binding is a compile error. The reasoning
row applies only to a think binding whose provider is `slng`; a direct provider
keeps its own regional settings.

Setting one row does not set the others. The reasoning model, tools, tracing,
carrier, database, and any other service also keep their own regional settings.
Review each service before making a data residency claim. LiveKit documents
[realtime region pinning](https://docs.livekit.io/deploy/admin/regions/region-pinning/),
[realtime region groups](https://docs.livekit.io/deploy/admin/regions/endpoints/#region-groups),
and [agent deployment regions](https://docs.livekit.io/deploy/admin/regions/agent-deployment/)
separately. Pipecat documents its worker regions and matching regional
WebSocket endpoints in its [regions guide](https://docs.pipecat.ai/pipecat-cloud/guides/regions).

## World part, exact region, or both

Use a world part when you want a regional boundary with room for SLNG to choose
between eligible regions for capacity:

```yaml
params:
  world_part_override: eu
```

Use an exact region when the speech request must stay pinned to one region:

```yaml
params:
  region_override: eu-north-1
```

Use one exact string when the same package targets LiveKit and Pipecat. The
LiveKit SLNG plugin also accepts an ordered list of exact model regions:

```yaml
params:
  region_override:
    - ap-south-1
    - ap-southeast-2
```

Pipecat accepts one exact SLNG model region. This model-region list is separate
from LiveKit's `deployment_region` list for agent workers.

You may write both, but the exact region always wins:

```yaml
params:
  world_part_override: eu
  region_override: eu-north-1
```

The last form does not provide a fallback. With `world_part_override` alone,
SLNG may spill between mapped, model-supported regions for capacity, but not
outside the selected world part. Choose `region_override` for hard regional
isolation.

## Regional alignment options

The codes below are not interchangeable. Each row groups the closest or
same-world-part choices. Use each platform's location list to choose the
shortest path for your users. A row does not promise the same data center or
create a residency guarantee.

| Geography | SLNG world part | SLNG exact model region | LiveKit worker | LiveKit realtime group | Pipecat worker / WebSocket |
|---|---|---|---|---|---|
| North America | `na` | `us-east-1` | `us-east` | `us` | `us-east` or `us-west` |
| Europe | `eu` | `eu-north-1` | `eu-central` | `eu` | `eu-central` |
| India | `ap` | `ap-south-1`, `asia-south1` | `ap-south` | `india` | `ap-south` |
| Southeast Asia | `ap` | `asia-southeast2` | | `asia` | |
| Australia | `ap` | `ap-southeast-2`, `australia-southeast1` | | `aus` | |

A blank cell means the platform does not currently advertise a worker option
near that SLNG model region. Availability is model-specific and can change. Check
the official [SLNG region override guide](https://docs.slng.ai/region-override),
[SLNG models by region](https://docs.slng.ai/models/by-region),
[LiveKit agent regions](https://docs.livekit.io/deploy/admin/regions/agent-deployment/),
[LiveKit realtime region groups](https://docs.livekit.io/deploy/admin/regions/endpoints/#region-groups),
and [Pipecat regions](https://docs.pipecat.ai/pipecat-cloud/guides/regions)
before deployment.

The table intentionally excludes LiveKit SIP pinning and carrier-specific
telephony regions because they use separate codes. They still affect latency:
place the telephony ingress near the caller and align it with the media and
worker regions. Pipecat's regional WebSocket endpoint should use the same region
as its worker.

### Other model providers

SLNG uses `world_part_override` and `region_override`, but these names are not
universal. Other STT, TTS, and LLM providers may offer a regional endpoint,
project location, deployment, or provider-specific parameter. Not every
provider or model supports regional pinning. Check that provider's documentation
and configure every model separately; choosing a worker region does not pin the
models it calls.

## One worker region or several

Pipecat accepts one `deployment_region` per target. A second Pipecat region is a
second target and agent name.

LiveKit accepts either one region as a scalar, as in the full example above, or
several regions as a list:

```yaml targets.yaml
targets:
  livekit:
    provider: livekit
    version: "1.6.10"
    sdk_language: python
    deployment_region:
      - eu-central
      - us-east
```

Unmute emits one LiveKit create command per listed region. The deployments keep
one dispatch name, so LiveKit may send a caller to another declared region when
the nearest deployment is at capacity. This is useful for latency and capacity
spill. For hard worker-region isolation, use separate agent names and explicit
dispatch instead of one multi-region target.

Region names use each platform's own vocabulary and Unmute forwards them as
written. A worker region such as `eu-central` and an SLNG speech region such as
`eu-north-1` are different settings and do not need to use the same name.
