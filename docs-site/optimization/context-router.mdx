---
title: "Context Router"
description: "The optimization layer for thinking: repeated turns come back from a cache instead of calling your model."
---

The SLNG Context Router is an **optimization layer for the `think` role**. It sits
between your agent and your reasoning model. On every turn it decides whether it
has answered this turn before. If it has, it replies from its cache. If it has
not, it calls your model and answers as normal.

You keep your model, your provider, and your bill for the turns that reach the
model. What you gain is speed on the turns that repeat.

This is the one SLNG optimization you opt into. Listening and speaking are already
optimised behind their bindings, as the
[Execution Layer](/optimization/execution-layer) page explains. Thinking is not, until you
make this change.

## Start here

Three edits, all to one binding:

<Steps>
  <Step title="Declare the key">
    Add `SLNG_API_KEY` to `secrets:`. Your own model's key stays where it is.
  </Step>
  <Step title="Point think at slng">
    Change the `think` binding to `provider: slng`, keeping the model you already
    use.
  </Step>
  <Step title="Name the cache and the model behind it">
    Add an `agent_id`, which names your project's cache, and an `upstream`, which
    says where your model actually lives. One `agent_id` for the package; the
    compiler gives each agent and task its own scope under it.
  </Step>
</Steps>

Then compile and run as usual. Nothing else in your package changes.

```yaml agent.yaml
secrets:
  - SLNG_API_KEY

models:
  think:
    reasoning:
      provider: slng
      model: gpt-5.6-luna
      agent_id: salon-concierge-v1
      upstream:
        provider: openai
      params:
        world_part_override: eu
        reasoning_effort: "none"
```

That is the whole edit. Everything else in your package stays as it is: prompts,
tools, agents, tasks, task groups, greetings, channels, capacity.

## How it decides

The router remembers pairs: **what your agent said last, and what the caller said
next**. When that same pair comes round again, it can answer from the cache.

Two things follow, and both matter more than they look:

**A first turn never caches.** There is no preceding pair yet, so the first turn
of every call takes the full path to your model. Measure a conversation with no
repeat in it and you will measure nothing.

**Not every repeat caches, and that is by design.** The router judges which turns
are worth treating as repeatable. Measured on 2026-08-19: two pairs identical in
everything a client controls behaved differently, one answering from cache on its
second send and the other going to the model eight times in a row while returning
a byte-identical answer each time. A repeat served by the model is expected, not a
fault, and nothing here promises otherwise.

## One stable `agent_id`, one scope per prompt

`agent_id` names your project's cache, and everything learned under one scope is
invisible to another. You write one value; the compiler sends one scope per agent
and per task underneath it. Both halves matter, and this section takes them in
turn.

You write one value, and you own its version suffix. Change a prompt in a way that
should make old answers wrong, and bump the suffix: `salon-concierge-v1` becomes
`salon-concierge-v2`, and the router starts fresh. Fix a typo, and leave it alone,
because throwing the cache away buys nothing.

The compiler cannot make that judgement for you. It has no way to know whether a
reworded sentence changes what a good answer looks like, so it never derives the
value from your prompts and never hashes them into it. A package sends one
`agent_id`, and compiling fails if two think profiles disagree about it.

### One scope per agent, from the one id you wrote

What the compiler does do is add the name of whoever is speaking. Each agent and
each task sends the `agent_id`, a colon, then its own name:

```
salon-concierge-v3:concierge
salon-concierge-v3:booking_specialist
salon-concierge-v3:task.booking
```

That is not decoration. The cache key is the last exchange, and it does not
include the system prompt, so two agents sharing one scope can be served each
other's answers. Measured on a live call: the booking specialist's opening line
after a handoff was the concierge's "what phone number should I use to look up
your customer profile?", served from cache in 1.27 ms with no model call. The
caller heard the agent repeat itself. One scope per prompt is what the router's
own contract asks for, and now that is what unmute sends.

The names come from your package and nothing else, so the same package always
compiles to the same scopes, on either target. A wording change never moves a
scope: only your version suffix retires a cache, and bumping it retires every
scope in the package together.

Two things you will notice:

- **Two agents with identical instructions now get two scopes** and stop sharing
  warmth. They are two prompt sites, and keeping them apart is the point.
- **An existing project goes cold once.** A single-agent package that used to send
  a bare `agent_id` now sends `id:agent_name`, which is a different scope. Hit
  rates rebuild over the next calls.

One more consequence worth planning for: hit rates build over calls either way. A
fresh id is a cold cache, so bump it deliberately rather than as housekeeping.

**If we have pre-warmed answers for you, they are arranged against a scope, not
against your `agent_id`.** So an arrangement made before your package sent one
scope per prompt reaches nothing, and the same is true after any id bump. The
generated runbook prints the exact list of scopes your package sends; that list is
what we need to redo it.

Compiling refuses a scope that will not fit. The value leaves as an HTTP header
and the bound is 128 characters, counted on the finished scope rather than on the
`agent_id` alone, so a long id plus a long agent name can be refused where the id
by itself was fine. The message names which agent or task produced the long value
and how the two lengths add up, so you know which of the two names to shorten. It
refuses rather than truncating, because two truncated scopes could land on the
same string and bring the collision back quietly.

## Regions

`params.world_part_override` picks which router serves you.

| Value | Endpoint |
|---|---|
| `eu` | `https://eu.context-router.slng.ai/v1` |
| `us` | `https://us.context-router.slng.ai/v1` |
| `india` | `https://india.context-router.slng.ai/v1` |
| `indonesia` | `https://indonesia.context-router.slng.ai/v1` |

<Warning>
  These four are the router's own regions. SLNG **speech** uses world parts `na`,
  `eu`, and `ap` under the same `world_part_override` key. One word covers all
  three SLNG roles, and the accepted set is different per role, so `na` is right
  for a `listen` or `speak` binding and wrong for this one. The compiler refuses a
  value the router does not serve and names the four.
</Warning>

The key is consumed rather than forwarded: it becomes the base URL, and the
compile report says so on its own line.

## Your model, and who serves it

The `upstream` block says where the router actually calls your model. It is
required, and there is no default, because your provider's credentials travel with
the request and a package has to name whose they are.

| `provider` | You must write | You may write |
|---|---|---|
| `openai` | nothing else | `url`, `key_env` to override the defaults |
| `openai-compat` | `url`, `key_env` | `auth_header` |
| `azure` | `url`, `key_env`, `deployment`, `api_version` | nothing |
| `vertex` | `credentials_env`, `location` | `project` |
| `bedrock` | `access_key_id_env`, `secret_access_key_env`, `region`, `model_id` | `session_token_env` |

Five spellings over four kinds of upstream. The OpenAI-compatible kind was
validated against the live router on 2026-08-19, which covers both `openai` and
`openai-compat`. **`azure`, `vertex` and `bedrock` come from the router team's
published field list and have not been run here**, so treat your first call on one
of those as the test.

On `openai` the compiler supplies the URL and the `OPENAI_API_KEY` name, so the
block is one line. Any other upstream writes its own:

```yaml agent.yaml
secrets:
  - SLNG_API_KEY
  - AZURE_OPENAI_API_KEY            # you wrote this name, so you declare it

models:
  think:
    reasoning:
      provider: slng
      model: gpt-5.6-luna
      agent_id: salon-concierge-v1
      upstream:
        provider: azure
        url: https://my-resource.cognitiveservices.azure.com/
        key_env: AZURE_OPENAI_API_KEY
        deployment: reasoning-deploy
        api_version: 2024-12-01-preview
      params:
        world_part_override: eu
        reasoning_effort: "none"
```

A key the router does not expect for that upstream is a compile error rather than
a silent pass-through, because an unknown field comes back as a 400 on every think
request.

### Where your credentials go

**The configuration travels inline, in the request body of every think request,
so your upstream credentials are sent to SLNG.** That is a trust decision, and it is the
price of not registering anything anywhere in advance.

What the tooling guarantees is narrower and worth being precise about: a
credential is always *named*, never written. A `*_env` field holds an environment
variable name, the generated agent reads the value with `os.environ[...]` at run
time, and no package, generated file, or compile report ever contains a value.
Every name you write has to appear in `secrets:`, and every name joins the
generated startup check, so a missing value stops the agent at boot rather than on
the first turn of a live call.

`auth_header` is a header **name**, not a secret. It exists for an
`openai-compat` host that wants the key somewhere other than
`Authorization: Bearer`, for example `auth_header: x-goog-api-key`. The value
still comes from `key_env`. No field mixes a literal with an environment value,
which is what keeps a package free of secrets.

### A Vertex service-account key

`credentials_env` names one variable, and its value may be the key JSON itself,
that JSON base64 encoded, or a path to the key file. The agent works out which at
startup, so a malformed value fails at boot with a message naming all three
shapes.

To produce the base64 form:

```sh
base64 < service-account.json | tr -d '\n'
```

Verified on macOS 2026-08-19: `base64` writes one line there already, and
`tr -d '\n'` is what makes the same command produce one line on GNU coreutils,
whose `base64` wraps its output by default. Paste the result into your `.env` as
one line, and keep the key file itself out of your repository.

## `reasoning_effort` is not optional in practice

If your agent has tools, set it. The reasoning models in the GPT-5 family reject
function tools on chat completions without it, and every tool turn comes back as:

```
400 Function tools with reasoning_effort are not supported ...
To use function tools, use /v1/responses or set reasoning_effort to 'none'.
```

`"none"` works. This is the same trap a direct OpenAI think binding has, and
[the reasoning model page](/models/llm) explains it there too. The compiler warns
when your package has tools and the param is missing, rather than refusing,
because it cannot know for certain which model family your upstream serves.

## Personal prompts stay cacheable

A prompt that names the caller is different on every call, which would mean
nothing ever repeats. So a router-bound prompt keeps its placeholders and the
values travel separately:

```yaml agent.yaml
variables:
  customer_name:
    type: string
```

```markdown instructions.md
You are the concierge for Aurora Salon. The caller is {{customer_name}}.
```

The router receives that prompt with `{{customer_name}}` intact, plus a map of
this call's values, and substitutes them itself. Every call sends the same prompt,
so turns can still repeat.

This applies to the system prompt only. Greetings, tool arguments, injected
values, and webhook paths keep rendering locally exactly as before.

The values are read again for every request, not once when the call started. So a
value your call learns partway through, from a verification step or a lookup, is in
the prompt from the next turn on.

That is also why a router-bound prompt may name a variable that has no value when
the call begins, where a prompt on a direct provider may not. A direct prompt is
rendered once, before the call, so an unset variable leaves a hole in it and
compiling refuses. A router-bound prompt is never rendered here at all, so there is
no hole to leave: name a `source: conversation` variable or one a task assigns, and
the value arrives when the call learns it. That is what makes a placeholder worth using for
something the caller tells you during the call, rather than only for what you knew
before it began.

Three details worth knowing:

- A variable with no value yet sends an empty string, never the word "None". It is
  still sent: a placeholder the router was given no value for is a 422, and a 422
  mid-call ends the call.
- A value over 4000 characters is truncated with a warning on stderr, and the call
  continues. An over-long value is not a reason to drop a live call.
- On Pipecat the refresh happens where the call writes the value rather than on
  every request, because that framework offers no per-request hook. The effect is
  the same for every path a package can take today, since the only writes are at
  call start and when a step finishes.

### Which values belong in a placeholder

A placeholder is for a value your agent **says**: the caller's name, the company
name, an appointment detail read back aloud. Those are the values that make an
answer personal, and personal answers are the ones the router otherwise refuses to
keep. Supplied as a value, the stored copy holds the placeholder instead of the
name, so the turn caches like any other and the next caller hears their own name
in it.

A value that changes **what the answer is** does not belong in one, however much
it varies per call. The reply language is the clearest case:

```markdown Wrong
Reply to the caller in {{session_language}}.
```

Two callers who chose different languages would share one cached answer and one of
them would hear the wrong language. Write a steering value into the prompt text
instead, and if two variants must never receive each other's answers, give each
its own `agent_id`: the agent id is the only thing that partitions the cache.

Nothing checks this for you. The compiler will not judge a value by its name, so a
steering value in a placeholder fails silently and only in production.

### Give the value the shape the agent says it in

A placeholder only earns its keep while the router can recognise the value in the
answer. It substitutes back where the answer holds the value **character for
character**, so a value the model tidies up on its way out, a phone number it
regroups, a date it rewrites, leaves the real thing in the stored copy. The
personal-data scan then refuses to share that copy, and the turn stops caching.

Measured against the live EU router on 2026-08-24, three reads per arm on fresh
scopes:

| Value supplied | The model said it back | Served from cache |
|---|---|---|
| `555 070 1222` | unchanged | yes, 109ms on the third read |
| `5550404111` | unchanged | yes, on the second read |
| `+15550707444` | regrouped, so the value never appeared | **never, 0 of 3** |

Nothing reports this. There is no error, no warning, and the caller hears a
correct answer every time. The only symptom is a hit rate of zero.

So write the format into the variable's own `description`, and make whatever
produces the value follow it. A task that returns a phone number should say what
shape it returns it in, the way `examples/salon-concierge` does:

```yaml agent.yaml
variables:
  customer_phone:
    type: string
    description: >-
      The caller's confirmed phone number, as the verification task returns it:
      digit groups separated by single spaces, with no plus sign, brackets or
      dashes.
```

### What the router will not cache, whatever you do

Three rules decide this, and none of them is about your placeholders:

| The answer | Why |
|---|---|
| holds personal data a scan flags | it would be replayed to the next caller |
| contains a tool call | the turn is an instruction to act, not an answer |
| follows a tool result | the result is this caller's data |

There is a fourth rule, and unlike these three a placeholder does beat it: the
router refuses to store an answer **holding a number in any script**, because a
number in a reply is usually caller-specific. A number the agent says from a
placeholder is not in the stored copy at all, so that answer caches like any
other. Measured above. A number the agent renders itself, or one it reformats
before saying, falls under the rule.

So an agent that quotes times and prices from its own working sees fewer hits
than one that asks questions, and that is the numeric rule working rather than a
fault. Where those numbers are per-call values the agent reads back, a
placeholder turns them into hits. The first turn of every call is always the
model either way: there is no preceding turn to have cached.

## Checking that it is working

**Read the run's own log.** Every think request writes one line, at info level, in
every run, deployed or local:

```
slng router: scope=clinic-scheduler-v1:concierge source=cache layer=l2_exact request_id=req_...
slng router: scope=clinic-scheduler-v1:concierge source=llm model=gpt-5.6-luna request_id=req_...
```

`source=cache` means no model ran. Repeat an exchange and watch it change: that is
the check, and it needs no dashboard and no code of yours. `layer` appears only on
a hit, `model` only on a live answer, `request_id` is what to quote to us. Nothing
aggregates the lines, so a hit rate is a count of them.

Do not read a hit off the clock instead. A hit has been measured at 396ms and a
generation faster than that, so latency alone tells you nothing on any single
turn.

The line is built from three response headers, which the generated project reads
through a hook on its own HTTP client because neither framework surfaces them.

| Header | Values | Meaning |
|---|---|---|
| `x-slng-response-source` | `llm`, `cache` | which path answered this turn |
| `x-slng-cache-layer` | `l1_exact`, `l2_exact`, absent on the model path | which cache layer answered |
| `x-slng-model` | a model id, present only on the model path | which model answered |
| `x-slng-request-id` | always present, errors included | quote this to support |

What to expect on a call where you repeat a turn: full latency on the first turn,
then roughly 110 ms against 800 to 1500 ms when a repeat is served from cache.
Tool turns always take the model path, both the request turn and the result turn.

<Note>
  Hit rates vary, so plan for the model path and treat cache hits as the upside.
  Read `x-slng-response-source` rather than inferring from latency: fast is not
  proof of a hit, and a repeat served by the model is expected rather than a
  fault. On the turns that miss, the router is an extra hop in front of your own
  model, so it costs a little rather than saving.
</Note>

Streamed responses report no usage on either path, so token savings cannot be read
off the stream.

If a repeat never caches, check in this order: is the agent id the same across the
two calls, did at least two seconds pass since the turn it repeats, is it the
second turn or later, and is it the exact pair of previous reply and current
message. If all four hold, stop looking. The router decides, and some turns never
cache.
