This page describes the carrierless form of Pipecat's `daily-sip` transport. It
can dial a cold-transfer destination, but it cannot receive calls. Unmute does
not ship a Daily transfer example or support warm transfer on Pipecat.

```yaml targets.yaml
targets:
  pipecat:
    provider: pipecat
    version: "1.7.0"
    connection: daily
```

```yaml connections/daily.yaml
transport: daily-sip
```

```yaml agent.yaml
destinations:
  billing_line: BILLING_PHONE_NUMBER
```

That one-line connection is the whole outbound route. No `carrier:` line is
needed because Daily dials the transfer destination. No `environment:` block is
needed either: `DAILY_API_KEY` is a compiler-known runtime requirement, not a
name authored in this connection. The generated runbook says who supplies it.

## The transfer

```yaml agent.yaml
controls:
  send_to_billing:
    kind: human_transfer
    when: The caller asks about an invoice, a refund, or a charge they do not recognise.
    cold:
      destination: billing_line
```

Cold only. The bot announces the handoff, Daily reroutes the caller's leg out
of the room, and the bot drops off. Billing answers knowing nothing about the
call.

Warm is **not built yet** on this route. Daily documents the pattern, so the
platform is not the limit; Unmute has not emitted it. That is a different
statement from "the platform cannot", and the docs keep the two apart.

The same cold transfer also works when a `daily-sip` connection names your own
carrier. The destination leaves through that carrier's SIP trunk, but Daily
stays in the call path, so both Daily legs keep billing until the call ends and
the destination leg also incurs the carrier's charge. That form needs the same
Daily dial-out permission. Its connection keys are listed in
[`connections/<name>.yaml`](/reference/connections-yaml).

## Dial-out has to be granted

`unmute validate` prints the prerequisite before you get anywhere near a call:

```sh
unmute validate <package>
```

```text wrap
✓ pipecat (pipecat)

Setup prerequisites:
  pipecat: daily_dialout: Ask Daily to enable dial-out on the domain the agent's rooms belong to: it is a paid feature granted on request, per domain, and international dial-out is enabled separately. It covers dialling a SIP URI as well as a PSTN number, so a target that carries its calls through its own carrier trunk needs the same approval and needs no purchased Daily number.
    https://docs.pipecat.ai/pipecat-cloud/guides/telephony/daily-dial-out (verified 2026-08-12)
```

Transfers on this route are dial-out, so without that approval the transfer
fails on a live call rather than at compile time. Ask first.

## No phone channel

```yaml agent.yaml
channels:
  web:
    kind: realtime_audio
```

The package declares web audio only because the carrierless Daily shape cannot
serve a phone channel. The conversation starts in the browser; the cold
transfer control dials the destination through Daily. For inbound phone calls,
use the `daily-sip` form that names a carrier.

## Running it

`unmute dev --telephony` refuses this route, and says why:

```text wrap
unmute: dev <package>: target "pipecat" uses a carrierless Pipecat Daily connection (transport daily-sip), which is outbound-only: it can dial a transfer destination but cannot receive calls, so there is no local telephony topology to run; talk to this agent now with `unmute dev <package>` in the browser, and to deploy it run `unmute compile <package>` and follow the Deploy and Human transfers sections of the emitted README
```

This route has no inbound topology to run. Talk to the agent in the browser and
use the emitted runbook for deployment and the outbound transfer.
