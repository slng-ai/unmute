This page describes Pipecat's `daily-sip` transport. It is a Pipecat route with
a native cold-transfer primitive, but Unmute does not ship a Daily transfer
example or support warm transfer on Pipecat.

```yaml targets.yaml
targets:
  pipecat:
    provider: pipecat
    version: "1.7.0"
    connection: daily
```

```yaml connections/daily.yaml
transport: daily-sip
```

```yaml agent.yaml
destinations:
  billing_line: BILLING_PHONE_NUMBER
```

That one-line connection is the whole route, and it is the shortest a connection
gets. No `carrier:` line, because on this form Daily provisions the number and
Daily's own infrastructure delivers the call to your deployed agent, so there is
no carrier account to configure at all. No `environment:` either, for the same
reason: the `DAILY_API_KEY` the runtime reads comes from the route, not from your
package, so it is not in `secrets:` and it is still in the generated
`.env.example`.

## The transfer

```yaml agent.yaml
controls:
  send_to_billing:
    kind: human_transfer
    when: The caller asks about an invoice, a refund, or a charge they do not recognise.
    cold:
      destination: billing_line
```

Cold only. The bot announces the handoff, Daily reroutes the caller's leg out
of the room, and the bot drops off. Billing answers knowing nothing about the
call.

Warm is **not built yet** on this route. Daily documents the pattern, so the
platform is not the limit; Unmute has not emitted it. That is a different
statement from "the platform cannot", and the docs keep the two apart.

The same cold transfer also works when a `daily-sip` connection names your own
carrier. The destination leaves through that carrier's SIP trunk, but Daily
stays in the call path, so both Daily legs keep billing until the call ends and
the destination leg also incurs the carrier's charge. That form needs the same
Daily dial-out permission. Its connection keys are listed in
[connections/&lt;name&gt;.yaml](/reference/connections-yaml).

## Dial-out has to be granted

`unmute validate` prints the prerequisite before you get anywhere near a call:

```sh
unmute validate <package>
```

```text wrap
✓ pipecat (pipecat)

Setup prerequisites:
  pipecat: daily_dialout: Ask Daily to enable dial-out on the domain the agent's rooms belong to: it is a paid feature granted on request, per domain, and international dial-out is enabled separately. It covers dialling a SIP URI as well as a PSTN number, so a target that carries its calls through its own carrier trunk needs the same approval and needs no purchased Daily number.
    https://docs.pipecat.ai/pipecat-cloud/guides/telephony/daily-dial-out (verified 2026-08-12)
```

Transfers on this route are dial-out, so without that approval the transfer
fails on a live call rather than at compile time. Ask first.

## No phone channel

```yaml agent.yaml
channels:
  web:
    kind: realtime_audio
```

The package declares web audio only. On this route the telephony belongs to
Daily: the number, the dial-in webhook, and dial-out permission all live on the
Daily domain, configured through Pipecat Cloud, not in anything Unmute
generates.

## Running it

`unmute dev --telephony` refuses this route, and says why:

```text wrap
unmute: dev <package>: target "pipecat" runs on the Pipecat Daily route (transport daily-sip), where Daily carries the phone call to a deployed agent, so there is no local telephony topology to run; talk to this agent now with `unmute dev <package>` in the browser, and for a real phone call run `unmute compile <package>` and follow the Deploy and Phone calls sections of the emitted README
```

That is the honest answer: this route has nothing local to run. Talk to the
agent in the browser to work on its behavior, and use the emitted runbook for
the phone part.
