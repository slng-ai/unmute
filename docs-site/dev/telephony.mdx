```sh
unmute dev examples/twilio-telephony-hello --telephony --target pipecat
```

With `--telephony`, `unmute dev` runs the route your connection declares instead
of the browser UI. A real call from a real phone can reach the agent on your
laptop.

This page is the mechanics: what runs, what it touches that is not yours, and what
it undoes when you stop it. The route vocabulary itself, and which routes exist,
is on [Telephony](/telephony/overview).

<Note>
  The Pipecat `cloud-websocket` route runs the generated agent directly with
  `uv` instead of Docker. Install `uv` and check it with `uv --version` before
  starting that route. The other local phone routes use Docker Compose.
</Note>

## What happens, in order

<Steps>
  <Step title="Compile and print the plan">
    The package is generated into `build/<target>/`, and the resolved route is
    printed: the transport, the carrier, the local services it needs, and the
    carrier steps no command can do for you.

    ```text wrap
    livekit: telephony route provider=livekit transport=sip carrier=twilio coordination=shared
    livekit: setup: get the selected carrier SIP address, username, password, and phone number from its SIP trunking console; these four reach the deployed agent's dial-out path directly, so no outbound trunk is registered
    livekit: local services: application, livekit_server, livekit_sip, redis
    compiled pkg/build/livekit
    ```
  </Step>
  <Step title="Check the credentials you have to supply">
    Only the ones that are yours. Values the command generates itself, such as the
    outbound token and the public URL under a managed tunnel, are never asked of
    you. A missing name stops the run before Docker or your carrier is touched, and
    the message says which name and why this route needs it.
  </Step>
  <Step title="Open a public tunnel, on the routes that need one">
    A route with carrier callbacks needs a public HTTPS origin. The command starts a
    `cloudflared` quick tunnel to the agent's port and uses its origin:

    ```text
    pipecat: managed tunnel https://<random>.trycloudflare.com (quick tunnel URLs rotate on every run)
    ```

    Quick tunnel URLs really do rotate on every run, which is why the next step
    happens on every start rather than once. `--public-url` skips this entirely and
    uses your own origin. The LiveKit SIP route needs no tunnel: SIP does not call
    back over HTTP.
  </Step>
  <Step title="Start the local stack">
    Docker Compose brings up the generated services. On LiveKit SIP that is the
    agent, Redis, LiveKit Server, and LiveKit SIP, and the command creates the local
    trunk and dispatch records against that local server itself, before the agent
    starts, so an inbound call has somewhere to land.

    The Pipecat Cloud carrier-stream route is the exception: nothing of yours is
    hosted on it in production, so locally there is no Compose stack either. The
    compiled agent runs directly with `uv` in the carrier's stream mode.
  </Step>
  <Step title="Point your number at this run">
    Where the carrier has an API for it, today Twilio, the number's voice webhook is
    set to this run's public URL and the previous value is printed:

    ```text
    pipecat: Twilio voice webhook for +15551234567 set to https://<random>.trycloudflare.com/telephony/inbound (was: unset)
    ```

    This is the one thing the command changes outside your machine, and it changes it
    in your name, which is why the previous value is printed rather than assumed.
  </Step>
  <Step title="Print the call line">
    ```text
    call +1XXXXXXXXXX  ·  ctrl-c to stop
    ```

    On an outbound-capable route it also says whether dial-out is ready, and what to
    add to place a call.
  </Step>
</Steps>

## Stopping puts things back

Ctrl-c undoes the outward changes:

- the carrier webhook is set back to what it was, and the restore is printed:

  ```text
  pipecat: Twilio voice webhook for +15551234567 restored to unset
  ```

- the tunnel is closed, so the URL stops existing,
- the Compose stack is stopped and removed. Named data volumes are kept.

The restore is armed before the number is ever touched, so it runs on every exit
path: a clean ctrl-c, an error, or a crash after the change. If the restore itself
fails, you get a warning naming the number, not silence.

## What each route actually runs

| Route | Local stack | Tunnel | Touches your carrier |
|---|---|---|---|
| Pipecat `cloud-websocket` + Twilio | the compiled agent under `uv`, no Docker | yes | sets the number's voice webhook for this run |
| Pipecat `carrier-websocket` + Twilio | Compose: agent, Redis | yes | sets the number's voice webhook for this run |
| LiveKit `connector` + Twilio | Compose: agent, LiveKit Server; no Redis | yes | sets the number's voice webhook for this run |
| LiveKit `sip` + Twilio | Compose: agent, Redis, LiveKit Server, LiveKit SIP | no | nothing; the trunk records it creates are on the local server |
| Pipecat `daily-sip` + Twilio | refused; run the emitted `telephony_helper.py` | not applicable | nothing |

The Daily route needs an existing carrier phone leg. Its generated README gives
the two commands for the helper and tunnel; `unmute dev --telephony` does not
host that public helper for you. Set `UNMUTE_PUBLIC_URL` to the helper's exact
HTTPS base URL before it starts. The helper verifies Twilio's signed `/call`
form before it uses the Pipecat Cloud key to start an agent session.

## The flags

| Flag | What it does |
|---|---|
| `--telephony` | run the route instead of the browser UI |
| `--no-webhook` | leave the carrier number alone; the run prints its public URL and you point something at it yourself |
| `--public-url` | use your own HTTPS origin instead of a managed quick tunnel |
| `--to <E.164>` | place one outbound call as soon as the stack is healthy |
| `--verbose` | follow the run's log on stderr as well as writing it to the log file |
| `--bot-port` | change the host port the agent publishes, default `7860` |

`--public-url` and `--to` both require `--telephony`, and say so:

```text
unmute: dev: --to requires --telephony
```

`--to` takes one E.164 number and checks it before anything starts:

```text
unmute: dev: --to must be an E.164 number like +15551234567, got "4155550123"
```

## Where the log is

Everything the stack prints goes to `build/<target>/telephony.log`, and the path is
printed with the ready line. It is also printed when the stack fails to start,
which is where the reason lives:

```text
telephony Compose failed to start. logs: pkg/build/livekit/telephony.log
unmute: dev pkg: start Docker Compose topology: exit status 1
```

A verified example of what you find in there: a port another run is already holding.

```text wrap
Error response from daemon: failed to set up container networking: driver failed programming external connectivity on endpoint unmute-pkg-livekit-e7f5b2b6-livekit_server-1: Bind for 0.0.0.0:7880 failed: port is already allocated
```

That one means another dev stack is still up. Stop it, or run the other package.

Use `--bot-port` to move the agent. On LiveKit SIP, set
`LIVEKIT_HOST_PORT`, `LIVEKIT_SIP_HOST_PORT`, and
`LIVEKIT_RTP_HOST_PORT_RANGE` before the run when those host ports are busy.
The local RTP range defaults to `10000-10100`; every occupied port and range
must differ when two stacks run at once.

## What a healthy local run proves

<Warning>
  A healthy local stack proves wiring, not reachability. A real call also needs
  carrier credentials, a voice capable number, and the route's public ingress. For
  SIP, network address translation on a laptop can block the call even when every
  health check passes.
</Warning>
