```sh
unmute compile examples/simple-prompt --target pipecat
```

```text
examples/simple-prompt/build/pipecat/
├── bot.py                # the agent
├── tools/                # your local handlers, copied
│   ├── __init__.py
│   └── book_appointment.py
├── tracing.py            # present when the package sets tracing
├── pyproject.toml        # pinned dependencies
├── Dockerfile
├── .dockerignore
├── compose.dev.yaml      # an optional container run; `unmute dev` uses local uv
├── pcc-deploy.toml       # Pipecat Cloud deploy manifest
├── .env.example          # exactly the variables you supply
├── README.md             # the runbook for this build
└── compile-report.json   # what the compiler decided
```

## bot.py

One file holds the agent: the prompts as module constants, the model
constructors, the tool wiring, and the pipeline. It imports Pipecat and your
handlers, and nothing from Unmute.

It also carries a startup check built from your `secrets:` list:

```python
REQUIRED_ENV = [
    "OPENAI_API_KEY",
    "SLNG_API_KEY",
]


def require_env() -> None:
    missing = [name for name in REQUIRED_ENV if not os.getenv(name)]
    if missing:
        raise RuntimeError(
            f"Missing required environment variables: {', '.join(missing)}"
        )
```

A missing key stops the container at startup and names what is missing, instead
of failing on the first spoken word.

## Run it without Unmute

The generated README says it:

```sh
cp .env.example .env                      # then fill in your keys

uv run bot.py -t webrtc                   # web: open the URL it prints
```

`uv` installs the pinned dependencies on the first run.

## Dependencies are pinned

```toml pyproject.toml
dependencies = [
    "pipecat-ai[openai,runner,silero,tracing,webrtc]==1.8.0",
    "pipecat-slng>=0.5.1",
    "python-dotenv>=1.0",
]
```

The extras are derived from what your package actually uses: the providers you
bound, the turn detector, tracing if you enabled it. The framework version is
the `version:` from your target.

## Deploy

The generated README is the authority, with your own values filled in. The
shape of it:

```sh
cp .env.example .env
pipecat cloud secrets set acme-support-pipecat-secrets --file .env
pipecat cloud deploy
pipecat cloud agent status acme-support-pipecat
```

The secret set comes first, because the manifest already names it and a deploy
cannot start without it. `pipecat cloud deploy` builds the image in the cloud
from the generated `Dockerfile`.

### The deployed agent's name

`acme-support-pipecat` above is the package's
[`name:`](/reference/agent-yaml#name) joined to the target it was compiled for,
and it is `agent_name` in `pcc-deploy.toml`. Pipecat Cloud agent names are
unique across an organisation and a deploy updates the agent matching the name,
so it has to say which package this is. Unmute used to write the target name
there, and every package on this target calls its target `pipecat`: two packages
in one organisation deployed over each other.

The secret set follows the same name, because a secret set is per-organisation
in the same way.

A rename creates a second agent rather than moving the first. The old one keeps
running and keeps billing, so delete it with
`pipecat cloud agent delete <old-name>` and create the secret set again under
the new name. On a phone route the TwiML Bin has to be repointed too:
[Redeploying](/deploy/redeploying#pipecat-cloud-websocket) is the ordered walk.

Every Pipecat route takes those same commands. Both telephony transports,
`cloud-websocket` and `daily-sip`, emit a `pcc-deploy.toml` and build on the
platform's base image, so there is no route here that you host yourself.

<Warning>
  Do not edit files in `build/`. Change the source package and compile again.
  The generated README says the same thing in its first paragraph.
</Warning>
