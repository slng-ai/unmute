SLNG hosts the agent. There is no project to run and nothing to keep alive, so
the compiler writes a deployment body and a runbook instead of Python, and one
command sends them:

```sh
export SLNG_API_KEY=...
unmute deploy examples/slng-support
```

<Warning>
  SLNG creates no tool from your package. A `local:` or `webhook:` block is
  refused on this target: reference a tool your organisation already has with
  [`slng:`](/build/tools/hosted) instead, or compile the package to pipecat or
  livekit, where your own handler or endpoint runs. The rest of this page
  describes the target in full, including the tool shapes.
</Warning>

## The trade

A slng package is shorter than the same agent written for pipecat or livekit, and
what is missing is not capability. It is the layer you would otherwise stand up
yourself.

| On a code target you author | On slng |
|---|---|
| a Python project, a `Dockerfile`, an image to host | nothing; SLNG runs the agent |
| worker counts, concurrency, scaling | SLNG's, already provisioned |
| a VAD, a turn model, endpointing windows | SLNG's turn taking |
| the event loop wiring STT to LLM to TTS | SLNG's pipeline |
| where each provider is called from | one region, chosen per call |

So here you author intent: prompt, models, tools, greeting, variables. The layer
under it is already running, already in-region, already warm, with STT, LLM,
TTS and the tool sandbox one network hop apart rather than one internet apart.
You give up owning the runtime and you get one that is co-located and tuned.

That is also why the refusals below are refusals rather than silent drops: a
setting that describes a runtime you no longer own has nothing to act on, and
being told is better than having it disappear.

## What compiling writes

To stop at the files:

```sh
unmute compile examples/slng-support --target slng
```

```text
examples/slng-support/build/slng/
├── agent.json                # the agent create body
└── README.md                 # the runbook: what to create, what to run, what to watch
```

This target writes no `tools/` directory. Every tool reference in
`agent.json`, whether a curated capability, a hosted tool, or an MCP server,
resolves by name against your organisation, so there is never a body of your
own to write beside it.

Unmute's compiler opens no connection to SLNG, at validate time or compile time.
It writes files and stops. [`unmute deploy`](/reference/cli/deploy) hands them to
the `voiceai` CLI, which owns your account and the push, so it has to be
installed:

```sh
brew install slng-ai/tap/voiceai
```

## targets.yaml

```yaml targets.yaml
targets:
  slng:
    provider: slng
    deployment_region: eu-central
```

That is the whole target. `version`, `pins`, `sdk_language` and `connection` are
all refused by name: each describes a generated project, and there is none.

`deployment_region` takes exactly one of `any`, `us-east`, `eu-central` or
`ap-south`. `any` lets SLNG route each call itself. This is the only target
whose region values are checked, because it is the only one whose platform
publishes a closed set.

## The pushed agent's name

The agent is pushed under the package's [`name:`](/reference/agent-yaml#name)
joined to the target it was compiled for. This target has no project to deploy
into, so that name is the whole identity.

```yaml agent.yaml
version: 1
name: acme-support
entry_agent: support
```

With the target above, that pushes an agent called **acme-support-slng**.

SLNG names are unique across an organisation and a push resolves which agent to
write by matching the name in the body, so pushing under a name that already
exists replaces that agent rather than adding one. Unmute used to write the
target name here, and every package on this target calls its target `slng`: two
packages in one organisation both pushed an agent called `slng`, and the second
replaced the first one's prompt, models and tool attachments.

Check a name is free before you claim it:

```bash
voiceai agents list
```

Renaming later does not move a deployed agent: it leaves the old one running and
creates a second.

## Model names

SLNG names a model with the vendor and the model joined by a slash. A package
writes them as two fields, and the slng driver joins them when it writes the
body:

```yaml agent.yaml
models:
  think:
    reasoning:
      provider: openai
      model: gpt-5.6-terra
```

That reaches SLNG as one string. A model name that already carries a slash is
passed through whole rather than joined twice, which is how a SLNG Context
Router model such as `slng/deepgram/nova:3-en` reaches the body unchanged.

Nothing else about a model is checked here. SLNG owns its own model list, so
Unmute forwards the values as written and validates none of them.

That makes a model string the field most likely to fail your push, and it fails
loudly: `AGENT_MODEL_UNAVAILABLE`, naming `models.stt`, `models.llm` or
`models.tts` and the string it rejected. Three different things cause it: the
model is not enabled for agents in your organisation, it is one of your own and
SLNG's router is off, or it is not served in the region and language this agent
asked for.

That last one is the surprising one. Not every model exists in every region, and
pinning `deployment_region` to a region a model does not serve fails at push.
`any` avoids it by letting SLNG route each call.

Unmute writes no `llm_router_enabled`, so SLNG applies its own default. That is
deliberate: a model your organisation brought its own key for has no entry in
SLNG's shared catalogue, and SLNG accepts one only when the router is on.
Writing the field off would refuse a whole class of your own models, and nothing
in a package asks for that.

## Push it

The runbook in `build/slng/README.md` is the authority for your package. In
outline:

```sh
export SLNG_API_KEY=...
unmute deploy examples/slng-support
```

An agent id comes back, and you need it to open a session. Read
[the command's own page](/reference/cli/deploy) for the flags; the one that
matters first is `--dry-run`, which changes nothing.

`unmute deploy` reads `SLNG_API_KEY`, then `VOICEAI_API_KEY`, then whatever
profile `voiceai login` stored. Those are two names for one token: a single SLNG
key serves every SLNG role, including the Context Router key a generated livekit
or pipecat project reads at run time. `VOICEAI_API_KEY` is the name the push tool
itself reads, so export whichever your shell already has.

The organisation is printed on every run, because an exported key and a stored
profile can belong to different ones.

To drive the push tool directly:

```sh
voiceai agents push build/slng
```

### Where your tools come from

A tool on SLNG runs inside the platform's own sandbox, in the region serving
the call, one hop from the model rather than a whole internet away. Code
there has no network access of its own: an `api_request` tool is how SLNG
itself reaches an outside service.

Reference what your organisation already has by name with
[`slng:`](/build/tools/hosted), for the reason at the top of this page.
`unmute pull` mirrors the definition into your package, so the same tool also
runs on livekit and pipecat. [Hosted tools](/build/tools/hosted) has the
field-by-field version, including the one limit: a hosted tool's Python
dependencies compile to slng and are refused on the two code targets.

### Names, not identifiers

`agent.json` writes each tool and MCP reference as a name, because no compiler
can invent an identifier a server assigns. SLNG's `tool_refs` entries require
`attachment_id`, `tool_id` and `version`, so a name has to become an id before
the body is accepted.

This includes a curated capability. A `builtin:` tool needs nothing *created*,
because SLNG already has it, and it still has a `tool_id` that has to be filled
in.

Resolving those names is the push step's job. It is also why
`voiceai agents create --file build/slng/agent.json` is the wrong command: that
posts the body verbatim, names included, and the API refuses it.

A `local:` or `webhook:` tool never reaches this step: the block is refused
before compiling, for the reason at the top of this page.

An MCP reference resolves the same way, and it needs one thing agent.yaml has to
say up front: which tools you want. Unmute compiles offline, so it cannot expand
"every tool on the server" into a reference list; an `mcp:` tool with no
`mcp.tools` list is refused at validate, naming the tool and pointing at
`mcp.tools`.

Once the list is there, the push looks up the server's name for its
`server_id`, then copies each named tool's schema hash out of the platform's own
stored capability snapshot. Nothing connects to the MCP server. The one caveat:
the platform refuses a snapshot that is unhealthy or older than five minutes.
Refresh it first with `voiceai mcp run <server>`.

The runbook says which case your package is in.

### A push replaces

Updating an agent replaces it with what the package declares. A tool reference
the package no longer names is detached, and a field that differs is
overwritten. `unmute deploy --dry-run` names both before anything happens.

The agent's name is `name:` joined to the target, so a run that reports `update`
when you expected `create` means an agent of that name already exists. Change
`name:` in `agent.yaml`, or let `--agent-id` pick a different one.

### Do not push a dashboard export back

An agent document exported from SLNG is not always a body the API accepts. The
export carries `orchestrator`, which the create body forbids: an export from an
agent running on LiveKit omits the field at its default and posts cleanly, and
the same export from a Pipecat agent is rejected. Several other fields differ,
and `llm_router_enabled` defaults the opposite way on the two shapes.

Compile from the package instead.

## Hosted tool dependencies

A hosted tool's Python dependencies are the platform's own, mirrored by
`unmute pull` into `tools/<name>.slng.json` rather than written by you. Each
is an exact `name==version` pin, because SLNG builds a locked, hash-verified
environment per tool.

The sandbox runs Python 3.14 with `pydantic` already installed, so a hosted
tool using only the standard library and pydantic needs no dependencies
mirrored at all.

This is slng-only. The code drivers build one dependency list for the whole
generated project out of the provider catalogue and read nothing per tool, so
a hosted tool that declares dependencies is refused on `livekit` and
`pipecat` rather than having the pins silently dropped. See
[Hosted tools](/build/tools/hosted) for the full story.

## The Vault

SLNG reads secrets from its own store. Unmute knows which names a package needs
and can create none of them, so the runbook lists them, grouped by where each
one came from, above the push command. No secret value reaches any emitted file
or any command in the runbook.

Two kinds appear there:

- a **secret** is a credential a tool authenticates with, named in the package
  as an environment variable and stored in the Vault under the same name;
- a **variable** is a `{{$NAME}}` token that SLNG substitutes into text at run
  time.

A `{{$NAME}}` token passes validation on a slng target and reaches the body
unchanged. On a LiveKit or Pipecat target it is refused, and the message says
what the token is rather than telling you to declare a variable that must not
exist.

A package that needs no Vault entries is told so, rather than shown an empty
list.

## What a slng package may not ask for

Every one of these is refused at validate, by name, with what to do instead.
None is dropped quietly.

| Package feature | Why SLNG cannot take it |
|---|---|
| tasks, task groups, handoffs | the create body carries one prompt and one greeting |
| a `turn:` section, `semantic_endpointing`, `endpointing_delay`, `pace` | SLNG owns its own turn taking |
| an `mcp:` tool with no `mcp.tools` list | unmute compiles offline and cannot expand "every tool on the server" into a reference list: name the tools you want |
| `placement: local` on any model | SLNG runs the pipeline; there is no machine of yours |
| `conversation.inactivity` | SLNG's idle nudges need three spoken texts a package does not carry |
| `conversation.max_duration`, `thinking_audio` | no field on the create body holds them |
| `interruption.minimum_words`, `interruption.ignore_phrases` | interruptions are on or off |
| a missing greeting, or a model-written one | SLNG requires a greeting and speaks the string it is given |
| `tracing:` | unmute instruments no process here, so it can install no exporter |
| a second `deployment_region` | SLNG takes exactly one |
| `variables` with `source: conversation` | nothing on the create body captures a value mid-call |
| outbound calling, `on_voicemail` | a package declares no carrier state on SLNG; `unmute deploy` attaches an existing trunk after a push |
| a warm human transfer | SLNG's curated transfer places a single blind transfer |

An MCP tool works. Its one caveat: the platform's stored capability snapshot
for that server has to be healthy and no older than five minutes, or the push
refuses it.

## If the agent answers with silence

A model can pass every check at create time and still fail on the call. Create
validates what your organisation is allowed to use; whether the provider behind
it answers is a different question.

```sh
voiceai agents calls list <agent_id> --json
```

`call_end_reason` on the latest call names the layer:
`terminal failure: component=llm reason=hard_fail` is the LLM, and `stt` and
`tts` appear the same way. That is a model or provider problem rather than a
problem with the compiled body, and swapping that one binding is the fix.

## There is no `unmute dev`

`dev` runs the generated project locally, and this target compiles no project.
To talk to a pushed agent, open a web session:

```sh
voiceai agents web-sessions create <agent_id> --file session.json
```

The agent id is the one `unmute deploy` printed; `voiceai agents list` finds it
again. The command returns LiveKit connection details, and a
`livekit_dispatch_id` meaning a worker joined the room.

The `--file` is required even though every field in it is optional, because the
endpoint declares a request body and the CLI sends none without it. A minimal
`session.json` is `{"arguments": {}}`; `arguments` is where the package's
declared variables get their value for one session.
