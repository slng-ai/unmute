---
title: "Variables"
description: "Declare a type once, save a task's result, and use it only where it is needed."
---

Use a variable when a later task or agent needs a reliable fact from this call.
For example, after moving a booking, save the new appointment. The next task
can use its current date without trying to resolve conflicting dates in the
conversation.

A variable lives for one call. It is not a database record. Your tools save
changes in your booking system; variables let the agent use the result later.

There are three choices: **declare** what a value holds, **save** it when a
task finishes, and **read** it in each prompt or tool that needs it. Saving a
value does not automatically share it with any prompt.

The snippets below extend an existing package. Merge them into the matching
blocks in `agent.yaml`; do not add duplicate top-level keys.

## Declare them

Start with the smallest useful value:

```yaml agent.yaml
variables:
  requested_service:
    type: Literal["haircut", "hair-color", "blowout"]
    description: The service the caller chose.
```

Use `str` for free text, `int` or `float` for numbers, and `bool` for a yes or
no fact. Use `Phone`, `Date`, `Time`, or `Id` when the spelling matters. Use a
`Literal` when there is a fixed set of choices.

The [type reference](/reference/variables#the-type-grammar) lists every type,
its limits, and how to represent an absent value.

## Save a value when a task finishes

Add this task under an agent in your package:

```yaml agent.yaml
agents:
  concierge:
    tasks:
      - name: choose_service
        when: Find out which service the caller wants.
        instructions: tasks/choose-service.md
        assign:
          - requested_service: result.service
```

```markdown tasks/choose-service.md
Find out which salon service the caller wants. Use what they have already
said and ask only if the service is missing or unclear. Then finish with
that service.
```

The task gets the conversation by default. `assign:` gives its generated
finish call a `service` argument with the type of `requested_service`. You
declare the type once, on the variable. You do not write a separate task
result schema or ask the owning agent to repeat the caller's request.

Unmute checks the finish arguments before saving them. If validation fails,
the task stays open so the model can correct the value. An ordinary tool
result does not fill a variable by itself: the task must finish.

## Read a value where it is needed

Add a placeholder to each prompt that should use the saved value:

```markdown tasks/booking.md
Requested service: {{requested_service}}
Use it if present. If no service is recorded, ask which service the caller wants.
```

An unset value renders as `none recorded yet.` The instructions work before
and after the earlier task saves the service.

The owning agent also needs a reference if it should remember the result
after the task returns. It receives a completion status and its earlier
conversation, not the private conversation inside the task. This rule applies
even when the task uses `history: messages`.

## Group related fields into a shape

A booking's ID, date, and time belong together. A shape lets one successful
task save them as one value:

```yaml agent.yaml
shapes:
  - name: Appointment
    fields:
      - booking_id: Id
      - service: Literal["haircut", "hair-color", "blowout"]
      - date: Date
      - time: Time

variables:
  appointment:
    type: Appointment
    description: The latest appointment successfully saved by the booking tool.
```

In a booking task, add:

```yaml
assign:
  - appointment: result.appointment
```

Write the task's instructions to copy the successful tool result and finish
immediately. Have the owner confirm the saved appointment to the caller:

```markdown instructions.md
Latest saved appointment: {{appointment}}
When the booking task completes, confirm this appointment once in plain speech.
Use its date and time in preference to older dates mentioned in the conversation.
```

`{{appointment}}` renders the whole object as compact JSON. This is input to
the model; the prompt tells it how to speak about the value.

## Name one part in a sentence

A prompt that needs only the date can read it directly:

```markdown
Appointment date: {{appointment.date}}
Use this date to answer the caller's question. If no date is recorded, ask for it.
```

The placeholder sends only that field. It does not include the booking ID,
service, or time. Nested shapes support longer paths. A path cannot select
an entry in a list; save the selected entry in its own variable first.

## Keep several records

Use a list when later steps need several records, such as complaints recorded
during the call. Use a single variable when only the latest value matters.

```yaml agent.yaml
variables:
  appointments:
    type: list[Appointment]
```

```yaml
assign:
  - appointments+: result.appointment
```

The `+` adds one item. Without it, an assignment replaces the value. A list
starts empty. A null append adds nothing, and an identical structured item
is not added twice. A changed appointment is a different item; this does not
update an older list entry by booking ID. Use a single `appointment` variable
for the latest booking instead.

## Hand a value to a tool

Sometimes the tool needs a value the model does not need to read or type.
Use `inject:` for that argument:

```yaml tools/check_availability.yaml
input:
  type: object
  properties:
    date:
      type: string
  required:
    - date
inject:
  - service: "{{requested_service}}"
local:
  handler: tools/check_availability.py
```

The model supplies `date`. The handler receives both `date` and the current
`service`. Keep injected arguments out of `input.properties` and
`input.required`.

### What happens when the value is missing

A missing or unconfirmed injected value stops the tool before it runs. The
error tells the model which task supplies or confirms the value, when one is
declared. Otherwise it asks the model to collect the missing value.

Injection is separate from prompt sharing. Tool results and spoken messages
can still contain the same value. See [Reduce context sharing step by
step](/optimization/context-scope).

## Use one in the greeting

If a name arrives with the call, declare it as a call-start value:

```yaml agent.yaml
variables:
  customer_name:
    type: str
    source: call_start
    default: there

conversation:
  greeting:
    speaks_first: agent
    text: "Hi {{customer_name}}, how can I help?"
```

The greeting renders once. It may name a value supplied at session start,
a default, or a prefetch assignment. Do not put an unconfirmed customer name
in the greeting; use [confirmation](/build/prefetch#always-check-a-value-with-the-caller)
when the call's identity still needs to be checked.

## Seed a value locally

```sh
unmute dev my-agent --var customer_name=Priya
```

Use `--var` for a declared variable with `source: call_start` or no `source`.
Values are parsed against the variable's type. For an object or list, pass
JSON and quote it for your shell.

System sources such as `from_number` depend on the phone route. LiveKit and
Pipecat supply different facts in different directions; the
[source reference](/reference/variables#sources) lists them. To exercise
prefetch and confirmation locally, use `--source from_number=+15005550006`
instead of seeding the phone variable directly.

## Secrets are not variables

Store credentials in the environment and declare their names under
`secrets:`. Never put a credential in a prompt placeholder, default, or task
result. See [Secrets](/reference/secrets).
