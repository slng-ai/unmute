Variables hold typed values for the duration of a call. Declare what each
value holds, save it from call-start data, prefetch, or a task, and reference
it in the prompts or tools that need it.

The snippets below extend an existing package. Merge them into the matching
blocks in `agent.yaml`.

## Declare a simple variable

A variable needs a name and a `type`. Start with plain text:

```yaml agent.yaml
variables:
  requested_service:
    type: str
    description: The service the caller chose for this booking.
```

`requested_service` is the name you use in assignments and prompt placeholders.
`str` means the value holds text. The declaration creates a place to save it.

A variable starts unset unless you supply an initial value. Use `default:`
only when there is a useful answer before anyone supplies one, such as a
fallback greeting name. Leave a requested service unset until it is known.

### Add a description that explains the meaning

`description:` is optional. Explain what the value means and which answer
belongs there. Include details that distinguish it from similar values,
such as whether a date is requested or already confirmed.

When a task saves the variable, Unmute includes this description in the
finish argument shown to the model. The type controls which values are
accepted; the description helps the model choose the right answer.

## Choose a type

Types give later steps a consistent value to work with. Unmute uses the
variable's type to define the task's finish argument and validate its answer
before saving it.

### Built-in types

| Type | What it holds |
|---|---|
| `str` | Free text, such as names and notes |
| `int` | A whole number |
| `float` | A number that may have a decimal part |
| `bool` | `true` or `false` |
| `Phone` | An international phone number in E.164 format |
| `Date` | Date text in `YYYY-MM-DD` format |
| `Time` | A 24-hour time in `HH:MM` format |
| `Id` | A short identifier with a defined character set |
| `EmailStr` | A valid email address, saved as plain text |
| `NameEmail` | A person and their email address, held as two fields |

`string`, `integer`, `number`, and `boolean` are aliases for `str`, `int`,
`float`, and `bool`.

### Custom types and combinations

| Form | What it holds |
|---|---|
| `Literal["value1", "value2"]` | One string from the choices you list |
| Your shape's name | An object whose fields and types you define under `shapes:` |
| `list[T]` | A list of values of type `T` |
| `T \| None` | A value of type `T`, or `null` when absence is a valid result |

`NameEmail` is an object type too, so `{{contact.name}}` and `{{contact.email}}`
read its parts. You do not declare it under `shapes:`. It is refused as a shape
name, because it already means something.

Here, `T` stands for the type you choose. Use `Literal` for a fixed set of
choices, a shape for related fields, and a list for several values. The next
section shows how to define your own object type.

The [type reference](/reference/variables#the-type-grammar) gives the exact
formats and composition rules. Your tools check business rules, such as
record existence and availability.

<Note>
LiveKit and Pipecat support all these types. The SLNG target supports basic
scalar variables: `str`, `int`, `float`, `bool`, and their aliases. It runs no
code of your package, so it has nowhere to check a shape.
</Note>

## Group related fields into a shape

A shape defines your own reusable object type. Choose a name, then declare
each field and its type under `shapes:`. Set a variable's `type:` to that
name to store an object with those fields.

One shape can be used by several variables. Each variable holds its own
value, and a task assignment saves all of the object's fields together.

For example, this package defines an object type called `Appointment` and
uses it for the variable `appointment`:

```yaml agent.yaml
shapes:
  - name: Appointment
    fields:
      - booking_id: Id
      - service: Literal["haircut", "hair-color", "blowout"]
      - date: Date
      - time: Time

variables:
  appointment:
    type: Appointment
    description: The latest appointment successfully saved by the booking tool.
```

Use the short field form, `- field_name: Type`, or add a field description
with `name:`, `type:`, and `description:`. A description on the shape explains
the whole object; a description on a field explains that part to the model.
See the [shape reference](/reference/variables#shapes-groups-fields-into-a-named-type)
for both forms.

For deciding which fields belong together, separating requested changes from
saved results, and choosing one record or a list, see
[Designing declared state](/best-practices/state-design#group-fields-that-describe-one-result).

## Save a value when a task finishes

Add this task under an agent in your package:

```yaml agent.yaml
agents:
  concierge:
    tasks:
      - name: choose_service
        when: Find out which service the caller wants.
        instructions: tasks/choose-service.md
        assign:
          - requested_service: result.service
```

```markdown tasks/choose-service.md
Find out which salon service the caller wants. Use what they have already
said and ask only if the service is missing or unclear. Then finish with
that service.
```

Here, `assign:` creates a finish argument named `service` from the
`requested_service` declaration. The task receives the conversation by default.
Its instructions say when to collect the answer and finish.

Assignments also accept whole objects. Use `appointment: result.appointment`
to save the shaped variable above. Tell a task using a tool to copy the
successful tool result and finish immediately.

All assigned values are checked before any are saved. If validation fails,
the task stays open so the model can correct the answer.

## Read a value where it is needed

Add a placeholder to each prompt that should use the saved value:

```markdown tasks/booking.md
Requested service: {{requested_service}}
Use it if present. If no service is recorded, ask which service the caller wants.
```

An unset value renders as `none recorded yet.` The instructions work before
and after the earlier task saves the service.

The owning agent also needs a reference if it should remember the result
after the task returns. It receives a completion status and its earlier
conversation, not the private conversation inside the task. This rule applies
even when the task uses `history: messages`.

### Read an object or one field

Use `{{variable}}` for the whole object, rendered as compact JSON. Use
`{{variable.field}}` for one field. A dotted path can follow nested shapes.
To read fields from a list item, first save that item in its own variable.

Tell the prompt how to use the value and what to do when it is missing.

## Keep several records

Declare `type: list[T]` when later steps need several values of the same
type. A list starts as `[]`.

In a task's `assign:`, use `variable+: result.field` to append one item or
`variable: result.field` to replace the list. Appending skips `null` and
identical structured items. See
[assignment rules](/reference/variables#assigning-a-task-result-to-a-variable)
for details, and [state design](/best-practices/state-design#choose-a-current-value-or-a-list)
to choose between a current value and a list.

## Hand a value to a tool

Sometimes the tool needs a value the model does not need to read or type.
Use `inject:` for that argument:

```yaml tools/check_availability.yaml
input:
  type: object
  properties:
    date:
      type: string
  required:
    - date
inject:
  - service: "{{requested_service}}"
local:
  handler: tools/check_availability.py
```

The model supplies `date`. The handler receives both `date` and the current
`service`. Keep injected arguments out of `input.properties` and
`input.required`.

### What happens when the value is missing

A missing or unconfirmed injected value stops the tool before it runs. The
error tells the model which task supplies or confirms the value, when one is
declared. Otherwise it asks the model to collect the missing value.

Injection is separate from prompt sharing. Tool results and spoken messages
can still contain the same value. See [Reduce context sharing step by
step](/best-practices/context-scope).

## Use one in the greeting

If a name arrives with the call, declare it as a call-start value:

```yaml agent.yaml
variables:
  customer_name:
    type: str
    source: call_start
    default: there

conversation:
  greeting:
    speaks_first: agent
    text: "Hi {{customer_name}}, how can I help?"
```

The greeting renders once. It may name a value supplied at session start,
a default, or a prefetch assignment. Do not put an unconfirmed customer name
in the greeting; use [confirmation](/build/prefetch#always-check-a-value-with-the-caller)
when the call's identity still needs to be checked.

## Seed a value locally

```sh
unmute dev my-agent --var customer_name=Priya
```

Use `--var` for a declared variable with `source: call_start` or no `source`.
Values are parsed against the variable's type. For an object or list, pass
JSON and quote it for your shell.

System sources such as `from_number` depend on the phone route. LiveKit and
Pipecat supply different facts in different directions; the
[source reference](/reference/variables#sources) lists them. To exercise
prefetch and confirmation locally, use `--source from_number=+15005550006`
instead of seeding the phone variable directly.
