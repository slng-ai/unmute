title: "Variables"
description: "Personalize a call, let the model save what it hears, and pass values into a tool without showing them to the model."
---

A variable is a named value that lives for one call. Use it to greet someone by
name, to remember what they asked for, and to hand a tool a value the model
should never see.

This page teaches the common workflow. For every type, source, and supported
location, use the [Variables reference](/reference/variables).

Every snippet below is a worked example you can paste into a package of your
own. No shipped example declares a `call_start` variable, so the commands here
name `my-agent`: the package you get from
[`unmute init`](/reference/cli/init), with the `variables:` block below added.

## Declare them

```yaml agent.yaml
variables:
  customer_name:
    type: string
    source: call_start
    default: there
    description: Caller's first name, used in the greeting and the prompt.
  customer_id:
    type: string
    source: call_start
    default: cus_1001
    description: CRM id of the caller. The booking tool receives it directly; never say it out loud.
  requested_service:
    type: string
    source: conversation
    description: The service the caller wants, for example a haircut or a colour. Save it as soon as they say it.
```

`type` is one of `string`, `number`, `integer`, `boolean`. `source` says where
the value comes from, and it changes what you can do with the variable.

| Source | Who sets it | When |
|---|---|---|
| `call_start` | whatever starts the call | before the first word |
| `conversation` | the model, during the call | whenever the caller says it |
| system sources such as `from_number`, `direction`, `call_id` | the phone adapter | on a phone call, when the route grants that fact. LiveKit's two routes grant the most; Pipecat's two Twilio routes grant a smaller set, each in one direction only for a phone number |

A system source works the same way whether you put it straight on a variable's
own `source:` or read it through a [`prefetch:`](/build/prefetch) entry: both
read the same route table, so the fact hydrates on whichever route grants it.
See the [Variables reference](/reference/variables#sources) for the full grid.

## Use one in the greeting

```yaml
conversation:
  greeting:
    speaks_first: agent
    text: "Hi {{customer_name}}, thanks for calling Sage and Stone Salon. What can I do for you?"
```

`{{name}}` renders the variable's value. The greeting and the prompt render
once, at the start of the call, so they can only name a variable that already
has a value: a `call_start` variable, or one with a `default`.

## Seed a value locally

In production the values arrive with the call. On your machine, `--var` stands
in for that:

```sh
unmute dev my-agent --var customer_id=cus_2002
```

It is repeatable, so several values seed one call:

```sh
unmute dev my-agent \
  --var customer_name=Priya \
  --var customer_id=cus_2002
```

Leave the flags out and the declared defaults are used, so the agent always has
something to say.

`--var` seeds the variables the dispatch payload fills: `source: call_start`,
and a variable that declares no `source:` at all. It refuses anything else
instead of accepting it and dropping it:

```text wrap
unmute: dev my-agent: --var requested_service=haircut: "requested_service" has source conversation, so the model saves it mid-call through update_variables, not you
```

An undeclared name is refused the same way.

## Let the model save one

Declaring a variable with `source: conversation` creates a tool called
`update_variables` in the generated project. You do not write it. The model
calls it when the caller says something worth keeping.

Say "I'd like a haircut" and `requested_service` is stored for the rest of the
call.

## Hand a value to a tool

This is the part worth internalizing. A tool's `input:` schema is everything
the model sees. `inject:` adds arguments the model never sees:

```yaml tools/book_appointment.yaml
input:
  type: object
  properties:
    slot_id:
      type: string
      description: ID returned by check_availability
  required:
    - slot_id

inject:
  customer_id: "{{customer_id}}"
  service: "{{requested_service}}"
```

The model is offered a one parameter function, `book_appointment(slot_id)`.
Your handler takes all three as ordinary arguments and knows nothing about
variables:

```python tools/book_appointment.py
def book_appointment(customer_id, service, slot_id):
    ...
```

The generated project renders the `{{tokens}}` from the live call state at the
moment of the call and passes them by keyword.

<Note>
  `inject:` renders on every call, not once at the start. That is why
  `{{requested_service}}` is legal here even though nobody has said it yet when
  the call begins.
</Note>

### What happens when the value is missing

An injected variable with no value refuses the call rather than sending a half
formed request. The model gets told why:

```text
cannot call book_appointment yet: requested_service not set. Ask the caller first.
```

So the model asks. `customer_id` never trips this, because it declares a
default.

## Group related fields into a shape

Some values are not one thing. A booking has a date, a time and a service.
Instead of three separate variables, declare a shape once and give a
variable that shape as its type:

```yaml agent.yaml
shapes:
  - name: Appointment
    description: One thing being booked, moved or cancelled.
    fields:
      - scheduled_date: Date
      - scheduled_time: Time
      - name: appointment_type
        type: Literal["haircut", "haircolor", "dry_cut"]
        description: The service the caller asked for, in the salon's own words.

variables:
  appointments:
    type: list[Appointment]
    description: What this call has booked so far, in the order the caller gave them.
```

A task fills it the same way it fills any variable, through `assign:`. The
`+` appends the result to the list instead of replacing it, so a second
booking in the same call does not erase the first:

```yaml agent.yaml
      - name: book
        instructions: tasks/book.md
        assign:
          - appointments+: result.appointment
        result:
          appointment: Appointment
          summary: string
        context:
          history: reset
```

## Read the block the compiler adds

Every agent prompt and every task prompt gets one more thing after your own
text, written by the compiler and never by you:

```text
Conversation info:
What this call has established so far. Read it rather than re-reading the
conversation, and never ask for something already recorded here.
1. Appointments: [{"scheduled_date":"2026-09-10","scheduled_time":"10:00","appointment_type":"haircut"}]
```

Before anything is booked, the same line renders as:

```text
1. Appointments: none recorded yet.
```

never as `[]` or `null`, so a step can tell "not yet known" from "known to be
nothing". Add a field to the shape and every prompt shows it, with no prompt
file touched.

For the full type grammar a shape's fields and a variable's `type:` can use,
see the [Variables reference](/reference/variables).

## Secrets are not variables

`{{...}}` renders variables only. Naming a secret in a template is a compile
error, not a value that leaks at run time:

```text
unmute: validate my-agent: build: agent.yaml:70: conversation.greeting.text
references {{OPENAI_API_KEY}}, but secrets never flow through templates; a secret
reaches a tool through its own *_env field
```

The file and the line are always there.

A template renders into speech, a prompt, a URL, or a log. That is right for a
name and wrong for a token. See [secrets](/reference/secrets).

## Try it

```sh
unmute dev my-agent --var customer_id=cus_2002
```

Seeding `customer_id` is the same thing a production call does when it already
knows who is calling. Put `requires: customer_id` on a task and the step
goes straight through with a value already set, while without the flag the agent
has to ask first. That difference is the variable doing its job.

That difference is also the whole idea behind [pre-fetch](/build/prefetch): fill
a value before the greeting and the step that existed to collect it is skipped,
with no edit to the step itself.
