title: "Variables"
description: "Declare a type once, save a task's result, and use it only where it is needed."
---

Use a variable when a later task or agent needs a reliable fact from this call.
For example, after moving a booking, save the new appointment. The next task
can use its current date without trying to resolve conflicting dates in the
conversation.

A variable lives for one call. It is not a database record. Your tools save
changes in your booking system; variables let the agent use the result later.

There are three choices: **declare** what a value holds, **save** it when a
task finishes, and **read** it in each prompt or tool that needs it. Saving a
value does not automatically share it with any prompt.

The snippets below extend an existing package. Merge them into the matching
blocks in `agent.yaml`; do not add duplicate top-level keys.

## Declare a simple variable

A variable needs a name and a `type`. Start with plain text:

```yaml agent.yaml
variables:
  requested_service:
    type: str
    description: The service the caller chose for this booking.
```

`requested_service` is the name you use in assignments and prompt placeholders.
`str` means the value holds text. Declaring it creates a place to save a value;
it does not ask the caller a question or fill the value from the conversation.

A variable starts unset unless you supply an initial value. Use `default:`
only when there is a useful answer before anyone supplies one, such as a
fallback greeting name. Leave a requested service unset until it is known.

### Add a description that explains the meaning

`description:` is optional. Use it to explain what the value means and which
answer belongs there. "The new date selected by the caller" is more useful
than "A date": it distinguishes the request from the date already booked.

When a task assigns this variable, Unmute uses its description to describe
the generated finish argument to the model. The type defines which values
are accepted; the description helps the model choose the right one. The
description is guidance, not a validation rule or a prompt placeholder. It
does not give another task access to the saved value.

## Choose a type

Types make saved answers predictable. A `bool` gives later steps a yes or no
value; a `Literal` keeps service names within the choices your tool accepts;
a `Time` keeps times in one format. Unmute derives the task's finish arguments
from these types and checks the values before saving them. You do not write
the same types again on each task.

These are all the supported built-in types and ways to combine them. Names
are case-sensitive.

| Type | What it holds | Example value | Why use it |
|---|---|---|---|
| `str` | Free text | `haircut` | Names, notes, email addresses, or external keys with arbitrary punctuation |
| `int` | A whole number | `2` | Counts that must not have a decimal part |
| `float` | A number that may have a decimal part | `12.5` | Measurements or other numeric values |
| `bool` | A yes or no value | `true` | A fact later steps can check without interpreting text |
| `Phone` | International phone number text | `+15005550006` | One leading `+` and 7 to 15 digits, with a nonzero first digit |
| `Date` | Date text | `2026-09-12` | Consistent `YYYY-MM-DD` format |
| `Time` | Time text | `11:30` | Valid hours and minutes in 24-hour `HH:MM` format |
| `Id` | Identifier text | `bkg_1001` | 1 to 64 characters; starts with a letter or digit, then permits letters, digits, `.`, `-`, `_`, and `:` |
| `Literal["haircut", "hair-color", "blowout"]` | One of the listed strings | `haircut` | A fixed set of accepted choices |
| A shape name, such as `Appointment` | An object with fields you declare | A booking ID, date, and time together | Save related facts as one record |
| `list[T]`, such as `list[Appointment]` | Several values of the same type | An array of appointment objects | Keep more than one value |
| `T \| None`, such as `Date \| None` | A scalar or shape that may be absent | A date or `null` | Allow a successful task to report that no value exists |

`string`, `integer`, `number`, and `boolean` are aliases for `str`, `int`,
`float`, and `bool`. `None | T` means the same thing as `T | None`.

There is no built-in `Email` type. Use `str` for an email address and check it
in your tool if needed. `Phone` checks format, not whether a number exists or
belongs to the caller. `Date` checks the text format, not calendar validity
or booking availability. Your tools still check those facts. Keep timezone
separately from `Date` and `Time`.

For the salon's fixed service menu, replace `str` in the first declaration:

```yaml agent.yaml
variables:
  requested_service:
    type: Literal["haircut", "hair-color", "blowout"]
    description: The service the caller chose for this booking.
```

Now a task must finish with one of those three strings. Keep `str` instead
when any service name is allowed.

A value can be unset before a task runs even without `| None`. Add `| None`
only when absence is a valid result to save. Lists start as `[]`; they cannot
also be nullable or directly contain another list. A shape can contain lists
and other shapes, but cannot refer back to itself. See the
[type reference](/reference/variables#the-type-grammar) for the full grammar
and validation limits.

<Note>
LiveKit and Pipecat support all these types. The SLNG target supports only
basic scalar variables (`str`, `int`, `float`, `bool` and their aliases);
it does not support tasks or the other types on this page.
</Note>

## Group related fields into a shape

A shape is a type you define by naming its fields and their types. A booking's
ID, service, date, and time describe one appointment. Grouping them lets a task
save one complete record, instead of updating separate variables that might
end up describing different bookings:

```yaml agent.yaml
shapes:
  - name: Appointment
    fields:
      - booking_id: Id
      - service: Literal["haircut", "hair-color", "blowout"]
      - date: Date
      - time: Time

variables:
  appointment:
    type: Appointment
    description: The latest appointment successfully saved by the booking tool.
```

`Appointment` defines the record's structure. The `appointment` variable
holds one record of that type for this call. You can reuse the shape for other
variables without declaring its fields again.

The short field form, such as `- date: Date`, is enough when the meaning is
clear. To explain a field, replace that line with the longer form:

```yaml
- name: date
  type: Date
  description: The date successfully saved by the booking tool, not a requested change.
```

A field description guides the model filling that field. You can also add a
`description:` to the shape itself to explain the record as a whole. The
field types check its structure; the task prompt must still say to copy the
successful tool result.

For deciding which fields belong together, separating requested changes from
saved results, and choosing one record or a list, see
[Designing declared state](/best-practices/state-design#group-fields-that-describe-one-result).

## Save a value when a task finishes

Add this task under an agent in your package:

```yaml agent.yaml
agents:
  concierge:
    tasks:
      - name: choose_service
        when: Find out which service the caller wants.
        instructions: tasks/choose-service.md
        assign:
          - requested_service: result.service
```

```markdown tasks/choose-service.md
Find out which salon service the caller wants. Use what they have already
said and ask only if the service is missing or unclear. Then finish with
that service.
```

The task gets the conversation by default. `assign:` gives its generated
finish call a `service` argument with the type of `requested_service`. You
declare the type once, on the variable. You do not write a separate task
result schema or ask the owning agent to repeat the caller's request.

Unmute checks the finish arguments before saving them. If validation fails,
the task stays open so the model can correct the value. An ordinary tool
result does not fill a variable by itself: the task must finish.

### Save a shaped result

In a booking task, add:

```yaml
assign:
  - appointment: result.appointment
```

Write the task's instructions to copy the successful tool result and finish
immediately.

## Read a value where it is needed

Add a placeholder to each prompt that should use the saved value:

```markdown tasks/booking.md
Requested service: {{requested_service}}
Use it if present. If no service is recorded, ask which service the caller wants.
```

An unset value renders as `none recorded yet.` The instructions work before
and after the earlier task saves the service.

The owning agent also needs a reference if it should remember the result
after the task returns. It receives a completion status and its earlier
conversation, not the private conversation inside the task. This rule applies
even when the task uses `history: messages`.

### Read a shaped result

Have the owner confirm the saved appointment to the caller:

```markdown instructions.md
Latest saved appointment: {{appointment}}
When the booking task completes, confirm this appointment once in plain speech.
Use its date and time in preference to older dates mentioned in the conversation.
```

`{{appointment}}` renders the whole object as compact JSON. This is input to
the model; the prompt tells it how to speak about the value.

## Name one part in a sentence

A prompt that needs only the date can read it directly:

```markdown
Appointment date: {{appointment.date}}
Use this date to answer the caller's question. If no date is recorded, ask for it.
```

The placeholder sends only that field. It does not include the booking ID,
service, or time. Nested shapes support longer paths. A path cannot select
an entry in a list; save the selected entry in its own variable first.

## Keep several records

Use a list when later steps need several records, such as complaints recorded
during the call. Use a single variable when only the latest value matters.

```yaml agent.yaml
variables:
  appointments:
    type: list[Appointment]
```

```yaml
assign:
  - appointments+: result.appointment
```

The `+` adds one item. Without it, an assignment replaces the value. A list
starts empty. A null append adds nothing, and an identical structured item
is not added twice. A changed appointment is a different item; this does not
update an older list entry by booking ID. Use a single `appointment` variable
for the latest booking instead.

## Hand a value to a tool

Sometimes the tool needs a value the model does not need to read or type.
Use `inject:` for that argument:

```yaml tools/check_availability.yaml
input:
  type: object
  properties:
    date:
      type: string
  required:
    - date
inject:
  - service: "{{requested_service}}"
local:
  handler: tools/check_availability.py
```

The model supplies `date`. The handler receives both `date` and the current
`service`. Keep injected arguments out of `input.properties` and
`input.required`.

### What happens when the value is missing

A missing or unconfirmed injected value stops the tool before it runs. The
error tells the model which task supplies or confirms the value, when one is
declared. Otherwise it asks the model to collect the missing value.

Injection is separate from prompt sharing. Tool results and spoken messages
can still contain the same value. See [Reduce context sharing step by
step](/best-practices/context-scope).

## Use one in the greeting

If a name arrives with the call, declare it as a call-start value:

```yaml agent.yaml
variables:
  customer_name:
    type: str
    source: call_start
    default: there

conversation:
  greeting:
    speaks_first: agent
    text: "Hi {{customer_name}}, how can I help?"
```

The greeting renders once. It may name a value supplied at session start,
a default, or a prefetch assignment. Do not put an unconfirmed customer name
in the greeting; use [confirmation](/build/prefetch#always-check-a-value-with-the-caller)
when the call's identity still needs to be checked.

## Seed a value locally

```sh
unmute dev my-agent --var customer_name=Priya
```

Use `--var` for a declared variable with `source: call_start` or no `source`.
Values are parsed against the variable's type. For an object or list, pass
JSON and quote it for your shell.

System sources such as `from_number` depend on the phone route. LiveKit and
Pipecat supply different facts in different directions; the
[source reference](/reference/variables#sources) lists them. To exercise
prefetch and confirmation locally, use `--source from_number=+15005550006`
instead of seeding the phone variable directly.

## Secrets are not variables

Store credentials in the environment and declare their names under
`secrets:`. Never put a credential in a prompt placeholder, default, or task
result. See [Secrets](/reference/secrets).
