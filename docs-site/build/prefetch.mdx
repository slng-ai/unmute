---
title: "Pre-fetch"
description: "Look up what you already know before the call starts, so the agent never has to ask."
---

Some things are true before the caller says hello. Today's date. The number they
are calling from. What your records say about that number.

`prefetch:` looks those up once, before the greeting, and puts them in variables.

## Why

Without it, the agent finds things out by talking. Our own salon agent used to:

- ask the caller to read out a phone number the phone network had already handed over;
- call one tool to ask what today was, then a second one to check the diary, just to understand "tomorrow".

Both are questions with answers you already had.

## What it can fetch

| Write this | And you get |
|---|---|
| `clock: date` | today's date, in your timezone |
| `source: from_number` | the number the caller is calling from |
| `tool: look_up_customer` | whatever one of your read-only tools returns |

Nothing else. If the caller has to decide it, the agent has to ask for it.

## How to write it

Each entry has a name, one thing to fetch, and where to put the answer.

```yaml agent.yaml
timezone: Europe/Madrid

prefetch:
  - name: today
    clock: date
    assign:
      - booking_date: result.date

  - name: caller
    source: from_number
    assign:
      - customer_phone: result.value

  - name: profile
    tool: look_up_customer
    args:
      - phone: "{{customer_phone}}"
    assign:
      - customer_name: result.name
```

Declare the variables it fills like any others, with a type and a default:

```yaml agent.yaml
variables:
  booking_date:
    type: string
    default: ""
  customer_phone:
    type: string
    default: ""
  customer_name:
    type: string
    default: ""
```

Now `{{booking_date}}` works in a prompt.

## Order matters

Entries run top to bottom. Above, `caller` gets the number and `profile` uses it.
Swap them and the compiler stops you:

```text wrap
agent.yaml:196: prefetch "profile" reads {{customer_phone}}, which prefetch "caller" assigns further down the list. Entries resolve in the order you wrote them: move "caller" above "profile"
```

## Three rules

**A clock needs a `timezone:`.** Containers run on UTC. Without one, a salon in
Spain taking a late booking for "tomorrow" writes down the wrong day.

**A tool needs `read_only: true`.** A pre-fetch runs on every call, right number
or wrong one, so it can only call a tool that reads:

```yaml tools/look_up_customer.yaml
read_only: true

local:
  handler: tools/salon.py
```

The compiler trusts that line, it cannot check your handler. Point a pre-fetch at
a lookup, never at anything that creates or changes a record.

**`assign:` and `args:` are lists.** One pair per `- ` line.

## Ask before you trust a phone number

The network tells you which handset called, not who is holding it. People call
from a partner's phone, or from work, or have two accounts.

`confirm:` names the step that has to hear the caller agree:

```yaml agent.yaml
variables:
  customer_phone:
    type: string
    default: ""
    confirm: customer_verification
```

Until that happens the value is held back:

- it appears in no prompt except that step's own;
- it will not unlock a step that `requires:` it;
- any tool handed it refuses to run, and says what it is waiting for.

It spreads, too. `customer_name` came from an unconfirmed number, so it is
unconfirmed as well. That is what stops the agent greeting a stranger by the
account holder's name.

Then write the step to read the number back:

```md tasks/verify-customer.md
The call came from {{customer_phone}}. If there is a number there, read it back
and ask if it is the right one for the booking. If it is empty, ask for a number.
```

The step now confirms instead of collecting.

## When there is nothing to fetch

This happens often:

- on your machine, `unmute dev` has no phone network;
- **no Pipecat route supplies a caller number**, so `source: from_number` works on LiveKit `sip` and `connector` only;
- a caller can withhold their number;
- your lookup will not know a first-time customer.

The entry is skipped, and so is any later entry that needed its answer. The
variables keep their defaults and the call goes ahead. `unmute validate` names
the entries that will always be skipped on a target, so read it before you ship.

Write prompts that still read properly when the value is empty. An empty variable
prints nothing at all.

<Tip>
  Write the sentence for the empty case first, then check it still sounds right
  once the value is there. The other way round gives you "Your number is ." on
  every call that skipped.
</Tip>

A pre-fetch cannot break a call. There is a time limit, and a lookup that is too
slow or fails is stepped over. Every entry logs what happened:

```text
prefetch today: resolved booking_date=2026-09-01
prefetch caller: skipped, the call carries no from_number
prefetch profile: skipped, customer_phone is empty
```

<Note>
  Not available on the `slng` target, which starts the session itself. A package
  declaring `prefetch:` for it is refused, and told to put the value in the
  agent's instructions instead.
</Note>

## Try it

Your machine has no caller ID, so stand in for one:

```sh
unmute dev examples/salon-concierge --source from_number=<a number in E.164>
```

Use a number your lookup knows and the agent should read it back and ask for a
yes. Leave the flag off and it should ask from scratch. Both happen in
production, so listen to both.

<Warning>
  Do not use `--var` for this. It writes the number straight in, skips the
  pre-fetch and marks nothing as needing confirmation, so your local run acts on
  a number it never read back.
</Warning>
