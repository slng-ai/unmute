Choose an architecture around the work your agent must complete. Cascade gives
you separate control over listening, reasoning, and speech, with more room for
complex workflows. Realtime and Live favor direct audio interaction and can
reduce the pause before a reply.

`architecture:` in `agent.yaml` selects the pipeline. Cascade is the default;
the other two use speech-to-speech models with different controls in Unmute.

```yaml agent.yaml
architecture: cascade     # the default; leave it out and you get this
```

## The three shapes

**`cascade`** separates speech recognition, reasoning, and speech generation.
Turn detection decides when to answer. You choose each role from the supported
providers, and can change one without replacing the whole pipeline.

**`realtime`** sends audio to one model on a Realtime API. It can answer with
its own voice or send text to a separate synthesizer. You choose the turn mode.

**`live`** uses a Live API model that listens, speaks, and controls its own
turns. Tool work goes to a separate reasoning model named as its backend.

## Pros and cons

| Architecture | Pros | Cons |
|---|---|---|
| [Cascade](/build/architecture/cascade) | Independent model choices and clearer stage-by-stage diagnosis; Unmute's richest workflow controls on LiveKit and Pipecat | More components to tune and usually more latency; reasoning sees a transcript rather than the caller's tone |
| [Realtime](/build/architecture/realtime) | Direct audio understanding, potentially quicker replies, a choice of turn mode and optional separate voice | Less freedom to change the reasoning model; Unmute currently limits it to one agent without tasks or saved state |
| [Live](/build/architecture/live) | The model handles turns, with a separate backend for tool work | No authored turn controls or separate synthesizer; Unmute currently limits it to one agent without tasks or saved state |

**The extra control is often worth the latency.** If a call must collect details,
confirm them, run an action, and recover when it fails, choose the architecture
that lets you express those steps clearly. A faster first reply is only one
part of a successful call.

## Every key this page adds

One key, at the top level of `agent.yaml`. It is read before anything else in
the file, because it decides which `models:` sections are legal.

<ParamField path="architecture" type="cascade | realtime | live">
  Which pipeline to build. Left out, you get `cascade`, which is what every
  package written before this key existed gets. An agent that binds a shape the
  key does not name is refused, and the message names the architecture rather
  than the binding.
</ParamField>

## Which to pick

**Does the call need several steps, tasks, handoffs, or saved values?** Start
with `cascade` on LiveKit or Pipecat. Those are current Unmute capabilities;
speech-to-speech models are not inherently unable to run complex applications.

**Do you need independent transcription, reasoning, and voice choices?** Use
`cascade`. Choose supported providers for each role. Realtime also lets you
keep a separate synthesizer, but its audio understanding and reasoning stay
with the realtime model.

**Is direct audio interaction the main priority?** Consider `realtime` or
`live` if their current limits fit the use case. Choose Realtime for control
over turns and voice; choose Live for automatic turns and a backend for tool work.

Compare a complete interaction: correct inputs, successful actions, recovery,
and response time. No architecture guarantees the fastest or cheapest result
for every model, network, and tool workload.

## What each one costs

These are **current Unmute capabilities**, not universal limits of the model APIs.

| | `cascade` | `realtime` | `live` |
|---|---|---|---|
| Main models | separate transcription, reasoning, and speech | one audio model; optional synthesizer | one audio model; backend for tools |
| Provider choice | independent per role | audio model; optional separate voice provider | live model and a backend at the same provider |
| Who decides the turn | supported detector or listener | your selected turn mode | the model |
| Tasks and handoffs | LiveKit and Pipecat | no | no |
| Saved call state | yes, with target-specific limits | no | no |
| Phone calls | supported routes | no | no |

Cascade gives you more places to tune quality, cost, and timing. Those choices
also mean more integrations to manage. Speech-to-speech removes some stage
boundaries, but tools, network calls, and turn timing still add delay.

## Which sections each one takes

| Section | `cascade` | `realtime` | `live` |
|---|---|---|---|
| `models.listen` | required | refused | refused |
| `models.think` | required | no agent binding | the `backend:` entry |
| `models.speak` | required | the half cascade | refused |
| `models.turn` | optional | refused | refused |
| `models.realtime` | refused | required | refused |
| `models.live` | refused | refused | required |

An unused reasoning entry can remain in a Realtime package, but the agent
cannot bind it with `think:`. Target restrictions still apply to every shape.
A refused section is named in the validation error with its source line.

## What compiles where

| Architecture | LiveKit | Pipecat | slng |
|---|---|---|---|
| `cascade` | yes | yes | yes |
| `realtime` | yes | yes | no |
| `live` | yes | yes | no |

A cell that says no is a refusal at compile, with a sentence saying which
architecture to write or which target to compile to. The slng target binds
listen, think and speak by name, so it has no slot for one model that does all
three. That is a fact about the target, not a gap in a driver.

## Troubleshooting

**"models.listen is not used under architecture: live"** you moved a package
to a speech-to-speech shape and left the cascade's sections behind. Delete them.
The model does that job now.

**"architecture: live has no place for tasks"** the message names
`architecture: realtime` as the shape whose session takes new instructions
mid-call, and then says it carries no tasks either. Both are true. Today the
answer is `architecture: cascade`.

**"slng target ... has no slot for one model that does all three"** compile to
`livekit` or `pipecat`, or write `architecture: cascade`.
