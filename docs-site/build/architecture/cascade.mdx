title: "Cascade"

Choose Cascade when your agent needs control over each stage and a workflow
with several steps. It usually adds latency, but lets you choose how the agent
hears, reasons, speaks, and moves between tasks.

Speech recognition produces text, a reasoning model writes a reply, and speech
synthesis turns it into audio. Turn detection decides when to answer. The
stages can overlap through streaming, which reduces the wait between them.

Leave `architecture:` out and Unmute uses `cascade`. This partial example shows
the bindings; merge it into an existing package and supply a real voice ID.

```yaml agent.yaml
models:
  listen:
    ears:
      provider: deepgram
      model: nova-3
  think:
    brain:
      provider: openai
      model: gpt-5.6-terra
  speak:
    mouth:
      provider: cartesia
      model: sonic-3
      voice: "a-voice-id"

agents:
  desk:
    instructions: instructions.md
    listen: ears
    think: brain
    speak: mouth
```

## Why pick it

### Pros

- **Control the workflow.** On LiveKit and Pipecat, combine tasks, handoffs, saved values, and tool calls. Each step can have its own instructions and access to the values it needs.
- **Choose each role.** Use a supported transcriber, reasoning model, and voice independently. Spend more on the part that needs better quality without replacing the others.
- **Find the failing stage.** Compare the recognized text, model reply, tool result, and spoken output. A wrong transcription needs a different fix from a failed tool.

### Cons

- **More sources of delay.** Turn detection, transcription, reasoning, speech generation, and tools all contribute. Streaming reduces the wait, but does not remove those costs.
- **More parts to operate.** Several integrations bring separate credentials, availability limits, and failure modes.
- **Less audio context for reasoning.** A transcript carries the words, but can lose tone, hesitation, and other clues in the caller's voice.

[LiveKit's comparison](https://livekit.com/blog/realtime-vs-cascade) explains these
component tradeoffs. [Coval's comparison](https://www.coval.ai/blog/speech-to-speech-vs-cascaded-voice-ai-which-architecture-should-you-deploy/)
shows why control and diagnosis matter when the agent must complete real work.

## Build a more complex workflow

Consider a caller who wants to change an existing request:

1. Look up the request with a tool.
2. Collect the change in a task and save the result.
3. Confirm the details before running the update tool.
4. Handle a refused update, or hand the conversation to another agent with the context it needs.

In a cascade package on LiveKit or Pipecat, those can be separate
[tasks](/build/orchestration/tasks) using [saved values](/build/variables).
The prompts name what each step may read, and your tool enforces the conditions
for changing the record. This gives you more control than putting every step
into one large prompt.

That control does not make a tool call automatically correct. Test the successful
path, missing inputs, and failed actions. The value of cascade is having clear
places to express and check that behavior.

<Note>
  Tasks, groups, and handoffs are supported on Unmute's LiveKit and Pipecat
  cascade targets. SLNG also uses a cascade, but has its own
  [target limits](/targets/slng#what-a-slng-package-may-not-ask-for).
  Realtime and Live support tools today, but Unmute does not yet give them
  these task and state controls.
</Note>

## The four roles

| Role | What it does | Where it is taught |
|---|---|---|
| `listen` | turns the caller's audio into text | [Transcription](/models/stt) |
| `think` | reads the text and writes the reply | [Reasoning](/models/llm) |
| `speak` | turns the reply into audio | [Voices](/models/tts) |
| `turn` | decides the caller has finished | [Turn detection](/models/turn-detection) |

`listen`, `think` and `speak` are required. `turn` is optional, and left out
each target builds its own default.

## What it costs

The tradeoff is usually a longer wait for the first audio than a comparable
speech-to-speech setup. It is not a fixed penalty: model choice, turn timing,
network placement, and tool calls all affect it.

Transcription can run while the caller speaks, and speech synthesis can begin
while the model is still generating text. Do not add every stage's duration
as though all work happens one stage at a time. See
[where the time goes](/optimization/latency#where-the-time-goes).

Start by tuning the slow stage. Keep the workflow controls that your use case
needs, then compare response time and completed actions with an alternative.
The [architecture overview](/build/architecture/overview#pros-and-cons) puts the
tradeoffs side by side.

## Troubleshooting

**The agent answers too slowly.** Start with
[Turn taking](/optimization/turn-taking). The silence window before the turn
ends is usually the largest single piece, and it is one line.

**The agent interrupts the caller.** The same page, in the other direction. A
shorter window answers faster and cuts people off more.

**A vendor name is refused.** Each role has its own list, and an unlisted name
is refused with the list. The role pages above carry them.
