One agent with a good prompt and a few tools handles more than you would expect.
When it stops being enough, there are three shapes to reach for.

New here? Read [How a package fits together](/build/how-a-package-fits-together)
first. It is one page, it answers "I want two agents, each with tasks, where do I
start?", and everything below assumes it.

| Shape | What it is | Where it is taught |
|---|---|---|
| **Handoff** | one agent gives the caller to another, and does not get them back | [Handoffs](/build/orchestration/handoffs) |
| **Task** | a short step the agent runs, which returns a typed result | [Tasks](/build/orchestration/tasks) |
| **Task group** | several tasks in a fixed order, sharing what they learn | [Task groups](/build/orchestration/task-groups) |

The difference that matters most is whether control comes back. A task returns. A
handoff does not.

None of these is how you reach a person: that is an
[escalation](/transfers/overview), and what it can do depends on the phone route.

## Five lists, four catalogs

Whichever shape you reach for, you write it the same way. An agent declares
what it can do in five lists, one per kind. Four of those have a top-level
catalog of the same name; the fifth, tasks, is nested right inside the agent
that defines it:

| Agent list | Catalog | What it does |
|---|---|---|
| `tools:` | `tools:` | does work and returns a value |
| `tasks:` | nested in the agent | runs a focused step, then control returns |
| `task_groups:` | `task_groups:` | runs several tasks in a fixed order, then control returns |
| `handoffs:` | `handoffs:` | the conversation becomes another agent, and never returns |
| `escalations:` | `escalations:` | the caller goes through to a person |

Which block a thing is written in is its kind, so nothing carries a `kind:`
field. [How a package fits together](/build/how-a-package-fits-together) walks
through a complete file.
