---
title: "Handoffs"
description: "One agent gives the caller to another, with different rules and different tools."
---

A handoff moves the caller from one agent to another. The new agent has its own
prompt, its own tools, and the call for good: nothing comes back.

Reach for it when two jobs have genuinely different rules, not just different
paragraphs. One prompt can only get so long before it starts contradicting itself.

Use a handoff instead of the other shapes when:

- nothing should come back. A [task](/build/orchestration/tasks) returns with
  a result; a handoff never does.
- the split is between two roles with different tools or permissions, not a
  fixed sequence of steps one role runs through in order, which is what a
  [task group](/build/orchestration/task-groups) is for.
- the same conversation might need to come back later. That is a second
  handoff in the other direction, not an automatic return.

The YAML on this page is one worked pair of agents. For a shipped package that
does it, read `examples/salon-concierge`: `concierge` handles bookings and
`complaint_specialist` handles complaints, with a control in each direction.

## Two agents in one package

```yaml agent.yaml
entry_agent: booking_desk

agents:
  booking_desk:
    instructions: instructions.md
    model: reasoning
    voice: voice
    handoffs:
      - to_appointment_manager

  appointment_manager:
    instructions: agents/appointment-manager.md
    model: reasoning
    voice: voice
    handoffs:
      - to_booking_desk
```

`entry_agent` decides who answers. Each agent has its own prompt file. They can
share models, or not.

## The handoff

You declare a handoff once under `handoffs:`, then put its name in the
`handoffs:` list of the agent or task that may use it. That pairing is the whole
model: every agent-level list has a same-named top-level catalog, and you attach
by name.

```yaml agent.yaml
handoffs:
  to_appointment_manager:
    to: appointment_manager
    when: The caller wants to reschedule or cancel an existing appointment.
    announce: "I’m connecting you with our appointment manager now."
    context:
      history: full
      variables: all

  to_booking_desk:
    to: booking_desk
    when: The caller wants to make a new appointment instead.
    announce: "I’m connecting you back to the booking desk for your new appointment."
    context:
      history: full
      variables: all
```

`when` is the condition the model reads. Write it as the situation, not as an
instruction to call a tool.

`announce` is optional. Write the exact short sentence the active agent should
speak. It is spoken once and finishes before the new agent takes over; the
model does not paraphrase it. Leave it out for a silent handoff. A failed
`requires` guard is checked first and never makes a false announcement.

`requires` is not handoff-only. It is legal on a delegate too, and that is
usually the better place for it: guard the step that needs the value rather than
the route to it. See [Guarding a step](/build/orchestration/tasks#guarding-a-step).
Never guard the way to a person, though. A caller who asks for a manager should
not be interviewed before anyone will route them.

Prefer a silent handoff when agents are internal roles behind one service. The
caller can keep talking to the same salon, clinic, or support desk without
hearing implementation details such as “I’m connecting you to another agent.”

`context` decides what the new agent knows. It is the whole of what travels:

| Field | What it does |
|---|---|
| `history: full` | the new agent sees the conversation so far |
| `variables: all` | the values collected so far travel with the caller |

Without them, the caller gets asked for their phone number twice.

`variables:` also accepts a list of names instead of `all`, to carry over only
those values. That list form works on LiveKit only: Pipecat and the SLNG
target only support `all`, and refuse a named subset.

When a task lists the handoff control, invoking it ends that task and any
remaining task-group steps before the receiving agent takes over. It never
returns through the agent that delegated the task. This is the direct path for
a caller who changes intent while a focused task is active.

On LiveKit, a receiving agent's own handoffs are hidden only during its first
automatic turn; every other tool stays available, and the handoffs are back on
the next caller turn. See [The opening turn cannot hand off
again](#the-opening-turn-cannot-hand-off-again) below for why, and why
reciprocal handoffs cannot bounce a caller on older carried intent before they
say anything new.

## A handoff does not come back

The second agent owns the call from that point. Nothing returns to the first
agent, and no result is passed back. That is the cost of this shape, and it is why
the example declares a control in each direction: coming back is another handoff,
not a return. The call-start greeting is only for the first entry; a handoff back
continues from the conversation instead of greeting again.

If you want a step that runs and hands control back with an answer, that is a
[task](/build/orchestration/tasks).

## The tool lists are the guardrail

In `examples/salon-concierge`, only `complaint_specialist` has `record_complaint`
and the refund policy. A caller cannot talk the concierge into filing a complaint
or quoting a refund rule, because the concierge has no way to do either.
Splitting agents is as much about splitting capability as it is about splitting
prose.

## The opening turn cannot hand off again

A receiving agent speaks first, and that opening reply is offered every tool it
has except its own handoffs. Without that, two agents whose prompts both say
"send this elsewhere" bounce the call between them before the caller hears
anything.

It applies to the opening turn only. Every turn after it, the agent has its full
list back, including the handoffs. That distinction is load-bearing: an earlier
version leaned on LiveKit's own on-enter tool flag, whose filter follows the
context of everything the opening reply starts, so an agent whose opening reply
ran a delegate never saw its handoffs again, stranding a live caller who asked
for another specialist for ten turns.

## Try it

```sh
unmute validate examples/salon-concierge
unmute dev examples/salon-concierge --target pipecat
```

Say you have a complaint about a service you paid for. The voice keeps going,
but the agent behind it changes.
