title: "Handoffs"
description: "One agent gives the caller to another, with different rules and different tools."
---

A handoff moves the caller from one agent to another. The new agent has its own
prompt, its own tools, and the call for good: nothing comes back.

Reach for it when two jobs have genuinely different rules, not just different
paragraphs. One prompt can only get so long before it starts contradicting itself.

This page follows `examples/subagents`: `booking_desk` takes new appointments,
`appointment_manager` reschedules and cancels.

## Two agents in one package

```yaml agent.yaml
entry_agent: booking_desk

agents:
  booking_desk:
    instructions: instructions.md
    model: reasoning
    voice: voice
    tools:
      - to_appointment_manager

  appointment_manager:
    instructions: agents/appointment-manager.md
    model: reasoning
    voice: voice
    tools:
      - to_booking_desk
```

`entry_agent` decides who answers. Each agent has its own prompt file. They can
share models, or not.

## The handoff

A handoff is a control. You declare it once and put its name in the tool list
of the agent that may use it:

```yaml agent.yaml
controls:
  to_appointment_manager:
    kind: agent_transfer
    to: appointment_manager
    when: The caller wants to reschedule or cancel an existing appointment.
    announce: "I’m connecting you with our appointment manager now."
    context:
      history: full
      variables: all

  to_booking_desk:
    kind: agent_transfer
    to: booking_desk
    when: The caller wants to make a new appointment instead.
    announce: "I’m connecting you back to the booking desk for your new appointment."
    context:
      history: full
      variables: all
```

`when` is the condition the model reads. Write it as the situation, not as an
instruction to call a tool.

`announce` is optional. Write the exact short sentence the active agent should
speak. It is spoken once and finishes before the new agent takes over; the
model does not paraphrase it. Leave it out for a silent handoff. A failed
`requires` guard is checked first and never makes a false announcement.

Prefer a silent handoff when the agents are internal roles behind one service.
The caller can keep talking to the same salon, clinic, or support desk without
hearing implementation details such as “I’m connecting you to another agent.”

`context` decides what the new agent knows. It is the whole of what travels:

| Field | What it does |
|---|---|
| `history: full` | the new agent sees the conversation so far |
| `variables: all` | the values collected so far travel with the caller |

Without them, the caller gets asked for their phone number twice.

A task may list the same `agent_transfer` in its own `tools:`. Calling it stops
that task and the rest of its task group, so a caller can raise a complaint in
the middle of booking without waiting for the booking flow to return first.

On LiveKit, transfer tools are hidden only during the receiving agent's first
automatic turn. Normal tools remain available, and transfers return on the
next caller turn. Reciprocal controls therefore cannot bounce on older carried
intent before the caller says anything new.

## A handoff does not come back

The second agent owns the call from that point. Nothing returns to the first
agent, and no result is passed back. That is the cost of this shape, and it is why
the example declares a control in each direction: coming back is another handoff,
not a return. The call-start greeting is only for the first entry; a handoff back
continues from the conversation instead of greeting again.

If you want a step that runs and hands control back with an answer, that is a
[task](/build/orchestration/tasks).

## The tool lists are the guardrail

In `examples/subagents`, only `appointment_manager` has `cancel_appointment`.
A caller cannot talk the booking agent into a cancellation, because the booking
agent has no way to perform one. Splitting agents is as much about splitting
capability as it is about splitting prose.

## Try it

```sh
unmute validate examples/subagents
unmute dev examples/subagents --target pipecat
```

Say you want to change an appointment you already have. The voice keeps going,
but the agent behind it changes.
