---
title: "Task groups"
description: "Run several tasks in a fixed order, sharing one context, and get one merged result."
---

A task group is an ordered sequence of tasks. The order is a guarantee, not a
request in a prompt.

This page follows `examples/task-groups`: identify the customer, select the
appointment, finalize it.

## Declare the group

```yaml agent.yaml
tools:
  - lookup_customer
  - check_availability
  - book_appointment

agents:
  appointment_desk:
    instructions: instructions.md
    model: reasoning
    voice: voice
    tools:
      - manage_appointment

tasks:
  identify_customer:
    instructions: tasks/identify-customer.md
    tools:
      - lookup_customer
    result:
      customer_id: string
      summary: string
    context:
      history: full

  select_appointment:
    instructions: tasks/select-appointment.md
    tools:
      - check_availability
    result:
      selected_slot: string
      summary: string
    context:
      history: full

  finalize_appointment:
    instructions: tasks/finalize-appointment.md
    tools:
      - book_appointment
    result:
      booking_status:
        enum:
          - booked
          - cancelled
      summary: string
    context:
      history: full

task_groups:
  appointment_flow:
    steps:
      - identify_customer
      - select_appointment
      - finalize_appointment
    context_scope: shared
    then: return
    merge: results

controls:
  manage_appointment:
    kind: delegate
    group: appointment_flow
    when: The caller wants to book, reschedule, or cancel an appointment.
```

Each name in `steps` is a task already declared in `tasks:`.

Every task, including a task inside a group, needs a non-empty `result:` and `context.history`.

| Field | Values | What it does |
|---|---|---|
| `context_scope` | `shared`, `isolated` | whether the steps see one running context or start clean |
| `then` | `return`, `transfer`, `end` | what happens after the last step |
| `then_target` | an agent name | required with `transfer`, illegal otherwise |
| `merge` | `results` | how the steps' results are combined |

## Delegate to the group

The complete example uses the same `delegate` control as a single task, with
`group:` instead of `task:`. The agent lists that control by name. Each member
task lists only the loaded tools it may call.

The agent has one control and no domain tools at all.

## Shared context is the point

With `context_scope: shared`, the service the caller named in step one is still
there in step two. Nothing is passed by hand. With `isolated`, each step starts
from its own prompt, which is what you want when a step should not be
influenced by what came before.

`context_scope` does not replace a task's `context:` block. It decides whether
member tasks share the group's running context. Each task still declares
`context.history` so the task is complete wherever it is used.

## The LiveKit warning

```sh
unmute validate examples/task-groups
```

```text
✓ livekit (livekit)
✓ pipecat (pipecat)

Warnings:
  livekit: LiveKit turn placement is a preference
  livekit: LiveKit TaskGroup is experimental
```

Read the second one. Task groups lower onto a LiveKit primitive that upstream
marks experimental. The package validates, compiles, and runs; the warning
tells you what you are standing on. Warnings go to standard error and the
command still exits 0.

## Try it

```sh
unmute dev examples/task-groups --target pipecat
```

Ask to book an appointment. Watch the three steps run in order, and notice that
nothing asks you the same question twice.
