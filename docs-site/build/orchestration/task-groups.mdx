title: "Task groups"
description: "Run several tasks in a fixed order, sharing one context, and get one merged result."
---

A task group is an ordered sequence of tasks. The order is a guarantee, not a
request in a prompt.

Use a task group instead of the other shapes when:

- several steps must run in a fixed order, and a prompt asking for that order
  is not a guarantee.
- the steps should share what they have learned so far, rather than each
  starting from its own prompt with nothing carried over.
- control should still return to the caller's original agent once every step
  finishes, the same as a single [task](/build/orchestration/tasks) does.

The YAML on this page is one worked group: identify the customer, select the
appointment, finalize it. No shipped example uses a task group, so copy the
shape from here rather than looking for a package.

## Declare the group

```yaml agent.yaml
tools:
  - lookup_customer
  - check_availability
  - book_appointment

agents:
  appointment_desk:
    instructions: instructions.md
    model: reasoning
    voice: voice
    delegates:
      - manage_appointment

tasks:
  identify_customer:
    instructions: tasks/identify-customer.md
    tools:
      - lookup_customer
    result:
      customer_id: string
      summary: string
    context:
      history: full

  select_appointment:
    instructions: tasks/select-appointment.md
    tools:
      - check_availability
    result:
      selected_slot: string
      summary: string
    context:
      history: full

  finalize_appointment:
    instructions: tasks/finalize-appointment.md
    tools:
      - book_appointment
    result:
      booking_status:
        enum:
          - booked
          - cancelled
      summary: string
    context:
      history: full

task_groups:
  appointment_flow:
    steps:
      - identify_customer
      - select_appointment
      - finalize_appointment
    context_scope: shared
    then: return
    merge: results

delegates:
  manage_appointment:
    group: appointment_flow
    when: The caller wants to book, reschedule, or cancel an appointment.
```

Each name in `steps` is a task already declared in `tasks:`.

Every task, including a task inside a group, needs a non-empty `result:` and `context.history`.

| Field | Required | Values and constraints |
|---|---|---|
| `steps` | yes | one or more declared task names, in order |
| `context_scope` | yes | `shared` or `isolated` |
| `then` | yes | `return`, `transfer`, or `end` |
| `then_target` | with `then: transfer` | declared agent name; illegal for `return` and `end` |
| `merge` | no | `results`; omitted also means `results` |

## Delegate to the group

A group rides `delegates:` like any other delegate, with `group:` instead of
`task:`. The agent names it in its own `delegates:` list. Each member task lists
the tools it may call.

The agent has one delegate and no domain tools at all.

A member task may also list a handoff, under its own `handoffs:` key. Calling it
ends that task and skips the group's remaining steps, then hands the caller
directly to the receiving agent.

A task has `tools:` and `handoffs:` and no other list. There is no `delegates:`
and no `escalations:` key on a task, so the shapes that used to be rejected are
now unwritable.

## Shared context is the point

With `context_scope: shared`, the service the caller named in step one is still
there in step two. Nothing is passed by hand. With `isolated`, each step starts
from its own prompt, which is what you want when a step should not be
influenced by what came before.

In a shared group, each exact typed result enters the shared context before the
next task starts. LiveKit labels that result with its source task so the later
task can identify it instead of reconstructing it from conversation wording.
An isolated group carries no results between steps. The final `merge: results`
map is keyed by task name and returns to the owner.

`context_scope` does not replace a task's `context:` block. It decides whether
member tasks share the group's running context. Each task still declares
`context.history` so the task is complete wherever it is used.

## Standing on a LiveKit beta

Task groups lower onto a LiveKit primitive that upstream itself marks
experimental. `unmute validate` prints no warning about this: the package
validates, compiles, and runs cleanly. Know it anyway, because it is a fact
about the platform underneath the feature, not about your package.

## Try it

Add the group above to a package of your own, then `unmute dev` it and ask to
book an appointment. Watch the three steps run in order, and notice that nothing
asks you the same question twice.
