title: "Tasks"
description: "Delegate a step to a focused prompt with its own tools, and get a typed result back."
---

A task is a step the agent hands off and gets back. The task has its own
prompt, its own tools, and a declared result. When it finishes, control returns
to the agent that called it. Its internal turns stay out of the agent's context,
while the completed delegate call stays there so the same request does not run
twice.

The YAML on this page is one worked pair of tasks. For a shipped package that
does it, read `examples/salon-concierge`: a verification task and a booking
task, one of them behind a `requires:` guard.

## Declare the task

```yaml agent.yaml
tasks:
  customer_record:
    instructions: tasks/customer-record.md
    tools:
      - lookup_customer
      - create_customer
    result:
      customer_id: string
      customer_name: string
      record_status:
        enum:
          - existing
          - created
          - failed
      summary: string
    context:
      history: full
```

`result` is the contract. The task must come back with those fields, and
`record_status` can only be one of three values. That is what makes a task
different from a longer prompt: the outcome has a shape.

Every task, including a task inside a group, needs a non-empty `result:` and `context.history`.

**Task `result:` and tool `output:` are different contracts.** Tool contracts
live in `tools/<name>.yaml`; the task's `tools:` list contains names only. The
task result describes the outcome returned after all of its tool calls. Keep
only what the calling agent needs instead of copying an attached tool's output
schema by default.

`context: history: full` gives the task the conversation so far, which is
usually what you want, because the caller has already said something the task
needs.

## Delegate to it

```yaml agent.yaml
controls:
  check_customer:
    kind: delegate
    task: customer_record
    when: Identify the caller before handling an appointment request.
    assign:
      customer_id: result.customer_id
      customer_name: result.customer_name

agents:
  appointment_desk:
    tools:
      - check_customer
      - manage_appointment
```

`assign` copies fields out of the result into package variables, so the rest of
the call can use them without asking again:

```yaml agent.yaml
variables:
  customer_id:
    type: string
  customer_name:
    type: string
```

## Guarding a step

A step that needs a value the conversation has not collected yet declares
`requires:`:

```yaml agent.yaml
controls:
  manage_appointment:
    kind: delegate
    task: appointment
    when: The caller wants to make, change, or cancel an appointment.
    requires:
      - customer_phone
```

Every name must be a declared variable, or the package will not compile. A guard
on a name nothing sets could never pass, and the symptom would be a step that
silently never starts.

**The caller hears nothing.** While `customer_phone` is empty the step does not
run, and the refusal goes to the model rather than to the caller. It names the
missing variable and the control that supplies it, so the model runs
`check_customer` and calls the step again in the same turn. The caller just hears
the next natural question.

The compiler also appends the requirement to the step's own description, so the
model usually collects the value during the earlier turns and never reaches the
guard at all. The guard is the net; the description is the mechanism.

**When the model cannot recover.** After five refusals of the same step the agent
stops recovering quietly and asks the caller for the missing value out loud, in
its own words. It does not fall silent and it does not end the call. That limit
lives in the emitted code, not in a prompt: a model can be argued out of an
instruction, and this exists for the case where it already has been.

Both refusals are logged, with variable and step names only. No caller speech and
no variable value is written, which matters when the identifier is a phone
number.

`requires:` works the same way on an [agent handoff](/build/orchestration/handoffs),
but prefer the step. Guarding the route rather than the work means adding an agent
whose only job is to hold the guard, and the caller has to be spoken through it.

## What the agent can do shrinks

Look at the agent's tool list. It holds two controls and none of the five
domain tools. The agent cannot book anything itself; it can only delegate.
Each task holds the tools its own step needs:

| Task | Tools |
|---|---|
| `customer_record` | `lookup_customer`, `create_customer` |
| `appointment_request` | `check_availability`, `book_appointment`, `cancel_appointment` |

Booking before identification is not a rule in a prompt here. It is
unavailable.

While a task runs, the caller is talking to the task: its prompt, and only the
tools and controls in that task's `tools:` list. The agent's own list is not
offered again until the task returns.

The one control a task may list is `agent_transfer`. Use it when the caller can
change intent during the step and should go straight to another agent. Calling
it ends the task and any remaining task-group steps; the destination takes over
without returning through the task owner. `delegate` and `human_transfer`
controls are rejected on tasks during validation.

That scoping is the useful half of delegation, and also the part to plan for,
because anything the task may need must appear in its own list.

A task that lists no `agent_transfer` still has a way out. Every generated task
prompt ends with one compiler-written rule: when the caller asks for something
none of the step's tools can do, and no handoff on the step covers it, call the
step's finish function right away with the closest result it has, and name that
request in `unserved_request`. You do not write that rule in the task's own
instructions. Without it, a locked-down step keeps refusing the same request
instead of handing the caller on.

The rule is narrow on purpose. It never excuses skipping the step's own work,
the caller's original reason for being in the step is not an unserved request,
and a handoff the step declares always wins over it. Loosely worded, a first
step reads the caller's opening request as out of scope and bails on turn one.

`unserved_request` is a reserved string field on every generated finish,
optional and empty by default. You do not declare it in `result:`, and a task
result that claims the name is a validation error. When it comes back filled,
the returned result carries it, the owning agent is told to take that request
next, and the caller does not have to ask twice.

Only a `then: return` group hands the result to an owner on both targets. With
`then: end` the call is over. With `then: transfer` the Pipecat handback still
carries the results and the rule, while the LiveKit one gives the receiving
agent the pre-flow context only, so the field goes unread there.

## Empty LiveKit task responses

Generated LiveKit tasks retry up to twice when a full successful response has
neither non-whitespace text nor a tool call. Each retry starts immediately in
the same speech turn. It keeps the task state and model settings, and
adds a distinct temporary recovery instruction to a fresh copy of the
conversation context before each retry. After a task tool returns, recovery
keeps only `finish` instead of the full tool list. Non-whitespace text or an
allowed tool call stops recovery.
Errors and cancellations keep LiveKit's normal behavior.

If all three opening attempts are empty, the task speaks one fixed brief
failure, runs no action, and stays active for the caller's next turn. If an
empty reply follows a task tool, recovery can only call `finish`; it cannot run
another operation. Exhausting that recovery asks the caller to check the current
state before trying again. This applies only to generated LiveKit tasks. Normal
LiveKit agents and Pipecat output are unchanged.

## Task or second agent

| | Task | Second agent |
|---|---|---|
| control returns | yes | no |
| result | typed, declared in `result:` | none |
| prompt | one focused step | a whole role |
| use it when | a step has a definite answer | two jobs have different rules |

## Try it

```sh
unmute validate examples/salon-concierge
unmute dev examples/salon-concierge --target pipecat
```

Ask to book a haircut. The agent delegates to `customer_verification` first, and
only then to the booking task, which is held back until the caller is
identified.
