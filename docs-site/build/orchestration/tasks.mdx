---
title: "Tasks"
description: "Delegate a step to a focused prompt with its own tools, and get a typed result back."
---

A task is a step the agent hands off and gets back. The task has its own
prompt, its own tools, and a declared result. When it finishes, control returns
to the agent that called it. Its internal turns stay out of the agent's context,
while the completed delegate call stays there so the same request does not run
twice.

This page follows `examples/multi-task`: one agent, two tasks.

## Declare the task

```yaml agent.yaml
tasks:
  customer_record:
    instructions: tasks/customer-record.md
    tools:
      - lookup_customer
      - create_customer
    result:
      customer_id: string
      customer_name: string
      record_status:
        enum:
          - existing
          - created
          - failed
      summary: string
    context:
      history: full
```

`result` is the contract. The task must come back with those fields, and
`record_status` can only be one of three values. That is what makes a task
different from a longer prompt: the outcome has a shape.

Every task, including a task inside a group, needs a non-empty `result:` and `context.history`.

**Task `result:` and tool `output:` are different contracts.** Tool contracts
live in `tools/<name>.yaml`; the task's `tools:` list contains names only. The
task result describes the outcome returned after all of its tool calls. Keep
only what the calling agent needs instead of copying an attached tool's output
schema by default.

`context: history: full` gives the task the conversation so far, which is
usually what you want, because the caller has already said something the task
needs.

## Delegate to it

```yaml agent.yaml
controls:
  check_customer:
    kind: delegate
    task: customer_record
    when: Identify the caller before handling an appointment request.
    assign:
      customer_id: result.customer_id
      customer_name: result.customer_name

agents:
  appointment_desk:
    tools:
      - check_customer
      - manage_appointment
```

`assign` copies fields out of the result into package variables, so the rest of
the call can use them without asking again:

```yaml agent.yaml
variables:
  customer_id:
    type: string
  customer_name:
    type: string
```

## What the agent can do shrinks

Look at the agent's tool list. It holds two controls and none of the five
domain tools. The agent cannot book anything itself; it can only delegate.
Each task holds the tools its own step needs:

| Task | Tools |
|---|---|
| `customer_record` | `lookup_customer`, `create_customer` |
| `appointment_request` | `check_availability`, `book_appointment`, `cancel_appointment` |

Booking before identification is not a rule in a prompt here. It is
unavailable.

While a task runs, the caller is talking to the task: its prompt, and only the
tools and controls in that task's `tools:` list. The agent's own list is not
offered again until the task returns.

The one control a task may list is `agent_transfer`. Use it when the caller can
change intent during the step and should go straight to another agent. Calling
it ends the task and any remaining task-group steps; the destination takes over
without returning through the task owner. `delegate` and `human_transfer`
controls are rejected on tasks during validation.

That scoping is the useful half of delegation, and also the part to plan for,
because anything the task may need must appear in its own list.

## Empty LiveKit task responses

Generated LiveKit tasks retry up to twice when a full successful response has
neither non-whitespace text nor a tool call. Each retry starts immediately in
the same speech turn. It keeps the task state and model settings, and
adds a distinct temporary recovery instruction to a fresh copy of the
conversation context before each retry. After a task tool returns, recovery
keeps only `finish` instead of the full tool list. Non-whitespace text or an
allowed tool call stops recovery.
Errors and cancellations keep LiveKit's normal behavior.

If all three opening attempts are empty, the task speaks one fixed brief
failure, runs no action, and stays active for the caller's next turn. If an
empty reply follows a task tool, recovery can only call `finish`; it cannot run
another operation. Exhausting that recovery asks the caller to check the current
state before trying again. This applies only to generated LiveKit tasks. Normal
LiveKit agents and Pipecat output are unchanged.

## Task or second agent

| | Task | Second agent |
|---|---|---|
| control returns | yes | no |
| result | typed, declared in `result:` | none |
| prompt | one focused step | a whole role |
| use it when | a step has a definite answer | two jobs have different rules |

## Try it

```sh
unmute validate examples/multi-task
unmute dev examples/multi-task --target pipecat
```

Ask to book a haircut. The agent delegates to `customer_record` first, and only
then to the appointment task.
