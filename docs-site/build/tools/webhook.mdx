The everyday tool. The model decides to call it, Unmute builds the request, and
your API answers.

Reach for a webhook when:

- you already have an API to call
- the URL is a deployment choice, not something to hardcode
- you want no code of your own to write or review

If the work is logic rather than a request, or there is no API to call, write a
[Python handler](/build/tools/python) instead.

```yaml tools/confirm_appointment.yaml expandable wrap
description: Confirm that the existing appointment stays as booked. Call it when the customer says the time works.

input:
  type: object
  properties: {}

inject:
  customer_id: "{{customer_id}}"
  dialed_number: "{{dialed_number}}"
  channel: phone

webhook:
  url_env: SALON_API_URL
  base_url: https://api.example.com
  path: /customers/{{customer_id}}/appointments/confirm
  auth:
    type: bearer
    token_env: SALON_API_TOKEN

announce: One moment while I confirm that.
effect: returns_data
interruption: provider_default
```

This is a worked example rather than a quote. For a real one, every field here
is real: [`examples/slng-support`](https://github.com/slng-ai/unmute/tree/main/examples/slng-support)
ships `tools/search_places_text.yaml`, a webhook tool that carries both
`url_env` and `base_url` the same way, so it deploys to slng and would compile
to a code target too.

`announce:` is the one line worth knowing about here, because a webhook is the
tool most likely to keep the caller waiting. The agent speaks that exact sentence
as the call starts and does not wait for it to finish, so the answer arrives no
later than it would in silence. It is a fixed sentence, and `{{variables}}` are
refused. Full rules in [the behavior fields](/build/tools/overview#the-three-behavior-fields).

## The block

| Field | Required | What it is |
|---|---|---|
| `url_env` | at least one of `url_env`, `base_url` | the UPPER_SNAKE name of an environment variable holding the base URL |
| `base_url` | at least one of `url_env`, `base_url`; required on SLNG | the literal `https://` base URL |
| `path` | no | appended to that base URL; when present it starts with `/` and may carry `{{variable}}` tokens |
| `auth` | no | how the request authenticates |

`url_env` holds a **name**, so the base URL is a deployment choice rather than a
package one: staging and production run the same package against different APIs.
Pipecat and LiveKit Agents read it at run time and never look at `base_url`.

## Naming the base URL for SLNG

SLNG stores the URL in the tool body it pushes, so there is no environment for
it to read at run time: `url_env` alone is not enough there. Leave `base_url`
out and SLNG refuses at compile:

```text
slng: slng target tool "confirm_appointment" names only url_env, and SLNG stores the
  URL in the tool body rather than reading it from an environment: add base_url with
  the literal https host, keeping url_env for the code targets
```

`base_url` has to be a literal address: no `{{variable}}` token in the scheme
or the host, because a name is not a shape SLNG's URL validator accepts. A
`path` on the same tool may still carry one, since that part renders per call
rather than living in the stored body.

Write both fields and each target reads only the one it needs. Drop `url_env`
and the code targets refuse the mirror way:

```text
livekit: livekit target reads a webhook base URL from the environment: tool
  "confirm_appointment" needs url_env, keeping base_url for a hosted target
```

## The path renders per call

```yaml
  path: /customers/{{customer_id}}/appointments/confirm
```

`{{customer_id}}` is a [variable](/build/variables), rendered when the tool is
called, and the rendered value is URL-encoded for you. Because it renders per
call rather than once at session start, a variable the conversation itself filled
in is fine here.

If the variable has no value when the model calls the tool, the call is refused
and the model is told what to ask the caller for, rather than sending a
half-formed request. A token that names nothing at all fails at compile time:

```text
tools/confirm_appointment.yaml:7: tool "confirm_appointment" webhook.path references
  {{not_a_variable}}, which is not a declared variable
```

## Authentication

```yaml
  auth:
    type: bearer
    token_env: SALON_API_TOKEN
```

| Field | What it is |
|---|---|
| `type` | `bearer` or `api_key` |
| `token_env` | environment variable holding the token |
| `header` | header name, `api_key` only, defaults to `X-API-Key` |

Again a name, never a value. A token written in place of a name is refused:

```text
livekit: tool "confirm_appointment" auth token_env must be an UPPER_SNAKE environment
  variable name, never a secret value
```

So is a field from the other scheme, and the message says why:

```text wrap
livekit: tool "confirm_appointment" auth header is not a bearer field: bearer always sends
  Authorization
```

Every name you use here goes in `agent.yaml` under
[`secrets:`](/reference/secrets). The compiler also infers these fields as
required environment names, so leaving one out of `secrets:` warns without
dropping it from generated environment instructions or checks.

**SLNG has no `api_key` scheme of its own.** It sends the token as a bearer
token whichever `type` you wrote, and drops a custom `header`. Write
`type: bearer` if the target is SLNG, so the package says what actually goes
over the wire; the code targets send `api_key` and its header exactly as
written.

## What the model fills in, and what it cannot

`input` is the model's half of the request. `inject` is yours.

```yaml
input:
  type: object
  properties: {}

inject:
  customer_id: "{{customer_id}}"
  dialed_number: "{{dialed_number}}"
  channel: phone
```

Injected values are merged into the call and **never shown to the model**, so it
can neither see them nor overwrite them. That is the place a customer id, a
captured slot, or the number the call went out to rides along. A key cannot be in
both lists, and the refusal explains the reason rather than just the rule:

```text wrap
tools/confirm_appointment.yaml:5: tool "confirm_appointment" injects "customer_id", which
  is also an input property; an injected value is hidden from the model, so it cannot
  double as a parameter the model fills in
```

The tool above takes no parameters at all: everything the API needs is injected.
The model can call it or not call it, and that is the whole of its authority. It
cannot invent a customer id.

A value that is exactly one `{{token}}` keeps that variable's declared type, so a
number stays a number.

Every injected value must be a scalar. Strings, numbers, booleans, and null are
legal; maps and lists are refused.

## Describing the result

```yaml
output:
  type: object
  properties:
    slots:
      type: array
      items:
        type: object
        properties:
          slot_id:
            type: string
          start_time:
            type: string
        required:
          - slot_id
          - start_time
  required:
    - slots
```

`output` is optional author documentation. The compiler checks that it is a
JSON Schema object, but no generator sends it to the model or writes it to the
compile report. Nothing checks the API's response against it either, not even
SLNG: SLNG proxies this request rather than running code of its own, so it has
nothing to introspect a response with. The example records the shape the API
is expected to return; teach the model how to use that data in the tool
description or prompt.

A [`local:`](/build/tools/python) handler's `output:` is the one exception:
SLNG runs that handler itself and checks its return value against it. Full
story in [Python tools](/build/tools/python#the-rules-the-function-follows).
